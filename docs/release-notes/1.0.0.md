Baesian 1.0.0 is the first release on npm, and the first that makes a promise: every later 1.x release keeps working with what this one writes.

Baesian is swipe review for the decisions your coding agents shouldn't make alone. Your Claude Code and Codex agents put each hard-to-undo design decision to you as a card, and you choose between its two options before you see which one the agent picked, then confirm or overrule it. Your answer goes back to the agent, and into git with the code it shapes.

## Install

You need Node 22 or later and git.

```sh
npm install -g baesian
```

Then sign up at [baesian.dev](https://baesian.dev), run `baesian init` and `baesian login` in your repo, and add the plugin:

- **Claude Code:** `/plugin marketplace add GusEllerm/baesian`, then `/plugin install baesian@baesian`.
- **Codex:** `codex plugin marketplace add GusEllerm/baesian`, then `codex plugin add baesian@baesian`, and accept the "Hooks need review" prompt the next time you start Codex.

The [setup guide](https://github.com/GusEllerm/baesian/blob/main/docs/setup.md) has each step in full.

## What every 1.x release keeps working

From 1.0, each later 1.x release:

- reads every file and commit trailer an earlier 1.x release wrote;
- keeps the hosted service's protocol, at `/v1/`;
- keeps the commands, flags, exit codes and MCP tools that `AGENTS.md` and the plugin tell your agents to use. Other output, such as a message's wording, may change.

A release that changes a file's format reads the new format but goes on writing the old one, and the release after it writes the new one, so a teammate, a machine or CI one release behind never meets a file it can't read. The hook blocks `baesian init` writes change the same way. A CLI further behind is told by the hosted service which release to install, before anything is sent or received. The setup guide's [Compatibility](https://github.com/GusEllerm/baesian/blob/main/docs/setup.md#compatibility) section has the details.

No file format changed for 1.0, and it reads every file 0.1.x wrote.

## Coming from 0.1.x

Releases 0.1.0 to 0.1.10 deployed the hosted service, while the CLI and the plugin were built from a clone of this repo. The service now runs 1.0.0, and it refuses a 0.1.x CLI with a message to install 1.0.0. On each machine you use Baesian on:

1. **Install 1.0.0 from npm,** in place of the copy linked from your clone:

   ```sh
   npm uninstall -g baesian
   npm install -g baesian
   baesian --version
   ```

2. **Install the plugin from GitHub,** in place of the one from your clone. In Claude Code, run these from a terminal, then start a new conversation (removing the marketplace you added from a path uninstalls its plugin too):

   ```sh
   claude plugin marketplace remove baesian
   claude plugin marketplace add GusEllerm/baesian
   claude plugin install baesian@baesian
   ```

   In Codex:

   ```sh
   codex plugin marketplace remove baesian
   codex plugin marketplace add GusEllerm/baesian
   codex plugin add baesian@baesian
   ```

3. **In Codex, trust the plugin's hooks again:** start Codex's interactive mode and accept the "Hooks need review" prompt. Until you do, Codex doesn't run them, and `codex exec` skips them without a warning.

Then, in each repo linked to baesian.dev:

4. **Run `baesian ci` again** (or `baesian ci --github`, which sets the variable for you). `BAESIAN_TRUST` then holds the service's key and a spare, which the service keeps offline and never signs with: if the service ever has to replace its key, it switches to the spare and your CI keeps passing. Replace your workflow's Baesian steps with the ones it prints. They run `npx --yes baesian@1.0.0`, pinned, where the steps 0.1.x printed ran whichever release was newest.
5. **Run `baesian init` again,** and commit what it changes: the instructions it writes in `AGENTS.md` now ask agents for the best case for their alternative (`alternative_rationale`). The hook blocks are the same as 0.1.x wrote.

## What's new since 0.1.10

- **On npm,** as `baesian`, and the plugin from this repo's marketplace on GitHub.
- **The plugin checks the CLI's release.** At the start of a session, when the `baesian` on your PATH isn't the plugin's release, or there's none, the agent is told to ask you to install or update.
- **CI runs a pinned release,** the one whose `baesian ci` printed its steps, and moves only in a commit.
- **A spare service key,** pinned in CI beside the service's own.
- **A CLI too old for the service is told which release to install,** before anything is sent or received.
- **Teammates and CI on different releases:** the commit gate counts a hook block that any released Baesian wrote as Baesian's own.
- **Practice cards.** Now and then a past card comes back with its options swapped, the agent's case for its alternative shown as its pick, to measure how often you come round to an agent's case. It never reaches an agent. A blind test of ten comes first, and if your guesses tell practice cards apart from real ones, none comes again.
