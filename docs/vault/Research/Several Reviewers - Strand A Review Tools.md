# Several reviewers, strand A: how review tools share the work

Provenance: one of three research strands run on 2026-11-11 for [[Several Reviewers]] (P20), by an agent working read-only from the web; the synthesis is [[Several Reviewers - Research]]. The questions it answers are that note's Q1 to Q8. Documentation was fetched on 2026-11-11. **Quoted phrases came through a fetch tool that summarises pages, so check exact wording against the page before repeating it anywhere public.** Four papers were read in full: Sadowski et al. 2018, Bacchelli and Bird 2013, Rigby and Bird 2013, and Czerwonka et al. 2015.

## Findings

### GitHub

1. **A review request gates nothing by itself; gating is a separate rule that counts approvals.** Branch protection or a ruleset requires "a specific number of approving reviews" from "people with write permissions in the repository or from a designated code owner". By default the restrictions "don't apply to people with admin permissions". Source: [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches). Documented behaviour. Q2, Q5.
2. **CODEOWNERS routes by path, and any one owner satisfies the requirement.** Owners are "automatically requested for review"; "an approval from any of the owners is sufficient"; "the last matching pattern takes the most precedence". Lines with invalid syntax are skipped, and an owner without access is simply not assigned. Source: [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners). Documented behaviour. Q1, Q2. Failure mode: one-of-N approval, and misconfiguration fails silently.
3. **Rulesets can require approvals per team by file pattern:** "up to 15 different teams", each with required approvals "from 0 (zero) to 10". Zero means "the team will be added for visibility" without needing to approve: a built-in observer role, and a count that rises by area. Source: [Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets). Documented behaviour. Q1, Q2, Q5.
4. **A team request notifies everyone unless it's resolved to named people.** "Requesting a review from a large team can notify every team member." Code review assignment removes the team and assigns "a specified subset of team members": round robin picks "who's received the least recent review request", "regardless of the number of outstanding reviews"; load balance "tries to ensure that each team member reviews an equal number of pull requests in any 30 day period". Members with status Busy are skipped; "if all team members are busy, the pull request will remain assigned to the team itself". Sources: [Managing code review settings for your team](https://docs.github.com/en/organizations/organizing-members-into-teams/managing-code-review-settings-for-your-team), [Requesting a pull request review](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/requesting-a-pull-request-review). Documented behaviour. Q1, Q6, Q7. Failure mode: with everyone busy it falls back to the group, the diffuse state again.
5. **"Request changes" is a personal block that only its author can lift, or a permitted person can dismiss with a reason.** If they're unavailable, "anyone with write permissions" can dismiss, which can be restricted to named people; "you must add a comment explaining why", and dismissing "changes the status of the review to a review comment", so the dissent stays on the record. Source: [Dismissing a pull request review](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/dismissing-a-pull-request-review). Documented behaviour. Q3, Q5.
6. **Every tool ties an approval to the version it was given on.** GitHub: "dismiss stale pull request approvals when commits are pushed", and "require an approval from someone other than the last person to push". GitLab: "an approval on a merge request is removed when you add more changes" (on by default). Gerrit: copy conditions decide which votes carry over; the rest are "outdated", and the voter re-enters the attention set. Azure DevOps: "reset all approval votes". Phabricator: "Accepted Prior Diff". Sources: the rulesets page above; [GitLab approval settings](https://docs.gitlab.com/user/project/merge_requests/approvals/settings/); [Gerrit labels](https://gerrit-review.googlesource.com/Documentation/config-labels.html); [Azure DevOps branch policies](https://learn.microsoft.com/en-us/azure/devops/repos/git/branch-policies). Documented behaviour. Q2, Q3: a card revised after an answer.

### GitLab

7. **An approval rule is a count plus a set of eligible approvers, and several rules can apply at once.** "A value of 0 makes the rule optional." Authors are excluded by default. Code Owner sections are "analyzed separately, and always enforced", can be made optional, and can demand a count. Sources: [Approval rules](https://docs.gitlab.com/user/project/merge_requests/approvals/rules/), [Code Owners reference](https://docs.gitlab.com/user/project/codeowners/reference/). Documented behaviour. Q1, Q2, Q5.
8. **GitLab separates who sets the rules from who is bound by them, and can demand re-authentication to approve:** "Require user re-authentication (password or SAML) to approve", the closest analogue to a hard answer proved by a passkey. "Request changes" blocks a merge, but someone with merge permission can bypass it. Sources: the approval settings page; [Merge request reviews](https://docs.gitlab.com/user/project/merge_requests/reviews/). Documented behaviour. Q3, Q5.
9. **GitLab built an attention-request feature and chose not to launch it.** The problem: reviewer and assignee status "do not indicate if any action is required on your part". The outcome: "We've made the decision to not launch the attention requests feature", because "there were just too many outstanding concerns"; the page doesn't say which. Source: the epic [Merge requests that require my attention](https://gitlab.com/groups/gitlab-org/-/epics/5331). Primary record, reasons not given. Q7.

### Gerrit

10. **Votes are graded, and the rule is "any top vote enables, any bottom vote blocks".** Code-Review: -2 "any -2 blocks submit"; -1 "does not block submit"; +1 "looks good to me, but someone else must approve"; +2 "any +2 enables submit". Who may cast which range is a permission per group. Submit requirements are queries, such as `label:Code-Review=MAX&user=non_uploader AND -label:Code-Review=MIN`, with an `overrideIf` for emergencies. Sources: [Labels](https://gerrit-review.googlesource.com/Documentation/config-labels.html), [Submit requirements](https://gerrit-review.googlesource.com/Documentation/config-submit-requirements.html), [Access controls](https://gerrit-review.googlesource.com/Documentation/access-control.html). Documented behaviour. Q2, Q3, Q5.
11. **The attention set records whose turn it is, apart from who is a reviewer.** "For every change, Gerrit maintains an 'Attention Set' with users that are currently expected to act." Adding a reviewer adds them; replying removes the replier; a reviewer's reply adds the owner; submitting clears it. The norm: "If you don't plan to respond within ~24h, then you should either remove yourself from the attention set" or tell the owner. Anyone can edit the set, and a hovercard shows why and when someone was added. The dashboard has "Your turn"; every email begins "Attention is currently required from:". The rules "are not meant to be super smart". Source: [Attention set](https://gerrit-review.googlesource.com/Documentation/user-attention-set.html). Documented behaviour. Q6, Q7.
12. **Gerrit replaced a single-assignee field with the attention set.** Its design documents give the reasons: "only one user can be assigned"; the Reviewed flag "is strictly personal and not visible to other users"; participants were emailed on every event, and "users have trouble identifying relevant messages"; the design preferred "multiple people's attention to not force reviews to occur in sequence". Sources: [Attention set use cases](https://www.gerritcodereview.com/design-docs/attention-set-use-cases.html), [conclusion](https://www.gerritcodereview.com/design-docs/attention-set-conclusion.html), [3.8 release notes](https://www.gerritcodereview.com/3.8.html). Primary design record. Q1, Q6, Q7.

### Google

13. **Google splits approval into three kinds that one person usually holds together:** correctness, ownership and readability; "most reviews have one person assuming all three roles". "Only one LGTM is required by default." "The cost of additional reviewers quickly outweighs their value." "The most important LGTM is the first one." A team alias is resolved to one person by a tool. On disagreement: seek consensus, then escalate to a tech lead, maintainer or manager; "don't let a CL sit around because the author and the reviewer can't come to an agreement". Sources: *Software Engineering at Google*, [chapter 9](https://abseil.io/resources/swe-book/html/ch09.html) and [chapter 19](https://abseil.io/resources/swe-book/html/ch19.html); the [review speed](https://google.github.io/eng-practices/review/reviewer/speed.html) and [standard](https://google.github.io/eng-practices/review/reviewer/standard.html) guides. A practitioner's account by the organisation that runs the process. Q1, Q2, Q3, Q6, Q7.
14. **At Google one reviewer is the norm, and review is fast.** From 12 interviews, 44 survey responses and logs of about 9 million changes: "fewer than 25% of changes have more than one reviewer", median 1. Median wait for first feedback "under an hour for small changes"; for the whole review "under 4 hours". Many teams assign reviews sent to a team address "in a round-robin manner, taking into account review load and vacations". "New team members are explicitly added as reviewers since they have not yet built up reviewing/editing history." A reported breakdown is "power": "dragging out reviews or withholding approvals". "The majority of changes are small, have one reviewer and no comments other than the authorization to commit." Source: Sadowski, Söderberg, Church, Sipko, Bacchelli, [Modern Code Review: A Case Study at Google](https://sback.it/publications/icse2018seip.pdf), ICSE-SEIP 2018, read in full. Empirical. Q1, Q2, Q6, Q8.

### Phabricator, Azure DevOps, Kubernetes, Apache, Rust

15. **Phabricator distinguishes normal from blocking reviewers:** a revision can't be accepted until a blocking reviewer has accepted, resigned or been removed. Resign is an explicit "not me". Owners packages can be added automatically as reviewer, blocking reviewer or subscriber. Herald rules come in three scopes with different authors: personal, object and global. Sources: [Mozilla's Phabricator notes](https://wiki.mozilla.org/Phabricator/Bugzilla_Equivalents), [Owners](https://secure.phabricator.com/book/phabricator/article/owners/), [Herald](https://secure.phabricator.com/book/phabricator/article/herald/). Documented behaviour; the acceptance rule is from an operator's wiki. Q1, Q2, Q3, Q5.
16. **Azure DevOps makes required or optional a property of each automatically included reviewer.** A group reviewer is satisfied by any member. Options include "prohibit the most recent pusher from approving their own changes", and "allow completion even if some reviewers vote to wait or reject", which keeps the minimum approvals and lets dissent not block. Source: [Branch policies](https://learn.microsoft.com/en-us/azure/devops/repos/git/branch-policies). Documented behaviour. Q1, Q2, Q3.
17. **Kubernetes uses two roles per area:** reviewers (`/lgtm`) for code quality, approvers (`/approve`) for "holistic acceptance criteria". Automation suggests reviewers. "An approver's /lgtm is simultaneously interpreted as an /approve", which the page says "goes against the idea of having at least two sets of eyes". Inactive reviewers are pruned, and approvers moved to `emeritus_approvers`. Source: [OWNERS files](https://www.kubernetes.dev/docs/guide/owners/). Documented process. Q1, Q2, Q5, Q6, Q8.
18. **Apache and Rust publish explicit quorum and dissent rules.** Apache: only PMC members' votes bind; a code change needs three +1 and no -1; a -1 is a veto that "cannot be overruled nor overridden by anyone", but "a veto without a justification is invalid"; votes run "at least 72 hours"; lazy consensus means "silence gives assent". Rust RFCs: "all members of the subteam must sign off", then a final comment period of "ten calendar days"; rfcbot records named blocking concerns, and "only the original author can mark their concern as resolved". Sources: [Apache voting](https://www.apache.org/foundation/voting.html), [Rust RFCs](https://github.com/rust-lang/rfcs/blob/master/README.md), [rfcbot](https://github.com/rust-lang/rfcbot-rs). Documented process. Q2, Q3, Q5, Q6.

### Triage, shared inboxes, on-call, peer review

19. **Linear enforces one assignee and puts a triage inbox in front of the team.** "Issues in Linear are assigned to a single person at a time, giving teams clear ownership." Triage is "a special inbox for your team" with accept, decline, duplicate and snooze; "triage responsibility" names who is notified or assigned, and can follow an on-call schedule. GitHub is the contrast: "issues and pull requests support up to 10 assignees". Sources: [Assigning issues](https://linear.app/docs/assigning-issues), [Triage](https://linear.app/docs/triage). Documented behaviour. Q1, Q6, Q7.
20. **Front allows one assignee and balances load with caps.** "A conversation can only be assigned to one user at a time." Load balancing assigns to "the teammate with the fewest open assigned shared conversations"; "if all teammates are at their limit, assignment rules will pause"; rules skip teammates "marked as Out of office or Busy". Source: [Front help](https://help.front.com/en/articles/2344). Documented behaviour. Q1, Q6.
21. **Help Scout detects collisions at send time.** Indicators show who is viewing and who is replying. If the conversation changed while someone was writing, it "stops the reply from being sent and gives the User a chance to review new updates": they can send it as it is, edit it or discard it. Source: [Traffic Cop](https://docs.helpscout.com/article/99-traffic-cop). Documented behaviour. Q3, Q7: a second answer arriving after a first.
22. **PagerDuty treats silence as a timed event.** An escalation policy is "an ordered set of rules"; the default escalation timeout is 30 minutes; several targets on a rule are "notified at the same time"; a policy can repeat "up to nine times", after which "the incident will stay assigned to the last user and will not continue to notify". Source: [Escalation policies](https://docs.pagerduty.com/incident-management/schedules/escalation-policies). Documented behaviour. Q6, Q7. Failure mode: the chain ends in a silent stall.
23. **PagerDuty separates "I have it" from "it's done".** "The user who acknowledges an incident claims ownership of the issue and halts the escalation process"; "acknowledging only halts escalation". An acknowledgement timeout returns the incident to triggered, but "is turned off by default". Sources: [Incidents](https://docs.pagerduty.com/incident-management/incidents/overview), [Round robin scheduling](https://docs.pagerduty.com/incident-management/schedules/round-robin-scheduling). Documented behaviour. Q2, Q6, Q7.
24. **HotCRP is the one tool found that hides other reviewers' answers by default:** "a PC member can see a paper's reviews only after completing their own review for that paper". GitHub, GitLab, Gerrit, Phabricator and Azure DevOps all show earlier votes to later reviewers. Source: [HotCRP chair's guide](https://help.hotcrp.com/help/chair). Documented behaviour; no rationale given. Q4.

### Studies

25. **Two active reviewers is the number practice converges on, however many are invited.** At Microsoft the median invited was 3, 3 and 4, but "the median number of people that actually take part in a review (other than the author) is 2"; there was "only a minimal increase in the number of comments about the change when more reviewers were active". It cites Porter et al.: "two reviewers discovered as many defects as four reviewers". Some reviews with no activity were "used for awareness purposes only"; others "simply received no attention from the invited reviewers". Source: Rigby and Bird, [Convergent Contemporary Software Peer Review Practices](https://users.ece.utexas.edu/~miryung/teaching/EE379K-Spring2014/Papers/Paper%204.pdf), ESEC/FSE 2013, read in full. Empirical, several projects' logs. Q1, Q2, Q6.
26. **People add recipients for awareness, not decision, and familiarity changes a review's quality.** Authors added a mailing list as an "optional" reviewer "so that everybody [in the team] is notified". 716 respondents (82%) said reviewers familiar with the files give different feedback: "substantially deeper, more detailed and insightful". Source: Bacchelli and Bird, [Expectations, Outcomes, and Challenges of Modern Code Review](https://sback.it/publications/icse2013.pdf), ICSE 2013, read in full: 17 developers observed, 165 managers and 873 programmers surveyed. Empirical, mixed methods. Q1, Q5, Q8.
27. **Assigning one named person where only a team was assigned cut time in review by 11.6%, in a randomised experiment.** At Meta, "on diffs that only had a team assigned, we randomly selected one of the top three recommended reviewers": 12.5k authors, spring 2023. Time in review fell 11.6% (p well under 0.01); time spent reviewing didn't change (p = 0.37): "We did not find that reviewers rushed reviews." The authors' hypothesis: "the bystander effect might be slowing down reviews of these diffs because no single individual was assigned". Source: Rigby et al., [Improving Code Reviewer Recommendation: Accuracy, Latency, Workload, and Bystanders](https://arxiv.org/html/2312.17169v2). Empirical, an A/B experiment: the only direct experimental evidence found on requests addressed to a group. Q1, Q6.
28. **Balancing load against expertise is a real trade-off, and authors resist it.** At Meta, ranking by workload cut the top recommendation's workload by 18 points and its accuracy by 4.9; "the top recommended low workload reviewer was often not selected". Mirsaeedi and Rigby (ICSE 2020): assigning by ownership concentrates knowledge and raises turnover risk "by up to 65%". Sources: the paper above; [the abstract](https://core.ac.uk/works/77729055), read as an abstract only. Empirical. Q1, Q6, Q8.
29. **Invited reviewers often don't respond, and a wrong first choice is costly.** Across 230,090 patches in Android, LibreOffice, OpenStack and Qt, "16%-66% of patches have at least one invited reviewer who did not respond". Reviews with a reviewer-assignment problem took "12 days longer to approve". Sources: Ruangwan et al., [arXiv 1806.10277](https://arxiv.org/abs/1806.10277); Thongtanunam et al., SANER 2015, seen only through search. Empirical. Q1, Q6.
30. **Targeted reminders shorten the slow tail.** Meta's Nudgebot: "the average Time In Review for all diffs dropped 7 percent" and "the proportion of diffs that waited longer than three days for review dropped 12 percent". Microsoft's Nudge, a randomised trial on 147 repositories, reduced "pull request resolution time by 60% for 8,500 pull requests". Sources: [Meta's engineering blog](https://engineering.fb.com/2022/11/16/culture/meta-code-review-time-improving/); Maddila et al., [arXiv 2011.12468](https://arxiv.org/abs/2011.12468). Empirical, experiments at two companies. Q6, Q7.
31. **Low participation is linked to defects, and a speed target needs a guard against rubber-stamping.** In Qt, VTK and ITK, low review participation was estimated to produce components with up to five more defects after release. Meta chose "Eyeball Time" as a guardrail because optimising for speed "could lead to negative side effects, like encouraging rubber-stamp reviewing". Sources: McIntosh, Kamei, Adams, Hassan, [MSR 2014](https://rebels.cs.uwaterloo.ca/confpaper/2014/05/30/the-impact-of-code-review-coverage-and-code-review-participation-on-software-quality.html); the Meta blog above. Empirical, three projects; practitioner. Q2, Q6.
32. **Divergent votes are common and usually end in acceptance.** In OpenStack and Qt, patches with divergent scores "account for 15%-37% of patches that receive multiple review scores"; they're integrated more often than abandoned, and "receive negative scores after positive ones in 70% of cases". Source: Hirao, McIntosh, Ihara, Matsumoto, [Code Reviews with Divergent Review Scores](https://arxiv.org/abs/2104.01537), IEEE TSE 2020, abstract read. Empirical. Q3, and Q2: a later reviewer often catches what the first approver missed.
33. **Evidence that seeing earlier votes biases later reviewers is weak.** Across 83,750 patches, the amount of prior feedback is "highly associated with the likelihood that the reviewer will provide a positive vote", but the associations "are not as strong as the confounding factors". In a controlled experiment with 85 developers, existing comments biased nothing, except that a comment about an unusual kind of bug made reviewers likelier to find another of that kind. Sources: Thongtanunam and Hassan, [TSE 2021](https://2021.icse-conferences.org/details/icse-2021-Journal-First-Papers/14/Review-Dynamics-and-Their-Impact-on-Software-Quality); Spadini, Çalikli, Bacchelli, [ICSE 2020](https://2020.icse-conferences.org/details/icse-2020-papers/17/Primers-or-Reminders-The-Effects-of-Existing-Review-Comments-on-Code-Review); abstracts read. Empirical. Q4.
34. **A new reviewer becomes useful after a few exposures to the same area.** "Without prior exposure ... only 33% of any reviewer's comments are deemed useful." "When reviewing the same part of code base for the third time, the usefulness ratio increases to about 67%. By the fourth time, it is equivalent to the project's long-term average." Source: Czerwonka, Greiler, Tilford, [Code Reviews Do Not Find Bugs](https://microsoft.com/en-us/research/wp-content/uploads/2015/05/PID3556473.pdf), read in full: an experience report citing internal data, its method not described. Q8.
35. **Reviewer recommendation adds little where people already know whom to ask.** Over more than 21,000 reviews at one company there was no evidence that recommendations influenced choices; users found them relevant, but they "rarely" added value. Source: Kovalenko et al., [Does Reviewer Recommendation Help Developers?](https://research.tudelft.nl/en/publications/does-reviewer-recommendation-help-developers), IEEE TSE, abstract seen through search. Empirical. Q1, for small teams.

## Patterns

- **Asking and gating are separate.** Who is requested is one setting; whose approval counts is another: GitHub, GitLab, Gerrit, Phabricator, Azure DevOps (1, 7, 10, 15, 16).
- **Address a group, resolve to one named person:** GitHub's code review assignment, Google, Meta's recommender, Linear's triage responsibility, Front's rules, PagerDuty's round robin (4, 13, 14, 19, 20, 23, 27).
- **Any one member of the owning group suffices:** CODEOWNERS, Azure DevOps group reviewers, Google's owners (2, 13, 16).
- **One accountable holder, others watch:** Linear and Front (one assignee), PagerDuty (the acknowledger owns it), GitHub's zero-approval teams and Microsoft's "optional" reviewers as observers. Gerrit is the deliberate exception, with several people's attention at once (3, 12, 19, 20, 23, 26).
- **An asymmetric rule: one qualified yes enables, one qualified no blocks, weaker votes advise:** Gerrit, "request changes" in GitHub and GitLab, Phabricator's blocking reviewers, Apache's vetoes (5, 8, 10, 15, 18).
- **Counts rise by area or stake, not everywhere** (3, 7, 13, 17, 18).
- **An approval is bound to a version** (6).
- **An explicit state for whose turn it is:** Gerrit's and Google's attention sets, PagerDuty's triggered, acknowledged, resolved; Help Scout's viewing and replying. GitLab tried it and withdrew (9, 11, 13, 21, 23).
- **Silence is timed:** PagerDuty's escalation, Gerrit's 24 hours, Google's one business day, nudge bots, Apache's 72 hours, Rust's ten days (11, 13, 18, 22, 30).
- **A cheap, explicit way to say "not me":** Gerrit, Phabricator's Resign, GitHub's Busy, Front's Out of office (4, 11, 15, 17, 20).
- **Overrides are permissioned and leave a record** (5, 8, 10).
- **Earlier verdicts are visible by default** in every code review tool; HotCRP is the exception (24, 33).

## Failure modes worth designing against

- **Diffusion of responsibility when a group is asked.** Team-only assignment was measurably slower (27); 16% to 66% of patches had an invitee who never responded (29); three or four are invited and two act (25); GitHub's fallback when all are busy is the team again (4).
- **A silent stall at the end of the chain.** PagerDuty stops notifying after its repeats (22); Front's rules pause when everyone is at their limit (20). An agent waiting on a blocking or hard card needs a defined last state.
- **Load that's unfair, or blind to expertise.** Round robin ignores outstanding work (4, 19); routing by expertise concentrates work and knowledge (28); authors bypass load-balanced suggestions (28).
- **Rubber-stamping under pressure for speed.** Most Google changes are approved with no comments (14); low participation goes with defects (31); Meta needed a time-spent guardrail (30, 31). A blind first choice is one such guard; time to answer is another signal.
- **One-of-N approval hiding the lack of a second look** (2, 6, 17).
- **Notification noise** (4, 9, 12).
- **Stale approvals:** every tool needed a rule (6). Here: a card revised after an answer.
- **A block held by someone absent or obstructive:** GitHub needed dismissal (5); Google reports withheld approvals as a power problem (14); Apache voids a veto without a reason (18).
- **Treating disagreement as an exception.** It happens on 15% to 37% of patches scored more than once, usually ends in acceptance, and the negative vote usually comes second (32). "First answer wins" would throw those later objections away.
- **Assuming anchoring is the main risk of visible answers.** The code review evidence for bias is weak (33). The stronger argument for blind answers is the independence of a second check.
- **New reviewers answering cold** (14, 34).
- **Building routing machinery a small team doesn't need** (35).

## Not verified

- **Exact wording** of quoted documentation, as above.
- Bosu, Greiler and Bird, "Characteristics of Useful Code Reviews" (MSR 2015): not read.
- Thongtanunam et al., SANER 2015: the claim that 4% to 30% of reviews have a reviewer-assignment problem; only "12 days longer" was seen, in an abstract surfaced by search.
- Read as abstracts or search snippets only: Kovalenko et al.; Mirsaeedi and Rigby; Hirao et al.; Thongtanunam and Hassan; Spadini et al.; Ruangwan et al.
- Meta's nudge paper (FSE 2022): the numbers are from Meta's blog and a third party's summary.
- Phabricator: upstream documentation doesn't say when a revision becomes accepted; the rule in finding 15 is from Mozilla's wiki.
- GitHub: whether a team's review-request notification is cleared for the other members once one of them reviews.
- GitLab: whether one approval from any listed code owner satisfies a section by default; why attention requests were withdrawn.
- PagerDuty: what the other targets on a level see once one acknowledges.
- Not found: any study of GitHub's team review requests in particular; any study measuring the effect of hiding earlier reviewers' votes in code review.
