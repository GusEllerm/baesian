# src/cli.ts

The CLI is tier 0 (D27): every harness can run it. `buildProgram` defines the commands, and `main` runs them and returns the exit code. `src/bin.ts` is the npm entry point. A reader that stops early (`baesian show B-x | head -1`) closes the pipe the command writes to: `src/bin.ts` ends the command there, quietly and with exit code 0, as a shell's own tools do, where it used to crash on Node's unhandled `EPIPE`.

All output goes through an `Io` object, and Commander's own output and exits are routed through it too (`exitOverride`), so tests drive `main` directly. Stdin is read as a stream (`readStdin`), because `readFileSync(0)` fails with `EAGAIN` on a pipe whose writer hasn't written yet.

The agent commands' logic is in `src/ops.ts` (below), which the MCP server calls too (P18), so the commands only parse their arguments and print what an operation returns: its lines, or with `--json` its data. Every line is built from the patterns in `src/style.ts` and rendered for the stream it goes to ([[#What it prints: src/style.ts (B-eyrt5)]]).

**In a linked repo (M9d)** the commands sync through the relay ([[src-sync]]), with no daemon: the filing commands (`file`, `revise`, `reply`, `rule`, `attach`, `withdraw`, `deck`) pull first and push after (`aroundFiling()`); `inbox` pulls, and pushes what's waiting; `wait` listens on the relay's socket (`waitWithRelay()`); `sync` pulls and pushes; the `pre-commit` hook pulls for at most three seconds ([[src-gate]]). What the relay said goes to standard error, so a command's output is its own; offline or signed out, everything works as before, and what's new goes up at the next command that reaches the relay. `Io.http` (a fetch and a signal), `Io.sleep` (between `login`'s polls) and `Io.run` (the `gh` that `ci --github` runs) are replaceable in tests. A repo that isn't linked does exactly what it did.

| `sync` | in a linked repo, pulls the relay's log and pushes what it doesn't have (M9d), saying how many files went each way; then copies new verdicts and ledger entries into the record, and, with a vault, writes its notes (`writeNotes`, D170) without staging them. A copy of another repo, whose history starts elsewhere, is linked to a project of its own; a config with no first commit gets it. Approving a new project asks the person to name it on that page (B-zqkwk), and `login` says so; the repo's own name is never sent. Then the first sync: everything an agent wrote goes up (B-6k0rk), and the answers from before linking (B-3zjjx), saying first how many files it sends (`SyncOptions.sending`), since a repo with a history of cards sends hundreds. It ends with the project, the relay's counts and the project's page as fields and, for a repo it linked, `next: git add … && git commit …`, ready to run, which commits the link with its `Baesian-Ack:` line as its own paragraph (B-w4g6c); the ack cites no decision, since it's kept in the repo's history. Signed in already, it says so. **A personal clone** (B-4rwyz) is linked in its own config, `.git/baesian/config.json`, with nothing to commit, which it says instead |
| `logout` | revokes this machine's grant on the service and deletes the grant file; offline, it deletes the file and says to revoke the machine on the website |
| `ci [--github] [--json]` | in a linked repo, pulls from the relay, then prints what CI needs to run `verify` (B-pt52b, [[src-sync#src/ci.ts: setting up CI (B-pt52b)]]): the service it read the keys from, `BAESIAN_TRUST`'s lines (the project's, B-mar8x; the service's key; the passkeys the service signed), read from the live layer, never the record, with a request to compare the passkeys with the account page; and the GitHub Actions steps. `--github` then sets the repository variable with `gh` (`Io.run`), if it's on PATH. Not linked, signed out or offline, it says what to run first, with exit 1. In a personal clone (B-4rwyz) there's no committed record for CI to check: it says so, and how to switch to shared mode, with exit 1, rather than print a pin |
| `check [--message <file>] [--json]` | previews the commit gate on the staged changes, as the hooks would print it (`describeReport`, [[src-gate]]): the decisions found, and what covers them, or why the commit would be blocked, the trailers to paste, and `baesian check --message <file>` as the next step. Exits 1 when the commit would be blocked, with `--json` too. In a personal clone it adds that the trailers will be taken out of the message |
| `verify [--base <ref>] [--merge] [--file-conflicts]` | CI: reruns the gate on every commit since the base, against its own committed record. `--merge` adds the merge gate and conflicting decisions ([[src-verify]]). Its headline says what failed; each commit is a row, a failing one followed by why and the trailers that would cover it; and a failure ends with the `git rebase -i` that rewords it (`describeVerify`). Run in a personal clone, it notes that it sees none of the clone's decisions |
| `mcp` | the MCP server, over stdio, for a harness to start; the plugin registers it ([[src-mcp]], `serveMcp`) |
| `hook <name> [args…]` | hidden; what the installed git hooks call (`runHook`). `pre-push` reads the refs being pushed from its input (B-h7rsv); in a personal clone, `post-rewrite` reads the rewritten commits from its input |

No command resolves a card (D32). **In a personal clone** (B-4rwyz), every command but `hook`, `mcp`, `init` and a quiet `inbox` first warns of anything `personalProblems()` finds ([[src-gate#Personal mode (B-4rwyz)]]): above all, a gate that's off because the clone's `.git/config` no longer includes Baesian's setting, or reads another after it, which `baesian init --personal` puts right. When `init` installs the hooks, it records how to rerun this CLI (`selfCommand`), for hooks run where `baesian` isn't on PATH (D48). `selfCommand` resolves the script path first: under `npm link` or a global install, `argv[1]` is the bin symlink, not the `.js` file. Run from source, there is no fallback, so the hooks rely on PATH.

## What it prints: src/style.ts (B-eyrt5)

The user decided what the command line prints on 2026-11-05, in the deck `cli-output`, from an audit of every command's output: one system, two renderings (B-eyrt5); citations of Baesian's own decisions behind a verbose flag (B-728jd); the command line decides colour, plainly for agents (B-qszqr); symbols as well as colour (B-t3tev); and what every row of `list` shares, said once (B-gff98).

- **One wording.** Every command builds its output as `Line`s from six patterns: a headline saying what happened, with the card's ID (`head`, and `failed` for an error); aligned `label:` fields (`fields`); rows with a header (`table`); next steps, `next: <command>  # why`, the command first so the line pastes, IDs filled in (`next`); `note:` and `warning:` lines; and errors, a headline then a next step (`errorLines`, from a `Told` error's steps; `failureLines` adds `baesian list --all` for a card that isn't there, for the CLI and the MCP server alike). Text others wrote stays a quoted JSON string, with its author named (D169), so it can't carry a terminal's escape codes; any other control character prints as an escape (`\u001b`).
- **Two renderings (`render`).** Plain text (`plain`, `PLAIN`) is the contract: what agents read through a pipe, and what the MCP server and the plugin's hooks get, never wrapped, one item a line. A terminal gets the same words styled, in the 16 standard colours by role, painted by `util.styleText` told not to check the stream: green success, yellow attention, red failure, magenta a hard card, cyan commands, bold IDs and headlines, dim explanations. A headline starts with ✓ (done), ✗ (blocked or failed), ! (needs attention) or → (a next step, in place of `next:`); a terminal that can't show them (`unicodeTerminal()`: not a UTF-8 locale, nor Windows Terminal; the Linux console; `TERM=dumb`) gets `ok`, `x`, `!` and `->`. Prose wraps at the terminal's width, at most 100 (`MAX_WIDTH`), hanging under its column; IDs, JSON, YAML and commands never break mid-token, and a command alone breaks only before a flag or `&&`, outside quotes, with a `\`. Trailer lines (`trailer`) are never styled, prefixed or indented, so they paste: git reads no trailer from an indented line.
- **Who gets which (`renderFor`, for each stream).** `--color` and `--no-color` decide it whatever else is set, and `--no-color` gives exactly what an agent reads. Otherwise an agent's harness gets plain text, even in a pseudo-terminal: any of `HARNESS_VARS` set (`CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `AI_AGENT`, `CODEX_THREAD_ID`, `GEMINI_CLI`, `CURSOR_AGENT`, `OPENCODE`; `harnessVar()`). A terminal gets symbols and wrapping, and colour unless `NO_COLOR` is set (even with `FORCE_COLOR`), it has none, or `FORCE_COLOR=0`. `FORCE_COLOR` gives a pipe colour and symbols, never wrapped. `settingsOf()` reads the three global flags before Commander parses the arguments, so its errors follow them too. `Io.terminal` says what each stream is; tests leave it out, and read plain text.
- **The hooks** (`runHook`) print each line after `baesian: `, a wrapped line too, but the trailers, so git's own lines can be told apart (`HookIo.how`, `Render.prefix`).
- **Usage** (`buildProgram`): a wrong flag or command prints a line and where to get help, `next: baesian list --help`, not the whole help; the help groups the commands (`commandsGroup()`); `baesian --version` prints the package's version (`VERSION`).

**Citations (B-728jd): src/cite.ts.** Citations of Baesian's own decisions, `(B-4rwyz)` or `(D42, D144)`, are marked where they're written, with `cite()` or `citeIn()`; nothing finds them by matching the finished text, which would catch the user's own card IDs. The marks are two characters from Unicode's private use area, around the citation and its punctuation; `unmark()` takes them out, citation and all, or with `--verbose` only the marks, so the citation prints where it was. Everything that leaves Baesian goes through it: `render`; `--json` and the MCP server's structured content (`unmarkJson`, `unmarked`); the local server's responses; the relay, for the one judgement it sends the website; and errors. An error that may cite is a `Told`: its `message` is plain text, citations out and its steps as `next:` lines, for the MCP server, the local server and the relay to print as it is, while the CLI renders its `marked` text and `steps`. The store's messages that data carries (a file that doesn't count, a note from the merge gate) keep their marks until they're printed; tests read them with `cited()`, which puts the citations back.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | done; for `wait`, resolved: use the decision |
| 1 | error, or a usage error |
| 3 | `file`: a possible duplicate (`EXIT_POSSIBLE_DUPLICATE`) |
| 4 | `wait`: answered but not a go-ahead (returned, deferred, withdrawn, superseded) |
| 5 | `wait`: no verdict yet; proceed provisionally |
| 6 | `wait`: no verdict on a hard card; don't proceed |
| 7 | `wait`: no verdict yet, and the reviewer is still there; run it again (D101) |
| 8 | `wait`: the card is held back by the repo's preferences; go ahead with your pick, as provisional: it counts as settled at merge (D150, B-chq61) |
| 130 | `wait`: stopped with Ctrl-C (`WaitCancelled`) |

`WAIT_EXIT` holds codes 4–8. `AGENTS_BLOCK` lists them for agents, and a test keeps the two in step.

**On several cards (B-xnae9, `exitCodeForAll`):** 0 when every card is resolved; 4 as soon as one is returned, or when every card is answered and one isn't a go-ahead (deferred, withdrawn, superseded); 8 as soon as one is held back; 7 when the run's slice is over; and when the time runs out or the reviewer is away, 6 if a card still open is hard, 4 if an answered one isn't a go-ahead, else 5. With `--until-answered` only 0, 4 and 8 (and 130, or 1 for an error) can come.

## src/modes.ts: `baesian init` in either mode (B-4rwyz)

The user decided B-4rwyz, "A personal mode: nothing committed", for someone who uses Baesian in a repo they share with collaborators who don't.
- **`setUpShared()`** is `init` as it always was: the live layer, the record's config, a vault, Baesian's block in the repo's hooks (`installHooks`) and the AGENTS.md block.
- **`setUpPersonal()`** (`init --personal`): the live layer with the clone's own config in it (`Store.init`, [[src-store#Personal mode (B-4rwyz)]]); `/.baesian/` in the clone's `info/exclude` (`excludeRecord()`, in `src/personal.ts`), so a stray record is never committed; and the clone's own hooks (`installPersonalHooks()`, [[src-gate#Personal mode (B-4rwyz)]]). AGENTS.md is left alone. It refuses a vault, whose notes are committed files, and a repo that is shared already (`sharedAlready()`): a record's config committed on any branch (`recordCommit()`), or an uncommitted `.baesian/` that a shared `init` wrote. The hooks are named in a config file of Baesian's that the clone's `.git/config` includes last, so a team's setup script that sets `core.hooksPath` leaves the gate on. Run again, it refreshes the hooks, puts the gate back if the include was taken out or something read after it overrode it (saying what had turned it off), and moves a clone an older `init --personal` set up, with `core.hooksPath` itself naming its hooks, to the included file (`PersonalInstall`).
- **`initShared()`** (`init --shared`) in a personal clone switches it: the clone's config becomes the record's, first, since it holds the link; the clone's own hooks go, with the include of Baesian's setting in its `.git/config`, so `core.hooksPath` is the team's again (`uninstallPersonalHooks()`); `info/exclude` stops hiding `.baesian/` (`includeRecord()`); then shared mode's setup; then this branch's record from the live layer (`Store.syncRecord` with `cardsForBranch()`: the cards filed on it or attached to it, and those its merges brought, D181, through the branches merged into it in turn). Nothing is committed: it ends with the `git add … && git commit …` to run, with the link's ack when the clone is linked (B-w4g6c), and says Baesian's own block in the hooks isn't a gate fact (B-g6ywj). Cards filed on other branches stay in the live layer until `init --shared` runs on each. Elsewhere, `--shared` is shared mode's setup plus this branch's cards into its record, when they aren't there. A repo whose record is committed is shared, and never switches back.

## src/ops.ts

One function per agent command, shared by the CLI and the MCP server ([[src-mcp]]): `fileOp`, `reviseOp`, `replyOp`, `ruleOp`, `attachOp`, `withdrawOp`, `waitOp`, `inboxOp`, `showOp`, `listOp`, `topicsOp` and `templateOp`. Each returns an `Op`: the lines the CLI prints (`Line`s, [[#What it prints: src/style.ts (B-eyrt5)]]), and the data its `--json` prints, which the server returns as a tool's text, in plain text, and structured content. Errors are the store's classes ([[src-store#Errors]]); `duplicateLines` is what a possible duplicate prints. The filing operations call the notifier they're given (`Actor`), so the CLI and the server each report a failed notification their own way. `waitOp` marks an answer delivered, and adds `next` and `exit` (`NEXT`: use, read, proceed, park, again, go). `waitAllOp` does the same for a wait on several cards (B-xnae9), marking each answer it gives delivered; a run that ends with "again" gives none yet, so they all come when the wait ends and the agent doesn't start on half of them. `deckWaitIds` picks a deck's cards for `--deck`: still with the reviewer (open or rerouted), filed or attached to by this agent, on this branch (`Store.branchCards`). This agent's, not every card in the deck, since an agent wakes for the answers it acts on; and the branch's, since agents share names (every Claude Code session is `claude-code` unless named). `fileOp` and `reviseOp` print the gate's outcome as the card's `level:` field (`levelField`), and `showOp` prints it for any card, without saying whether a held card was drawn for audit: that changes nothing an agent does. `inboxOp` marks each item with whether it can still take a reply or a rule draft. `cardDetails` and `verdictLines` are how a card and a verdict read; `listOp` lays the cards out as rows (B-gff98).

## src/quote.ts

Text others wrote reaches agents quoted, with its author, on one line (D169): titles, a card's fields, options, a reviewer's choice and comment, a parent's title in a brief. Raw, a field holding a newline could pass for Baesian's own lines ("B-7f3kq resolved: …"). `q` makes a text a JSON string; `said` gives `<what> by <author>: "<text>"`; `byLine` names the author, `Gus Ellerm (a person)` or `claude-code on main (an agent)`, quoting a name that isn't plain, since agents name themselves; `answerLine` is a verdict on one line. Everything an agent reads goes through them: `describeOutcome`, `describeBrief`, the operations' lines, the gate's report (`describeReport`) and `verify`'s messages; on a terminal they stay quoted, so a title can't carry escape codes into it, and so the plugin's hooks, which print `inbox --quiet`. `show` (`cardDetails`) gives each of the card's fields a line of its own, with its author, `secret_reason` among them (B-jfkv9).

## src/wait.ts

**One card or several (B-xnae9).** `waitForAll` waits on a list of cards; `waitForVerdict` is `waitForAll` on one, with the outcome it always gave. A wait on several returns a `WaitAllOutcome`: each card's outcome in the order asked (a `CardOutcome`: resolved, answered, held, no verdict, or `StillOpen`), and why it ended: `answered` (every card), `returned` (one came back to the agent, before the rest), `held`, `again` or `no-verdict`. Cards already answered when it starts get no marker, and a fresh marker this agent left on one, from a run that ended with "again", is removed. Each card still open keeps its marker until it's answered. `describeAll` is what the agent reads: why it ended, then each card in `describeOutcome`'s words, and the cards still open with the command to wait on them again. A card that becomes held mid-wait now ends the wait as `held`, where before it went on waiting.

**With no time limit (`WaitOptions.untilAnswered`, `--until-answered`).** No slice, no budget and no presence check: it ends only when the cards are answered, or one comes back or is held back, so it never exits 5, 6 or 7, and records no fallback, since the agent isn't proceeding: it ended its turn. Its markers show for the budget (`timeoutMs`, from the first wait), as a wait the agent ran itself would, then are removed while it goes on listening (B-3az04, the user's answer): an agent that ended its turn an hour ago isn't one that has just stopped for the reviewer, and the relay gets no heartbeats from it after that.

`waitForVerdict` runs in short slices (D101), so a run fits inside any harness's command limit (Claude Code's default is 2 minutes). Each poll reads through a fresh `Store.view`, so a card's status reads every other card once, not once per question ([[2026-11-03 Scale Test]]). It polls the store every `POLL_MS` until one of four things happens:
- the card leaves `open` or `rerouted`. A `held` card returns at once, before any marker, as `held` (exit 8): the agent goes ahead with its pick, whatever level it asked for (B-chq61);
- the client's heartbeat is older than `PRESENCE_STALE_MS`, so the reviewer is away;
- the wait's budget, `DEFAULT_TIMEOUT_MS` (9 minutes), is spent. It counts from the card's first run;
- the run's slice, `SLICE_MS` (100 seconds), is over. The run then returns `again`, exit 7, and the agent runs `baesian wait` again.

While it waits, it keeps a waiting marker (`Store.startWaiting`), refreshed every `WAITING_BEAT_MS` (D90), calling `WaitOptions.onBeat` at each beat (the MCP server reports progress then), and `WaitOptions.onMarker` whenever the marker is written, refreshed or removed: in a linked repo it goes to the relay as a heartbeat (`waitWithRelay()`, [[src-sync]]). `WaitOptions.signal` stops a wait: it throws `WaitCancelled`, removes the marker, and records no fallback; the CLI aborts it on Ctrl-C, the MCP server when a call is cancelled or its input closes. A run that ends with `again` keeps its marker, and the next run picks it up, which is how the budget knows when the wait began. Any other ending removes it. With no verdict, a blocking card gets a fallback recorded (`Store.recordFallback`), and a hard card never proceeds; both by the level in force (`Store.levelOf`), which in a hosted repo the relay's signed gate record can raise. `exitCodeFor` and `describeOutcome` turn the result into the exit code and the text the agent reads, with what the reviewer wrote quoted and named (D169), including the card's briefs (`describeBrief`): what a parent's verdict did to it, how its answer changed, or that a held card its agent went ahead on has been overturned since (D151), and the commits to rework, with those a rebase or a squash has since taken off every branch listed apart (D80, D81, B-9v5xj). `baesian inbox` and `baesian show` print the same briefs, and `show` says who is waiting or stopped waiting. A wait that ends with an answer marks what it printed as delivered (`Store.markDelivered`), so `inbox` and the plugin's hooks don't hand it over again. A resolved card whose answer retired a rule tells the agent not to cite the rule again (D119). The clock and the sleep can be injected, so the tests run without real time passing.

## src/notify.ts

`notifyFiled` sends notifications only for blocking and hard cards (`shouldNotify`):
- an OS notification (`osascript` on macOS, `notify-send` on Linux), with the text passed as arguments rather than built into a script;
- the user's `notify` command, with the card as JSON on stdin.

Both are fire-and-forget: a failed notification never fails the filing. Settings come from `userConfig`, never from the repo. `BAESIAN_OS_NOTIFY=0` turns OS notifications off.

## src/agents.ts

`writeAgentsBlock` keeps `AGENTS_BLOCK` between `BEGIN` and `END` in `AGENTS.md`, and leaves everything else in the file alone. With a vault, `agentsBlock` adds one sentence pointing agents to the vault's routing notes and its rules in force, to read as guidance when deciding whether to file (D173); the gate never reads them. `claudeMdMissesAgents` warns when `CLAUDE.md` doesn't import `AGENTS.md`. `CARD_TEMPLATE` is the draft that `baesian template` prints: the required fields of [[File Formats#Card revision]] to fill in, and the optional ones commented out. Its `touches` list includes `infra`. It's made from `CARD_FIELDS`, a table of each field's note, which also describes the MCP filing tools' fields (D167), so the two can't drift. `secret_reason`, the reason for filing a card that looks like it holds a secret in a hosted repo (B-jfkv9), is in the tools' fields, not the template: `baesian file --secret-reason` sets it. `agentName` names whoever runs a command (D102): `--agent`, then `$BAESIAN_AGENT`, then the name an MCP client gave (`clientAgentName`, which makes Claude Code's and Codex's `claude-code` and `codex`), then the harness's own name (`harnessName`, from variables such as Claude Code's `AI_AGENT`, or Codex's `CODEX_THREAD_ID`), then `agent`. `AGENTS_BLOCK` covers:
- when to file a card, and that every card states its strongest alternative and its crux;
- that a topic names one question, so a follow-on gets its own, narrower topic (D112);
- that the reviewer chooses before seeing the agent's pick, case or body, so what they need in order to choose goes in `crux_fact`, kept neutral (provisional, on the finding 2 card);
- that the decision record is committed with the code, so secrets, credentials and private output stay out of cards (B-vqn69). The plugin's skill says the same, and `baesian file` warns on text that looks like a secret ([[src-store]]);
- the commit gate: card or ack trailers, and `baesian check`;
- `wait`'s exit codes, with the one reply to an answer against the agent's pick (D104);
- leaving `baesian wait <ids> --until-answered` (or `--deck`) running in the background when a turn ends with cards still open whose answers the agent will act on, in a harness that wakes it when a background command finishes (Claude Code), and acting on what it printed when it ends (B-xnae9);
- drafting a rule when an answer asks for one, with `baesian rule` (D110);
- naming a long-lived agent with `$BAESIAN_AGENT` (D102);
- what to do when `baesian file` exits 3, including for a follow-on (D112);
- that a level is a minimum only when a card is shown, and a held card means go ahead with the pick, as provisional, settled at merge (D150, B-chq61); `wait` exits 8 for one;
- that only a person resolves a card, or sets the repo's preferences: agents never write preference files (D147).

The template says the same as the block: reuse a topic only for the same question, and `crux_fact` is the only context the reviewer sees first.

**In personal mode** (B-4rwyz) AGENTS.md isn't touched, so the plugin carries the instructions: `personalInstructions()` is `AGENTS_BLOCK`'s, after a paragraph on what personal mode changes for the agent (the gate takes its trailers out of the message, into the clone's ledger; card IDs and Baesian stay out of what the collaborators see), with the sentence on the record being committed replaced, since it isn't. `baesian inbox --quiet`, which the plugin's session-start hook runs, prints it at a session's first read; the MCP server adds a line to its instructions too ([[src-mcp]]).
