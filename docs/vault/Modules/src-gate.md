# The commit gate

The livedocs pattern applied to decisions ([[Baesian Design#The git gate]]). The gate reports facts it can check mechanically. The agent that made the commit covers each one with a card or an ack, because it has the context.

## src/facts.ts: detectors (D25, D55)

`detectFacts` takes a `Snapshot` (two trees, and the paths that differ) and returns `DetectedFact`s plus warnings.
- `stagedSnapshot` compares the index with HEAD, or with `EMPTY_TREE` before the first commit.
- `commitSnapshot` compares a commit with its first parent, for CI.

| Kind | Finds | Built in |
|---|---|---|
| `dep` | runtime dependencies added to or removed from `package.json`, `pyproject.toml` (PEP 621 and Poetry), `requirements*.txt`. Not dev dependencies, version bumps or lockfiles | Python names normalised (`normalisePython`) |
| `schema` | paths matching the schema list: `DEFAULT_SCHEMA`, or the preferences' `gate_schema` | migrations, `*.sql`, Prisma, JSON Schema, GraphQL, and a `schema.ts` module (Drizzle's and Convex's, and Zod schemas of files on disk, like Baesian's own `src/schema.ts`) |
| `infra` | paths matching the infra list: `DEFAULT_INFRA`, or the preferences' `gate_infra` | workflows, Dockerfiles, compose, Terraform, wrangler, fly, vercel, netlify, and committed git hooks (`.githooks/`, `.husky/`), which run on everyone's machine (D135), except a change that only adds, updates or swaps Baesian's own block, exactly as this release's or any released one's `baesian init` wrote it (`onlyBaesianBlock()`, B-g6ywj, B-np6af) |

**`api:` facts (M3c; D56, D58, D59).** The detector is off unless the preferences' `gate_api` lists the project's public modules. When it's on, `Snapshot.apiChanges` asks livedocs: `livedocsSignatures` runs `livedocs signatures --cached`, or `--rev <commit>` for CI, with `--json`.
- Only breaking changes count (`BREAKING`: a changed signature, or a removed export), and only in the listed modules. A new export is additive.
- Each one becomes `api:<qualname>`.
- If livedocs is missing or fails, that's a warning, never a block.

What counts as a signature is livedocs' rule: parameters, defaults, return types and class heritage. For constants, only a declared type annotation counts. Zod schema constants therefore aren't API facts: in this repo, format changes are caught by the schema detector, whose built-in list counts `src/schema.ts` (`**/schema.ts`; until B-qkek1, the config's `gate_schema` listed it).

**The repo's link to the service (B-w4g6c, M9d).** A commit that changes the service, project or first commit in `.baesian/config.json` (`CONFIG_PATH`) is a fact, `infra:.baesian/config.json`, linking a repo first included, and unlinking it: changing where a repo's cards are sent takes the same sign-off as changing its CI. `linkFact()` (private) compares those three fields between the two versions, and runs before anything is ignored, so neither `DEFAULT_IGNORE`'s `.baesian/**` nor a repo's own ignores hide it; the rest of the config and of `.baesian/` stays out of sight. The first commit is among them because it's what ties a checkout to its project (B-5gnea): changing it alone would let a copy sync with the original's. `baesian login` prints the ack that covers the fact when it links a repo (`linkAck()`, [[src-sync]]). CI's `baesian verify` reports it the same way, since it detects with `detectFacts()` too. For a while (B-qkek1's stopgap, 2026-11-05) a change to the config's `gate_*` keys was a fact as well; the gate no longer reads them, so it isn't.

`DEFAULT_IGNORE` (`node_modules`, `.baesian/`, vendor, fixtures) is never looked at, whatever a repo sets. A rename counts when either the old or the new path is in scope. A manifest that doesn't parse produces a warning, not a guess. Globs come from `globToRegExp`.

## src/gate-paths.ts: what the gate looks at, and who changes it (B-qkek1)

The built-in lists (`DEFAULT_SCHEMA`, `DEFAULT_INFRA`, `DEFAULT_IGNORE`) and a repo's own, which live in its preference files ([[File Formats#Routing]]), never in the committed config: an agent edits the config, and on 2026-11-05 a commit that set the config's `gate_ignore` to `["**"]` and added a dependency passed `baesian verify` with no card or ack. The user decided B-qkek1: the settings move to the preferences, which only the client writes, and a change that makes the gate see less takes the passkey in a hosted repo, as loosening a row does (D163). The module is pure, with no Node, so the CLI, CI, the relay and the client share it; `facts.ts` re-exports the built-in lists.

- **`GatePaths`** is a preference file's four lists, `schema`, `infra`, `api` and `ignore`, each left out meaning the built-in one; `Settings.paths` carries it ([[src-routing]]), and `detectFacts()` takes it as its options (`DetectOptions`). `pathsOf()` gives the list the gate applies for a kind; a repo's ignores are added to `DEFAULT_IGNORE`.
- **`pathSetting()`** is a list as a file keeps it: trimmed, without blanks or repeats, and left out when it's the built-in one, in any order. An empty schema or infra list is kept: the gate looks for none.
- **`pathsLoosening()`** says what a change makes the gate stop seeing: a schema, infra or API list that no longer covers every path the old one did, and paths ignored that weren't. `loosening()` includes it, so the store's judgement of a preference file and the relay's passkey prompt both take it in.

**Comparing globs (`uncovered()`, in `src/globs.ts`).** Exact, not a guess from the text: each glob is read as an automaton over a path's characters, as `globToRegExp()` reads it, and walking them all together over the characters that matter (the slash, those the globs name, and one standing for every other) finds a path the first list misses, if there is one. So `**/schema.ts` covers `src/schema.ts`, `**` covers anything, and `deploy/*` with `deploy/*/**` covers `deploy/**` together, though neither does alone. It gives up after 50,000 states, and a glob it can't tell about counts as not covered: as loosening.

## src/trailers.ts (D52)

`parseTrailers` runs `git interpret-trailers --parse` on the message after `cleanMessage`, which drops comment lines and the `--verbose` scissors section. It returns the cards, the acks (fact ID → reason), and any malformed Baesian trailers, which block the commit rather than being ignored.

`readHistory` searches the history of every branch, local and remote-tracking, for `Baesian-Card` trailers (B-9v5xj), so a changed answer's brief finds a card's commits after a rebase, or a squash that keeps the trailer, rewrote them ([[src-store]]). One `git log` reads each commit that mentions the trailer, with git's own trailer rules, as `parseTrailers` does: only the message's last paragraph counts, so a squash message that lists each commit's message, trailers and all, isn't read as citing anything. It returns a `History`: the `CitingCommit`s for each card, oldest first, and `History.onBranch`, which says whether a commit is on a branch at all (false once it's rewritten, or if it never existed). It's cached per process for as long as the branches point where they did.

## src/gate.ts

`evaluate` covers each fact in this order:
1. an ack for its ID;
2. a cited card whose `touches` map to its kind (`KIND_OF_TOUCH`, D53);
3. a rule whose `covers` matches it, unless the rule is retired (D119).

Separately, it checks every cited card, by the level in force (`Store.levelOf`): the one the gate at filing wrote on the card ([[src-routing]]), raised in a hosted repo by the relay's signed gate record; all of it in one `Store.view`. In a hosted repo a card's status reads only the answers the service signed (D138, [[src-store#The hosted service's proof (M9a)]]), so a hard card answered only on the machine is still unresolved. A cited card that's:
- unknown, withdrawn or superseded: blocked;
- rejected: blocked, with a rework brief listing the commits in its ledger (D30);
- hard and not resolved: blocked (D46);
- returned with a question, filed as provisional or blocking, or held back by the gate (written provisional): allowed.

`describeReport` prints the result (B-eyrt5): a headline, `commit blocked: …` at commit time or `this commit would be blocked: …` from `baesian check`, saying why (`blockedBecause`); the uncovered decisions as rows; and the trailers to paste, each a line of its own at the start of the line, never styled or prefixed (`blockedBody`, which `verify` prints under each failing commit too). A passing commit lists what covers each decision. The hooks print every other line after `baesian: `, so git's own lines can be told apart ([[src-cli#What it prints: src/style.ts (B-eyrt5)]]). What a reviewer wrote, in a rejection or a new verdict, is quoted with their name (`answerLine`, D169). `verdictsSinceLastCommit` adds the verdicts since the branch's last commit. Commit times have one-second resolution, so a verdict given in the same second as the last commit can be shown twice; that's harmless.

**Where it looks (B-qkek1).** `detectStaged` reads the paths from the preferences in force (`Store.inForce`), as the gate at filing reads its rows: on your machine, the newest preference file in the live layer; in CI, the newest in the commit's own record; in a hosted repo, only one that counts, signed and, when it loosens, with the passkey's proof ([[src-store#The hosted service's proof (M9a)]]). With none, the built-in lists. A newest file that can't be read is a warning, and the built-in lists apply. A config that still has the old keys is a warning too (`staleGateKeys()`, `configWarnings()`): they're ignored, and it says to set them in the client's preferences panel, under "What the gate looks for", then delete them. `baesian check` and the commit gate print it every time; `baesian verify` says it once, for HEAD.

**In the client,** `<GatePathsSection />` is that section of the preferences panel, after the rows: the built-in detectors nobody changes (dependencies, and the repo's link), then the four lists, one glob a line, each with "Use the built-in list" when it isn't. Before you use a draft it says what the gate would stop seeing, and it sends the four lists through the same path as every preference change, over the file in force; on the website one that loosens asks for the passkey first ([[Client Build]]).

## src/hooks.ts (D54)

`installHooks` finds the hooks directory git uses (`git rev-parse --git-path hooks`):
- with no `core.hooksPath` and no real hooks in `.git/hooks`, it creates a versioned `.githooks/` and points git at it;
- otherwise it installs in place.

`HOOKS` are six: `pre-commit`, `commit-msg`, `post-commit`, since D181 `post-merge` and `post-rewrite`, which find merges, and since B-h7rsv `pre-push`, which records a branch pushed to the remote's default branch. `baesian init` adds any missing to a repo's hooks folder, inserting its block into a hook the repo has of its own, and `pre-commit` says to run it while any lacks the block (`missingHooks()`): that's how a repo set up before `pre-push` gets it, `baesian init` once, and in shared mode a commit of the new `.githooks/pre-push` (Baesian's block alone, which the gate doesn't count as a decision, B-g6ywj), after which every clone has it. `post-merge` and `post-rewrite` get their `$1` (the squash flag; what rewrote), `pre-push` its `$1`, the remote's name; `post-rewrite`'s standard input, the commits it rewrote, is left for the repo's own lines after the block (`</dev/null`). `pre-push`'s standard input, the refs being pushed, is Baesian's and the repo's both (Git LFS's pre-push reads it): the block copies it to a temporary file, which Baesian reads and which becomes the script's standard input again, whole, for the lines after the block. The three after the fact can't stop anything, and `pre-push` mustn't: with Baesian missing they skip quietly, and whatever `pre-push`'s Baesian does, failing included, the push goes on (`|| :`, not `|| exit $?`).

`writeHook` puts `hookBlock()` right after the shebang, so it runs before livedocs' `exec`. The block's text, its markers and `HOOKS` live in `src/hookblock.ts`, apart from the installer, so the fact detector can read them without importing it: `onlyBaesianBlock()` says whether a hook change only adds, updates or swaps Baesian's block, with nothing else in the file changed: the block must be one a Baesian wrote for that hook (`isBaesianBlock()`), this version's `hookBlock()` or any released one's, whose SHA-256 digests `RELEASED_BLOCKS` lists by hook (B-np6af), since teammates and CI are often a release apart. Such a change isn't an infra fact (B-g6ywj), so a repo's first commit after `baesian init` passes the gate, whichever release ran it; any other change to a hook, deleting one or taking the block out is a fact, as D135 has it. A release lists the blocks of the releases before it, never those after: a block only a newer release wrote counts as a change to the hook, and needs a card or an ack, until the release that judges it lists it. A release that changes a block adds the one it replaces to the list; a test runs each release tag's own `hookBlock()` and fails while any of its blocks is missing. A block found flawed is taken out, and counts as a change again. A hook that holds another tool's lines too, such as livedocs' pre-commit, is a fact when it's first committed, since those lines aren't Baesian's.

The block is identical on every machine, because `.githooks/` is committed. It calls `baesian` from PATH. If `baesian` isn't there, it runs the command stored in the clone's own git config under `FALLBACK_KEY` (`baesian.fallback`), which `setFallback` writes at init time (D48). That config is local: shared by the clone's worktrees, never committed. If neither exists, the hook refuses to commit, except in `post-commit`, which can't stop a commit anyway.

The first version embedded the fallback's absolute paths in the hook itself. That would have put one machine's paths in the repo, and made every other machine's `init` rewrite the committed hooks.

`runHook` runs each hook, and returns the exit code git sees (a promise, since `pre-commit` may reach the relay):
- **`pre-commit`**, in a linked repo, first pulls the relay's log (M9d, `syncRelay()`, [[src-sync]]), for at most `PRE_COMMIT_PULL_MS` (three seconds), so answers given since come into the record with the commit; offline, or slow, it says so on standard error and commits what's here, never failing. Then it syncs the record and stages all of `.baesian/` (D37). With a vault configured, it then writes the vault's notes from that record (`writeNotes`, [[src-vault]]; D170) and stages them: the notes written now, those `baesian sync` wrote and nobody added, and those whose only unstaged change is Baesian's own (bringing the index's version up to date gives the same note). A note with someone's unstaged edit is left as it is, with a message: staging it would commit their unfinished edit. A missing vault is a warning, never a block. It notes which record files and notes nobody had staged before it, in this worktree's own git directory (`baesian-staged.json`).
- **`commit-msg`** runs the gate. It skips merge commits, which CI checks. When it blocks a commit, it unstages the record files and notes `pre-commit` staged, back to the last commit's version, and leaves any you staged yourself (D122). The next commit stages them again. A commit blocked by another hook still leaves them staged: livedocs' `pre-commit` runs after Baesian's part, and blocking there means `commit-msg` never runs.
- **`post-commit`** writes a ledger entry for each `Baesian-Card:` in the commit (D15): one line naming the commit (D120), `ledgerBody()`, never its subject. While a rebase runs, HEAD is detached, and the entry names the branch being rebased (`rebasing()`), whose commit it is (D181). Then it looks for a merge (D181): a squash's commit, with the marker `post-merge` left, or a merge whose conflicts were resolved and committed, which `post-merge` never sees; where the record is committed, any commit, since one may bring another branch's cards.
- **`post-merge`** (D181), after a merge or a fast-forward, `git pull` included: with the squash flag, `git merge --squash` moved nothing yet, so it notes what `SQUASH_MSG` says was squashed (`noteSquash()`), for the commit that follows; otherwise it finds the merges from where the branch was (`ORIG_HEAD`) to HEAD, writes each (`Store.writeMerge`), says so on standard error, and, if it found any, sends them to the relay in a linked repo, for as long as `pre-commit` pulls (`PRE_COMMIT_PULL_MS`); offline, they go at the next sync.
- **`post-rewrite`** (D181), after a rebase (`git pull --rebase` included), the same from `ORIG_HEAD`; after an amend, nothing.
- **`pre-push`** (B-h7rsv, "Record it at the push"): a push that moves the remote's default branch to a branch's tip, as `git push origin v1/next:main` does, records that branch merged into the default branch, at the push, as a fast-forward of the default branch here is recorded: `findMerges()` from the remote's old tip to the pushed one, `moved` (the ledger read for the commits it brings, no patch-ID matching), keeping the pushed branch's merge, and saying so on standard error ("recorded v1/next merged into main, as it's pushed to origin, with …"). The refs come on its standard input (`pushedRefs()`). The remote's default branch is its HEAD as the last fetch saw it (`refs/remotes/<remote>/HEAD`), else the repo's (`Store.defaultBranch`). The branch is the local ref pushed, the checked-out branch for `HEAD:main`, or the one local branch at the pushed object. Only a fast-forward of the remote's branch from a tip this clone has: a forced push isn't a merge, and one the remote would refuse isn't recorded; a ref created or deleted, a push to another branch, or the default branch pushed itself records nothing (its own movement here was recorded when it moved). The push lands after the hook, and could still be refused by the remote (a protected branch); then the merge is recorded though the push failed. Nothing goes to the relay at the push, so a push never waits on it: the merge goes up at the next sync (a filing, `inbox` from a harness's hook, `baesian sync`). It never fails, and says nothing when it can't look. When main is later brought up to the pushed branch here, `post-merge` finds the same merge, in the same file (`mergeFile()`), and writes nothing.

A repo where the live layer doesn't exist is never blocked.

### Personal mode (B-4rwyz)

In a clone that uses Baesian for one person, in a repo whose collaborators don't (`Store.personal`, [[src-store#Personal mode (B-4rwyz)]]), nothing in the repo's hook files changes:
- **The clone's own hooks.** `installPersonalHooks()` writes a folder of hooks in the live layer (`personalHooksDir()`, `PERSONAL_HOOKS`: `.git/baesian/hooks/`). Git finds it through a config file of Baesian's own beside it (`personalGitConfig()`, `PERSONAL_GIT_CONFIG`: `.git/baesian/git.config`), which sets `core.hooksPath` to the folder, absolute, since `.git` is a file in a linked worktree; the clone's `.git/config` includes that file at its end (`PERSONAL_INCLUDE`, `[include] path = baesian/git.config`, relative to `.git/config`'s folder), and every worktree of the clone reads it.
- **Why an include, at the end:** a team's setup script (`make setup`, run after cloning, in each new worktree, after a lock change) runs `git config core.hooksPath .githooks`. Setting `core.hooksPath` in `.git/config` itself, as personal mode first did, let that line replace Baesian's and turn the gate off silently, for every worktree at once. Git reads an include where it appears, and the last value of a key wins; `git config` edits the `[core]` section above the include, and even `--unset-all` followed by a set leaves Baesian's value in force (checked with git 2.56). So the clone's own `core.hooksPath`, in `.git/config`, stays the team's to set, and names the hooks that run after Baesian's. Written once, at the end (`includeLast()`, appending under git's own lock, `config.lock`): moved to the end again only when something that could set `core.hooksPath` (that key, or another include) has come after it.
- **How hooks chain.** Each hook (`personalHook()`) runs Baesian's block, for the hooks in `HOOKS`, then the repo's own hook of that name, with the same arguments and standard input, exiting as it does (`exec`), and only if git would have run it (a file, executable). The repo's folder is found each time a hook runs, not when it's installed: the last `core.hooksPath` git reads, at any level and through any include, other than Baesian's own value; git's own `hooks/` when there's none (`repoHooks()` does the same in Node). That's the team's setting in `.git/config` now, wherever `make setup` last pointed it, or a person's global `core.hooksPath` where the clone sets none, as git would have used without Baesian; relative, it's found from the worktree's root, as git finds it. **No loop:** a hook with the first line of one of the clone's own (`PERSONAL_MARK`) is never run from one, so a `core.hooksPath` naming Baesian's folder (absolute, relative or through a link), or a copy of one of its hooks in the team's folder, ends the chain. `post-rewrite` and `pre-push` read their input first and hand Baesian a copy, then the repo's hook. Besides Baesian's six, the hooks a working clone runs are passed on whether or not the repo has them yet (a hook the team adds later still runs), and any other the repo's folder has when it's installed (`reference-transaction`, say).
- **`hookBlock()` for personal mode** (`PersonalBlock`) differs in two ways: a missing Baesian says how to stop using it in this clone (`PERSONAL_STOP`, which takes the include out of `.git/config`), not to commit with `--no-verify`; and `post-rewrite` and `pre-push` pipe the input in, where the shared block leaves `post-rewrite`'s alone and copies `pre-push`'s through a temporary file. A personal clone set up before `pre-push` had one already, passing the push on to the repo's, without Baesian's block: `missingHooks()` lists it, so `pre-commit` says to run `baesian init`, which writes it again.
- **What's noticed.** `personalProblems()`: the gate is off (git doesn't run the clone's hooks), saying why: `.git/config` no longer includes Baesian's setting, Baesian's file is missing or names another folder (the clone moved), or something git reads after the include sets `core.hooksPath` (another include, a worktree's own `config.worktree`, `git -c`), named by where it's set; `.git/config`'s own `core.hooksPath` names Baesian's folder, so the repo's hooks don't run; a hook the repo's folder has that the clone's don't pass on; and a stray `.baesian/`. Every command but the hooks', the MCP server's and `init` says so ([[src-cli]]), as does `pre-commit` when it runs. Running `baesian init --personal` again puts it right, except a setting read after the include from outside `.git/config`, which it names (`PersonalInstall.stillOff`).
- **A clone an older `init --personal` set up** (`core.hooksPath` in `.git/config` naming the clone's hooks, the team's folder kept under `baesian.repohooks`) is told to run `baesian init --personal`, which converts it (`restoreRepoSetting()`): the team's value back in `[core]`, or unset where there was none, `baesian.repohooks` unset, and the include added. A `core.hooksPath` in `.git/config` naming Baesian's folder some other way is taken out the same way. `baesian.repohooks` isn't kept: the hooks read the team's folder as they run.
- **`uninstallPersonalHooks()`** takes it all out when the clone switches to shared mode: the include, Baesian's file and the folder (an older clone's setting put back first). The clone's own `core.hooksPath` was never changed, so git runs the repo's hooks again.
- **`pre-commit`** pulls as in shared mode, and stages nothing: there's no record and no vault's notes.
- **`commit-msg`** runs the gate as in shared mode. Once it lets the commit through, it takes the `Baesian-Card` and `Baesian-Ack` trailers out of the message (`withoutBaesianTrailers()`, in `src/personal.ts`: only from the trailer block git reads, with their continuation lines), so the shared history never shows them, and notes the cards cited with the tree being committed (`noteCited()`, `baesian-cited.json` beside the index). Acks are checked here, and kept nowhere after. A merge's message loses them too. `git commit --no-verify` skips the gate and keeps whatever trailers the message has.
- **`post-commit`** writes the ledger for the cards noted, when the commit's tree is the one noted (`takeCited()`), as well as for any trailers left in the message; `post-merge` does the same for a merge commit.
- **`post-rewrite`**, after an amend or a rebase, carries the ledger over: each entry for a rewritten commit gets one for the commit it became, on the same branch, as the trailers would have carried it in the message (B-9v5xj). Then it looks for merges, as above.

So in personal mode the ledger is what says which commits build on which cards; merges are found from it (`LEDGER`, below).

## src/merges.ts: finding merges (D181)

The user decided D181 in conversation: the website shows a project's decisions by branch, with merges and the commits that cite cards. A merge is found by the hooks of the machine that saw a branch A move, and recorded as a `MergeEvent` ([[File Formats#The others]]). **`findMerges()`** takes a movement (`Moved`: A, from, to, the squash marker's commits, `deep`) and returns what it merged, through one of two detectors behind one interface, **`MergeDetector`**, chosen by **`detectorFor()`**: the committed record where the commit's tree holds it (`recordCommitted()`), else the ledger.

- **A's line.** The commits on A's first-parent line from where it was to where it is, oldest first; where a pull merged A's own upstream (`refs/remotes/*/A`) into a branch that had moved on, the upstream's line comes first (private `withUpstream()`), so a merge made there is found at its own commit, and a card arrives once.
- **`RECORD`** (shared mode, today's): each commit's files added against its first parent, in one `git log --diff-merges=first-parent` over the line: a card's first revision (`.baesian/cards/<id>/r1.md`) or a deck. Who filed each is read from the commit's own blobs (`git cat-file --batch`), so a card this machine never had counts. A card whose `source_branch` is B, not A, came from B; one this branch attached to (`baesian attach` copies a card into the record) didn't, nor its deck. It sees merge commits, squashes, fast-forwards and rebases alike. **Since B-w41p7 it reads the ledger too**, but for a plain commit: the commits citing cards, made on B, that the movement made reachable (as `LEDGER` finds them, their cards left to the record), so a movement that brings B's commits citing cards and no card, as a later fast-forward of a branch merged before does, is a merge of B. Where B's cards came at a commit none of B's commits came with (a squash or rebase made elsewhere), B's ledger commits are matched by patch ID at that commit only, for the tip that landed.
- **`LEDGER`** (personal mode, B-4rwyz, where the record isn't committed: built for it before personal mode was, and used whenever a commit's tree has no record, so personal mode has nothing to switch on; tested end to end there, with the hooks as git runs them): the commits each commit on A's line made reachable (itself, or for a merge, everything it brought), and the ledger's entries for them made on another branch; a squash's commit brings the commits its marker names. **Squashes and rebases made elsewhere** (GitHub's) make commits the ledger never saw: with `deep` (a merge, a pull or a rebase; never a plain commit, so a commit stays quick), each new commit that matches nothing is matched by patch ID (`git patch-id --stable`) against each ledger commit of another branch not reachable from where A was (a rebase or cherry-pick of it, "rebase and merge", a one-commit squash), and then against each such branch's whole change, from its merge base with A to its newest such commit (a squash). Capped at 50 of A's commits, 10 branches and 200 ledger commits.
- **The ledger it reads** (private `ledgerByCommit()`): the live layer's entries, and where the record is committed, the record's at the commit A moved to, for another machine's entries that haven't come down from the relay yet.
- **Which branch came in** (private `cameIn()`): the branches, local or remote-tracking, whose tips the movement made reachable and no other such tip contains; and a branch one of those began from, whose tip is on that one's first-parent line with no merge recorded of it into that one (the bug sweep's D8: feat2 made from feat1 and merged into main brings all of feat1, which merged with it; a branch fast-forwarded into the one merged, and recorded so, merged into that one, not A). A's own upstream among the names is a pull: with a branch that brought something at the tip beside it, it's that branch's merge (D1: v1/next pushed to the remote's main, then main brought up to it, is one merge of v1/next, not one per run of its commits); with none, it's read merge by merge. - **What it brought, by ancestry (B-w41p7).** Each merge found is checked against git before it's returned (private `landed()`): a commit is part of it if it's reachable from the tip that landed and wasn't reachable from A before it (`git rev-list <tip> --not <base>`, the base A's commit before it: where the movement started, a merge commit's first parent, or the parent of a run's first commit). ### The history scan (B-dezkk)

The user decided B-dezkk, "The history scan finds them": merges git's history shows that no hook saw (made before a repo had Baesian's merge hooks, or where it isn't installed) are recorded once, read as a pull reads them, so a branch merged before the hooks isn't drawn loose. **`scanHistory()`** finds them, and with `write` records each; `baesian login` runs it when it links a repo, before the first sync, and `baesian sync --history` runs it any time ([[src-cli]]).
- **Each branch's own line** is read by `findMerges()` with `after` (`Moved.after`): no branch is named by its ref (`cameIn()` isn't asked, so the line is read merge commit by merge commit and run by run, as the pull path does), and a run of another branch's commits ends before A's own next commit, the ledger says, rather than at the next arrival. A branch's own line is its first-parent line from where it left the lines read before it: the default branch's first (`Store.defaultBranch`), from its first commit, then each other branch, local or, where there's no local one of the name, remote-tracking, by how much history it holds, so a branch fast-forwarded into another adds nothing of its own, and v1/next's line, which starts with main's history, isn't read as main's cards merging into v1/next (what this repo's one-off scan had to filter by hand).
- **The line a merge commit brought** is read in turn, as the merged branch's, so a branch merged into another before both reached the default branch is found merged into that other, at its own merge commit: its owner is a branch whose ref is on that line (A's own upstream, pulled, is A's), else the branch the merge's subject names (`Merge branch 'x'`, a remote-tracking branch, a pull request's; read here, never kept or sent), else the one branch it brought. The owner's merge is kept at that commit, and the others it brought are found on the owner's line, merged into it, where they came; with no owner to tell by, the merge commit stays as the pull path reads it.
- **From no further back** than the first card or ledger entry in the live layer, a day early: nothing older brought a card.
- **Recorded once.** A merge it finds isn't recorded where one of the same branch is at the same commit, or where a merge of that branch already lists any of the cards or commits it lists: the same merge read another way (a hook's fast-forward at its tip, or an older reading of the same run, as this repo's records from before the sweep are). So run again it finds nothing new; and a branch merged twice into different branches with the same commits keeps only the first.
- **In this repo** (a copy of it, on 2026-11-05): of 28 merges the scan finds, 27 were recorded already, and one is new, worktree-agent-aaba362's two commits (339af8f, 0d27b82) merged into overnight/2026-11-03 at 377ec9c, which the branches panel drew loose. From a live layer with no merges at all, it finds those 28 and nothing else: the overnight branch into main, aaba362 into overnight, and the builders' worktrees into v1/next, none of them artefacts.

**`noteSquash()`** and **`takeSquash()`**: the squash marker, `baesian-squash.json` beside the worktree's index, as `baesian-staged.json` is: HEAD and the commits `SQUASH_MSG` lists, taken by the next commit on that HEAD. **`rebasing()`**: the branch a rebase in progress rewrites.

## Why the record is staged in pre-commit

git ignores files staged by a `commit-msg` hook: they're left for the next commit (tested on git 2.55). So the record is staged in `pre-commit`, and the trailers are read in `commit-msg`. Staging only the files the hook had just copied missed the cards `baesian file` wrote at filing time, so the hook stages the whole record directory.
