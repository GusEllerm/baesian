# service/: the hosted service (M9b, M9c, M9e, M9f)

The design is [[Hosted Service]] sections 1 to 4 (P15) and [[Formats for v1]] sections 7 and 8 (P16), as the cards in deck `hosted` decided them: Workers and an object per project (B-rca1z, D140), the service in this repo with its own package (B-pjw5y), the store run over the relay's storage (B-0ag7h) to serve the state as `baesian serve` does (B-17wn9), every relay address under `/v1/projects/{project}/` (B-7z97x), hibernating WebSockets for live updates (B-bv49e), and tests in workerd (B-hx2fn). M9c added accounts and sign-in, as D153, D176 and the cards below decided them. Nothing is deployed: that's M9f. The formats, the account tables and how to run it locally are in [[File Formats#The relay (M9b)]] and [[File Formats#Accounts (M9c)]].

The package is `service/`, with `service/wrangler.jsonc` and its own `service/package.json`. Its runtime dependencies are `@simplewebauthn/server` (B-jp22m) and `oauth4webapi` (B-s76hg); `wrangler`, `@cloudflare/vitest-plugin` and `vitest` are for development. It imports the store, the schemas and the state from `src/` as they are, and resolves their own dependencies (zod, yaml) from the root's installed packages, so the root's `npm ci` comes first. `service/wrangler.jsonc#account_id` pins the Cloudflare account the service runs in (D177), so no wrangler command run here reaches another; locally, wrangler's auth profile `baesian` is bound to the repo, and local runs and the tests need no login. The accounts database, `baesian-accounts`, exists there, in eastern North America, with every migration applied (`service/wrangler.jsonc#d1_databases`). The service answers at `https://baesian.dev` and nowhere else (B-aa9pc): `service/wrangler.jsonc#routes` is a Custom Domain on the bare domain, `workers_dev` and `preview_urls` are off, Workers Logs are off (`service/wrangler.jsonc#observability`; Cloudflare turns them on for new Workers otherwise, and the privacy policy promises no request logs), and so is the zone's Web Analytics (RUM), in the dashboard (Web Analytics, baesian.dev, Manage site, Disable; turned off 2026-11-05): a free-plan zone has it on by default, and Cloudflare then injected its beacon into every page, which the site's CSP blocked but which the privacy policy doesn't allow for, `SERVICE_ORIGIN` and `SERVICE_RP_ID` name it, codes come from `sign-in@baesian.dev`, onboarded to Email Sending, and `TURNSTILE_SITE_KEY` is a managed widget for it. `GLOBUS_CLIENT_ID` is the app the user registered at app.globus.org, whose redirect is `https://baesian.dev/v1/globus/callback`. The four secrets, `SERVICE_SIGNING_KEY`, `VAPID_KEY`, `TURNSTILE_SECRET` and `GLOBUS_CLIENT_SECRET`, are set on the Worker itself, by the user, each piped from where it was made. **Deploying** (B-bk20v) is `.github/workflows/deploy.yml`: on a tag `v…` whose commit is on `main`, and whose name is `v` plus the version in `package.json`, `service/package.json` and the plugin's manifest, all three (B-3femd: the release commit sets them, `npm version <x.y.z> --no-git-tag-version`, which sets `src/version.ts` too (`scripts/set-version.mjs`), and the manifest by hand, so `baesian --version` names the release and the plugin's users get its update, D114), it runs CI's checks, builds the site, applies the accounts database's migrations, then `wrangler deploy`, with an account-owned API token in the repo's secret `CLOUDFLARE_API_TOKEN` (Editor on this Worker, D1 Edit, and Workers Routes Write on baesian.dev). Then, for a release from the workflow's `FIRST_NPM_RELEASE` on (1.0.0, B-h0vyy), a job of its own publishes the command line to npm (B-xr2fa) by trusted publishing, with provenance and no token: the only job with `id-token: write`, on Node 24 with no npm cache, from a fresh checkout and build ([[Release v1#Publishing the CLI to npm]]). Last, a job of its own makes the release's page on GitHub Releases (B-yj9wc) from the notes the release commit wrote in `docs/release-notes/<version>.md`, with `gh release create` and the repo's `GITHUB_TOKEN`, the only job with `contents: write`; the deploy job checks those notes exist before it migrates or deploys anything ([[Release v1#The docs]]). The service's tests (`service/vitest.config.ts`), the CLI's relay harness, the browser tests and `.dev.vars` (`service/scripts/dev-vars.mjs`) each give their own address and Turnstile's test keys; the service's tests also blank the deployed service's spare key (B-x47ek), so they have none but what a test sets. Wrangler's local server takes a route's host as its own and rewrites `Origin` to it, which `crossSite()` would refuse, so the harnesses set `inferOriginFromRoutes: false` and `npm run dev` passes `--local-upstream localhost:8787`.

## The Worker (service/src/index.ts)

**`handleRequest()`** takes every request, with the services it's given (`Services`: sign-in, the accounts database, the mailer, Turnstile and `fetch`), which `servicesFor()` makes from the environment; a test hands in its own mailer, to read the codes, and a stand-in for Globus. Addresses under `/v1/projects/{project}/` go to the project's object (below); `GET /v1/keys`, for anyone, gives the service's keys (`keysReply()`, below, B-x47ek); the rest of `/v1/` to accounts and sign-in, `signInRoute()` and `machinesRoute()`.

**The CLI's release (B-4p43b, [[Release v1]] step 4).** A machine names its Baesian's release on every request, in the header `baesian-version` (`RELEASE_HEADER`), and a request of a machine's to a project's address from one older than the relay serves is refused before anything else, with 426 (`TOO_OLD`), `{ error, minimum, release }`, the error naming the release to install (`tooOld()`, in `service/src/release.ts`). The oldest it serves is `minimumRelease()`: the oldest release that reads every format this one writes, never one before 1.0.0 (`FIRST_STABLE`), and never above its own, so a build before its version is set serves its own CLI. A request that names no release is from a Baesian before the header (0.1.x), refused once the minimum is 1.0.0; one whose header isn't a release number is refused too. A person's requests, from the website, which is always the service's own release, aren't checked.

**Each project's tables (B-866d2, [[Release v1]] step 3)** change by numbered migrations, run as the project's object wakes (`migrateObject()`, in `service/src/object-migrations.ts`): its meta table holds its schema version (key `schema`, `SCHEMA_KEY`), and `ProjectRelay` runs the migrations after it (`OBJECT_MIGRATIONS`), in order, in one `transactionSync`, then sets the version, before it serves anything; if one throws, nothing is kept. A migration may add, change or drop tables and columns, and is never edited once released: a later change is a new one. A project at a newer version than the code's (after a rollback) throws `NewerSchema`, so the object serves nothing rather than guess at its tables. Migration 1 is every table the relay had before migrations, each made if it isn't there, as releases 0.1.0 to 0.1.10 made them with `CREATE TABLE IF NOT EXISTS` and never changed one after the first deploy but by adding `retention_commits`; and the practice table, new with it. So a project stored on baesian.dev before, with no schema version, wakes into migration 1 with every row kept and gains what it lacked; a new one gets every table at once. Migration 2 (1.0.2) adds `built`, where the state is kept once built (B-evrec, below); a project 1.0.1 left at schema 1 gains it as it wakes, every row kept. Migration 3 is for several reviewers (P20, below): the tables `sent_to`, `presence_of` and `push_told`, and a column each on `push_sent` (`account`) and `push_arrivals` (`handed`); a project 1.0.2 left at schema 2 gains them as it wakes, every row kept, with nobody noted as sent a card that arrived before. No class makes its own tables any more: `SqlFileStorage`, `RetentionLedger`, `PushLedger`, `PracticeTable`, `BuiltTable`, `SentTo` and `MemberPresence` use the tables the migrations made.

**`ProjectRelay`** is the Durable Object class, on SQLite (`service/wrangler.jsonc#migrations`). It learns its project on first use and serves no other. Each method builds a `Relay` over its files and runs it; when the project's version moved, it tells every socket (`changedMessage()`), and `BUILD_AFTER_MS` (2 seconds) after the last such move it builds the state again and keeps it (`ProjectRelay.buildSoon`, private; B-evrec, below), so a burst of uploads is one build. Its signing key comes from the secret `SERVICE_SIGNING_KEY` (`ServiceSigner.fromEnv`); without one it serves what it holds and refuses every write, with 503. Each method runs `ProjectRelay.relay` first, which brings an erased project's tables back before anything reads them.

The object also keeps the project's practice answers (`PracticeTable`, in `service/src/practice-table.ts`, B-rehdw): one row per entry in a table of its own, never in its files or its log, so no machine is ever sent one, the state never has one, and writing one moves no version, announces nothing and counts nothing; they go with the project (`ProjectRelay.erase`). It keeps its notification state (`PushLedger`, below) and retention's (`RetentionLedger`, below), runs its alarm (`ProjectRelay.alarm`) to send notifications and, once a day, to remove the text retention says goes (`ProjectRelay.sweep`), with an alarm always set after a write, and counts what's done in it (`Usage`, below): a card revision uploaded (`Relay.filedUsage`), an answer, topic merge or preference change written (`Relay.answeredUsage`, `Relay.preferencesUsage`, against `Relay.settings` before it), a notification sent, and the day's first visit on each kind of screen, from the reviewer's heartbeat. The Worker counts a reply of 500 or more by its address's name alone (`routeOf()`).

## The storage (service/src/sql-storage.ts)

**`SqlFileStorage`** is the store's `Storage` over the object's SQLite, B-0ag7h's second kind of storage. Every move of the project's version also empties the table `built` (B-evrec, below), in the write's own transaction. Five tables, made by the object's migrations (above): `files`, one row per path with its bytes; `log`, the append-only log; `meta`, the project and its version; `pending`, answers waiting for the passkey and the batches asking for them; and `before_linking`, the answers a machine uploaded from before linking (B-3zjjx).
- **`SqlFileStorage.create`** is an INSERT, so a taken path throws `FileExists`. In the same transaction it signs the file if the service signs its kind, writing its `.sig` beside it, and adds the file's entry to the log. A `.sig` is never its own entry: it rides in its file's, as `sig`. Nobody else writes one.
- **`SqlFileStorage.replace`** is an INSERT OR REPLACE, and **`SqlFileStorage.remove`** a DELETE; neither is logged. **`SqlFileStorage.list`** is a range query, from `dir/` up to `dir0`, giving the distinct next segment. Paths go through `checkPath()`, as memory's do.
- **`SqlFileStorage.after`** reads the log: each entry joined with its file's bytes and its `.sig`, so retention can drop a body and keep the rest of the entry (D137). Each entry is checked by `readRelayEntry()` on the way out. **`SqlFileStorage.cardsInLog`** gives the log by card, for retention: each card's last entry, when its first and latest revisions arrived, its bytes in all and its paths; **`SqlFileStorage.dropCard`** deletes a card's files' bytes, their signatures and its waiting markers in one move of the version, never touching the log (M9f).
- **`SqlFileStorage.transaction`** runs a whole answer or upload in one `transactionSync`, so if anything throws, nothing it wrote is kept, log entries and version included. **`SqlFileStorage.asMachine`** names the uploading machine in the entries written (D162). **`SqlFileStorage.version`** moves with every write but the reviewer's heartbeat, as the local server ignores `presence.json`, and is kept in SQLite, so it never goes back after an eviction. **`SqlFileStorage.putPending`** keeps a composed answer, or a batch, until the time it's given, apart from the live layer, and drops what has expired. **`SqlFileStorage.asBeforeLinking`** writes an answer from before linking unsigned, and lists it in `before_linking`, which marks its entry (`before_linking: true`); **`SqlFileStorage.beforeLinking`** gives that list, and **`SqlFileStorage.answered`** whether anything in `verdicts/`, `rules/`, `topics/` or `preferences/` has the service's signature yet, that is, whether a person has answered on the website.

## One project's relay (service/src/relay.ts)

**`Relay.store`** is the project's store: `Store.over` the project's files, on the branch `RELAY_BRANCH` (`relay`), with the config `{ service, project }`, and pinned as CI pins them: the service's own key (`ServiceSigner.trust`) and each earlier one in the project's `trust/`, with the revocations there (`Relay.root`, private), and the passkey key files the relay itself put there, each checked against those keys. Only the relay writes `trust/` (a machine's upload of a trust file is refused), so after the service switches to its spare key (B-x47ek), what its old key signed still counts, as it does in CI, whose pin holds both. So it counts what a machine with the pin counts, passkey proofs included. Everything a person writes goes through it, as the local client's answers do.

**The state, kept as built (B-evrec, "Kept in the project's database").** Building the state reads, parses and checks every file of the project: on baesian.dev, 0.6 to 0.9 seconds for 222 cards, against 20 milliseconds to send its 896 KB ([[2026-11-11 Kept State and Live Inboxes]]). So **`Relay.state`** builds it once (`snapshot()`, through `Relay.built`, private) and keeps it in the project's own database, in the table `built` (**`BuiltTable`**, in `service/src/built.ts`): part 0 says which version it was built from, by which release and key (`Relay.stamp`, private: the release, the service's address and its key), how many parts follow, the cards waiting, and until when it holds; parts 1 up are the state's JSON text, in parts of `PART` UTF-16 units that never split a character (`inParts()`), each under the 8 MB a value may be.
- **Never older than the files.** `SqlFileStorage`'s version moves in each write's own transaction, and the same statement empties `built`, so the table is empty or current: an upload, an answer, a waiting marker written or removed, a topic merge, the default branch, and retention removing a card's text (`SqlFileStorage.dropCard`), whose text is gone from here in the same step (R-1sxpy). A removal that's rolled back (`Relay.sweep`'s check that nothing else changes) brings the kept state back with the files. `BuiltTable.get` also refuses what was built from another version, under another stamp (a new release, or the service's key changed), or with a part missing, and it's then built again.
- **What moves no version is added as it's sent:** the clock (`server.now`), when this object started (`server.started`), and the reviewer's presence, read from `presence.json` as it is. The kept text is the state without those two keys; `Relay.state` puts them in front of it.
- **A waiting marker goes stale by the clock alone** (D90), with no write: what's kept says `stale: false` only until the first of its fresh markers would turn (`Built.until`), and a read after that builds it again.
- **What's waiting** (`Relay.waiting`) is kept in part 0, worked out from the state's cards by **`waitingOf()`**: open cards and audits, each at its level in force, the card's own raised by the relay's gate record, as `Store.levelOf` gives it; each with whom it was sent to, and a card a member passed on, with who passed it (`Waiting`, P20, below). So `GET waiting` and the alarm's notifications read one small row when the project hasn't changed, and build the state, and keep it, when it has.
- **Built again after a change** (`ProjectRelay.buildSoon`, `Relay.build`): two seconds after the last write, so a read that comes later, even after the object has left memory, finds it; a read that comes first builds it itself. It's a timer in the object's memory, not its alarm, so when notifications are decided is unchanged; if the object goes first, the next read builds it. An erased project's timer is cleared.
- **A reply's `text`** (`Reply.text`) is a body already made as JSON, which `reply()` and `respond()` send as it is.

- **The answers from before linking (B-3zjjx, M9e)** are the one exception to "a machine never uploads an answer" (Hosted Service section 3), bounded: at first link the CLI uploads the answers, rules, rule retirements, topic merges and preference files that count on its machine as from before linking (B-45xz8), and the relay takes them (`BEFORE_LINKING_KINDS`, `beforeLinkingKind()`) only while `SqlFileStorage.answered` says nobody has answered on the website. Each is checked as an upload is, must match its path, and must name no account or project, which only the website's answers do. It's kept unsigned and apart (`SqlFileStorage.asBeforeLinking`), and **`Relay.store`** counts it, as B-45xz8 counts the record at the linking commit on a machine (`StorageOptions.beforeLinking`), so its card shows as decided, marked `before_linking` in the state. Every other machine pulls it and counts it only where its own record at the linking commit holds it. The risk accepted: in that window, an agent with the machine's token could put an answer nobody gave on the website, labelled as from before linking; no machine counts it, and nothing more is taken once anyone answers there.
- **Uploads** take only the kinds an agent writes (`AGENT_KINDS`, `agentKind()`): card revisions, the CLI's gate records, withdrawals, fallbacks, attachments, decks, and waiting markers; and what the hooks write (D181): a ledger entry, only with the body that names nothing but its commit's short ID and its card (`isLedgerBody()`, through `AgentKind.check`, which is given a document's body), naming its commit, for a card already here; and a merge, named for its commit, branch and target (`mergeFile()`, B-ttn2c), of one branch into another, with the tip that landed and the commits citing cards it brought (B-w41p7); a later fast-forward of the same branch is a merge of its own, at its own commit, so a file the relay takes as any new one. And the repo's default branch (B-jr8mk), `default-branch.json` (`DefaultBranch`): only a branch's name, as git allows one (`BranchName`). Each is read as the store reads its kind, through `upgradeFile()` and the kind's schema, and its fields must match its path; a revision needs the one before it, and a withdrawal, fallback, attachment or marker its card (`uploadProblem()`). Everything a person writes, signatures, trust files and the relay's gate records are refused by name (`notAgentWritten()`). A waiting marker and the default branch are mutable state, replaced, never logged; the state carries the default branch as `defaultBranch` (`Store.defaultBranch`), and it's kept while the project is.
- **Writes** run in one transaction (`Relay.write`, private). The first write to a project puts the service's key in its layer, `trust/service-<key>.json`, so a machine's first pull has it before anything signed; every card revision written, uploaded or filed by Baesian, gets the relay's gate record, `Store.relayGate`, with its draw from `ServiceSigner.draw`.
- **An answer** names the session's account and handle, the project (B-tf9fc) and the card revision's digest (B-f571v), and the client, `hosted-desktop` unless the page says `hosted-phone` (D130). The relay's storage signs the verdict and whatever the answer writes beside it: a rule from an accepted draft, a rule's retirement, a slider proposal's preference file. Then Baesian's own proposals are filed, as the local server files them (`afterVerdict()`); their failure never fails the answer. Their cards name the branch `relay`.

### Who answers what (P20, B-r51ts, B-rxbss, B-v43z8)

Any member answers a card (`Relay.verdict`), and the answer names them. Two things are refused:
- **What only owners answer:** a rule's draft, a pattern to make a rule of, and a proposed move of one of the gate's settings (a card with `rule`, `convention` or `pref_row`), 403 from a member, as `POST preferences` is.
- **A card someone else has decided** (`DecidedByAnother`, 409): a second person's answer never replaces the first, so it isn't written, and the record keeps meaning what it meant, for every release that reads it. The reply says who decided, when, what, and whether this answer would have been the same (`decided: { by, at, decision, same }`). It's checked as the answer is written, so one that waited for the passkey while someone else decided is refused when the tap comes. The member who decided changes their own answer as before, and the agent is told (D81). An answer from before linking names no account, and is an owner's to change.

### Whom a card is sent to (P20, B-2n7s4, B-tzdjn; service/src/sent-to.ts)

A card is every member's, and it's **sent to** one: the member whose machine uploaded its revision (`ProjectRelay.upload`, given the account the machine is signed in as), noted in the same step as the upload in the table `sent_to` (**`SentTo`**: card, revision, account, when). A card only owners answer (`Relay.forOwners`: a rule's draft, a pattern to make a rule of, a proposed move of a setting), one Baesian files itself, and one that arrived before members were, are sent to **nobody in particular**, which means the project's owners.
- **It's the relay's own note:** in no file, so never in the log, never signed, and never sent to a machine. Nothing about who may answer rests on it. It goes when its card's text does (`SentTo.forget`, with retention).
- **In the state,** each card whose latest revision was sent to someone says so: `ApiCard.sent_to`, their account (`Relay.built`). The kept state holds it, and the note is written before anything can read the project, so no build is without it.
- **What waits for a member** (`waitsFor()`) is every waiting card but one only owners answer when they aren't one (`ownersOnly()`, `Waiting.owners`), and one they passed on ("it's outside my expertise", `not_my_area`): a card someone passed on still waits for everyone else (`waitingOf()` lists a `rerouted` card with the accounts whose latest answer on its latest revision passed it, `Waiting.passed`). Once every member has passed it, it waits for nobody, as a card its one reviewer passed on always has. **What was sent to a member** (`sentTo()`) is what waits for them and names their account, or names nobody when they're an owner. `GET waiting` counts both for the asker (`countFor()`).
- **A member who leaves** (removed, leaving, or their account deleted 14 days after closing): `ProjectRelay.memberGone`, called by the members' route (`SignIn.memberGone`) and by the daily job for each project the account was only a member of (`Accounts.memberOnlyOf`, `deleteClosed()`), sends their cards to nobody in particular (`SentTo.release`), moves the project's version so pages listening read the state again (`SqlFileStorage.touch`), sets the alarm so an owner is told of a card that's now theirs, and forgets their heartbeat and what they were told (`MemberPresence.forget`, `PushLedger.forget`). A closed account's cards stay sent to it for its 14 days, so restoring it finds them as they were.
- **Each member's presence** (**`MemberPresence`**, the table `presence_of`): their last heartbeat, there for 90 seconds (`MEMBER_PRESENT_MS`). The project's `presence.json` still says whether anyone is there, which is what an agent's wait reads (D41).

### Answers that take the passkey (D139, D163, M9c, B-a6xpc)

An answer on a card whose level in force is hard, whatever its response, and a preference file that lets more cards past you (a change, or an accepted slider proposal) take the reviewer's passkey. The relay finds them as it writes (`Relay.verdict` and `Relay.preferences` both run the answer the same way). Since B-a6xpc, such answers wait, and one tap of the passkey confirms every answer waiting:
1. **Composed, and waiting.** The answer runs through the store in a transaction; what it wrote that needs a proof is noted, by kind and SHA-256 digest, in the order written (`Needed`), and nothing is kept. The relay keeps the answer, its time and those digests for 30 minutes (`Pending`, `PENDING_MS`), long enough for a sitting, and replies 202: `{ passkey: { pending, proving, expires } }`, `proving` naming what it writes that takes the passkey (an accepted slider proposal that loosens writes two: the verdict and the preference file).
2. **Asked for together.** `POST batches` with the waiting answers' IDs, in the order they were answered, up to 50 (`MAX_BATCH`), each this account's own (`Relay.batch`). The relay keeps the batch (`Batch`) as long as its last answer waits, with the list of every file's digest; answers no longer waiting are named in `expired`. Its challenge (`challengeFor()`) is the digest of that list (`batchChallenge()`, [[src-trust#src/passkey.ts: passkey proofs (D139, D163, B-a6xpc)]]), or, for one file alone, that file's own digest, base64url, as before (P16 section 7). The Worker adds the browser's options for `navigator.credentials.get()`: the account's passkeys, user verification required.
3. **Signed.** The browser's one assertion comes back to `POST proofs`, `{ batch, response }`. The Worker checks it with SimpleWebAuthn (`verifyAssertion()`) against the account's own passkey and the batch's challenge, and moves the passkey's counter. An assertion over any other list (one missing an answer's digest, or in another order) doesn't check, and nothing is written.
4. **Written.** `Relay.proveBatch` runs each answer again, in turn, at the time it was composed, each in a transaction of its own: its bytes must be the ones the passkey signed, or its card changed meanwhile (`Changed`, 409: the card was answered again, or the preferences moved). Each file's proof is written beside it, `<file>.passkey.json` (`PasskeyProof`), naming the batch's list when it holds more than one file, the passkey's key file is put in `trust/` if it isn't there, and each file must then count by `Store.judge`, M9a's own checks, `proofProblem()` among them, before it's kept. An answer that expired between the ask and the tap isn't written (410); the rest are. The reply lists each answer's outcome (`Outcome`), each one written counted as its own address counts it, and the agents waiting on those cards hear of them over the log and the live socket as of any answer.

So **the relay can hold cards back**: a passkey-proved preference change counts in its store, and its gate record (`Store.relayGate`) holds what the new settings let past (B-sa8tg).

**Passkey key files** (`Relay.putKeys`): each of an account's passkeys, `trust/passkey-<12 hex>.json` named for its credential (`keyFileName()`), the same bytes in every project, signed. They're put in every project the account owns when a passkey is enrolled or a project is made, and again with each proof. The CLI pulls them; CI pins each by hand (D159), with the line the website gave at enrolment.

## Retention (service/src/retention.ts)

M9f, as cards B-9jqt4 ("Keep it 30 days after delivery"), B-ec3kj ("90 days, then only its metadata"), B-dsqyd ("30 days after delivery, as answered") and D137 decided, and the rule R-1sxpy restates: a card's text goes from the relay on a schedule, and the project's log keeps every entry, so a machine is sent each one without its body and the relay still knows what was at each path. The periods are **`RETENTION`**; **`due()`** says whether a card's text goes now, and **`delivered()`** whether a card is delivered. The [[Privacy Policy]] states them.
- **An answered card** (resolved or superseded) keeps its text 30 days after it was **delivered**: every machine whose grant for the project is live now (not revoked, not lapsed after 30 days unused, `Accounts.liveGrants`; locally and in tests the stand-in's machines too) has been sent the log past the card's last entry, and at least one machine has. "Sent" is a `GET log` reply that carried it (`Relay.log` notes each machine's furthest, by its grant), not a later request's `after`, so a machine that pulls once and is never used again doesn't hold it back for good. An answer no machine was ever sent keeps its card's text. A changed answer (D81) is a new last entry, and the 30 days start again.
- **A held card nobody answers** (held, not drawn as an audit) loses its text 90 days after its latest revision arrived, delivered or not.
- **A withdrawn card**, by its agent or because a card it builds on was rejected, likewise: 30 days after the withdrawal was delivered (B-dsqyd).
- **Everything else** keeps it: open cards and audits, returned, passed on and deferred ones.

**The commits that cite a card, and merges (D181).** A ledger entry is its card's path (`cardOfPath()`), so its bytes go with the card's text; it isn't the card's last entry (`isLedgerPath()`, `SqlFileStorage.cardsInLog`), so a commit citing an answered card doesn't put off the day its text goes. A merge goes once every card it brought has, and each of the commits it lists had ledger entries here that went with their cards' text, none left, which is once every card they cite has gone too (B-w41p7; `SqlFileStorage.dropFiles`, after the cards each day). B-15v62 ("Keep it, and say so", decided by the user): a commit whose ledger entries never came here (made on a machine that isn't signed in to the project, or before ledger entries left their machine) hasn't gone, so a merge listing one stays while the project does, as one that brought only a branch's deck does, as decks do: the relay can't tie it to any card's text, and /privacy says so. Before, the daily look read "never had them" as "they all went" and dropped such a merge at once, for good, since its log entry kept answers a second upload "already here". The commits whose entries went are noted as their cards' text goes (`RetentionLedger.commitsGone`), read from the entries before they're removed, in the same transaction. Both go with the project when its owner's account is deleted, as does the default branch (B-jr8mk), which is kept while the project is.

**`Relay.sweep`** runs once a day per project, at the object's alarm (`ProjectRelay.sweep` gives it the live machines): it finds each card due, notes what stays of it, and removes its files' bytes (`SqlFileStorage.dropCard`): its revisions, gate records, withdrawal, fallbacks, attachments, answers and their proofs, and waiting markers, with their signatures. All due cards go in one transaction, unless that would change another card's status or level as the relay's store computes them (a card built on one, returned because it chose otherwise; one superseded by it): then each is tried alone, oldest first, and one that changes another waits until that one goes too. Rules, topic merges, preferences, decks and trust files are never removed.

**`RetentionLedger`** is five tables in each project's object, never logged, signed or sent: `retention_sent` (per machine, the furthest it was sent the log), `retention_delivered` (per card, when it was first found delivered, at which last entry), `retention_removed` (per card whose text went: its ID, latest revision, level in force, how it ended, when it was filed, settled and removed, and its size), `retention_held` (per writer and row, how many held cards' gate records went, which the burn-in still counts through `StorageOptions.heldEarlier`, so removing a card never changes how the gate holds the next), and `retention_commits` (the commits whose ledger entries went with their cards' text, `RetentionLedger.goneCommits`, B-15v62). A project whose cards' text went before `retention_commits` existed has none of their commits noted, so its merges listing them stay; none had, the relay being under 30 days old.

**What the website and the CLI see.** The state lists the removed cards as `removed` (`ApiRemovedCard`, [[Client Build]] item 21), never among `cards`. An upload for a removed card is refused with 410 (`Relay.upload`), and the CLI then stops offering the card's files; a file sent again with the bytes the log names is taken as already there (200). A machine that pulls an entry with no body has nothing to write; if it has the file nowhere, here or in the record, it's told ([[src-sync]]).

## Signing (service/src/signer.ts)

**`ServiceSigner`** holds the service's Ed25519 key, PKCS #8 in PEM, from the secret. **`ServiceSigner.sign`** signs a file of a kind the service signs (`signedFile()`) as `signMessage()` does, OpenSSH's armored format in the `baesian` namespace; **`ServiceSigner.draw`** signs a card revision in `baesian-draw` (`drawMessage()`) and reads the draw from that signature; **`ServiceSigner.serviceKey`** is the key's trust file, from `SERVICE_KEY_ID`, `SERVICE_ORIGIN`, `SERVICE_RP_ID` and `SERVICE_KEY_VALID_AFTER`. With the stand-in's key (`test/service.ts`), the relay's gate records and signatures are its bytes, but for the time.

**The spare key (B-x47ek, "Pin a spare key now"; [[Release v1]] step 6).** The spare in use is `relay-2`, made on 2026-11-10; its variables are in `service/wrangler.jsonc`. The person makes a second Ed25519 key with `service/scripts/spare-key.mjs`, which writes its private half to a path they give, outside any repo, readable only by them, and prints its public half and three Worker variables for `service/wrangler.jsonc`'s `vars` (variables, not secrets: they're public): `SERVICE_SPARE_KEY_ID` (the key after `SERVICE_KEY_ID`, `relay-2`), `SERVICE_SPARE_PUBLIC_KEY` (`ssh-ed25519 AAAA…`) and `SERVICE_SPARE_KEY_VALID_AFTER` (when it was made). The private half is kept offline. **`spareKey()`** reads the three into the service key file the relay would write the day it signed with it, with the service's origin and relying party, or says why it can't (one missing, the key in use's ID, not an Ed25519 key). The service never signs with it: **`keysReply()`**, `GET /v1/keys`, publishes it as `spare` beside the key in use, `service`, with `problem` when it's named but can't be read; and `baesian ci` prints its line beside the key's ([[src-sync]]). It's never in a project's files, so no record holds a key CI doesn't pin yet (D142). The day the key in use must be replaced: set the secret `SERVICE_SIGNING_KEY` to the spare's private half, `SERVICE_KEY_ID` and `SERVICE_KEY_VALID_AFTER` to the spare's, take the three spare variables out, deploy, and make a new spare. The relay then writes the spare's key file as it writes any key it signs with, which is the line CI pinned, and keeps trusting the old one (`Relay.root`). Revoking the old key, if it was compromised, isn't built: the relay writes no revocation.

## Live updates (B-bv49e)

`GET live` is accepted with `ctx.acceptWebSocket`, so an idle socket costs no duration. On opening it's told the version, `{"type":"changed","version":N}`, and again after every request that moved it; the client reads the state again, as it does on the local server's `changed` event. A `ping` is answered `pong` by the runtime (`setWebSocketAutoResponse`). Sockets survive the object's eviction, hibernated, and hear the next change. A project's desk holds one, and so does the projects page, one for each of your projects, to ask a project's waiting count again when it changes (B-gty71, [[Client Build]] item 30).

## Who may do what (service/src/access.ts)

**`Access`** says who a request is from: `Access.identify` gives a **`Principal`**, a session (a person in a browser: account and handle, and the project the address names if the account is one of its members, with its role there, P20) or a machine (a grant: machine, account, project), or nobody. **`accountAccess()`** is the real one (M9c): a bearer token is a grant's access token (`Accounts.grantByAccess`), and otherwise the cookie `SESSION_COOKIE` (`__Host-baesian-session`) is a sign-in (`Accounts.session`); a session reaches the projects its account is a member of (`Accounts.role`), as an owner or a member. **`handleRequest()`** enforces Hosted Service section 3 whatever implements it:
- an answer (`verdicts`, `aliases`, `preferences`, `proofs`, `presence`) refuses any request with an `Authorization` header, whatever it holds, before anyone is identified, so no token can answer;
- a person's request must come from the website's own pages (`crossSite()`): `Sec-Fetch-Site`, when sent, must be `same-origin` (or `none`), an `Origin`, when sent, must be `SERVICE_ORIGIN`, and anything that changes something must send one. SameSite=Strict keeps the cookie off other sites' requests too;
- only a machine uploads, and only a session answers; each grant is for one project, and a session reaches only the projects its account is a member of (403 otherwise); nobody signed in is 401;
- a project's settings are its owners' to change (B-rxbss): `POST preferences` from a member is 403 (`refusal()`, and again in `ProjectRelay.answer`).

**`accessFor()`** picks the implementation: `accountAccess()` whenever there's an accounts database; and only when `BAESIAN_ENV` is `development` (a local run, from `.dev.vars`) or `test`, with grants given in `BAESIAN_DEV_ACCESS`, M9b's stand-in beside it (`devAccess()`, `readGrants()`, `eitherOf()`): fixed machine tokens and session cookies, each for one project. `wrangler.jsonc` makes production the default (unset counts too), where only real sign-ins count. With no accounts database at all, `NO_ACCESS` refuses everyone.

## Accounts (service/src/accounts.ts)

**`Accounts`** is the D1 database (B-ytdt2), its tables in `service/migrations/` and [[File Formats#Accounts (M9c)]]. Every secret is kept as its SHA-256 (`hashOf()`, `service/src/secret.ts`): session and machine tokens, emailed codes, recovery codes, flow secrets. **`LIMITS`** holds every lifetime and count:
- a sign-in ends after 30 days unused or 90 days in all (B-vtr1r); its last use is written at most every 5 minutes; it keeps a name ("Firefox on a Mac", `browserName()`) and its last use, nothing about where it came from (B-7bq05);
- what asks for the passkey afresh (adding a passkey, linking Globus, approving a machine) takes a check in the last 5 minutes (`Accounts.fresh`); signing in counts as one;
- an emailed code is six digits, works for 15 minutes and 5 tries (`Accounts.tryCode`), and an address gets at most 5 codes an hour and 10 a day (`Accounts.codesSent`); a sign-up or recovery, once checked, has an hour to enrol its passkey; a passkey ceremony, 5 minutes;
- a recovery code is 20 characters of Crockford's base32, in four groups (`recoveryCode()`), replaced each time it's used;
- a machine's access token lasts an hour; its grant lapses after 30 days unused; a request to sign in waits 10 minutes, polled every 5 seconds.

**Members (P20, stage 1; `service/migrations/0006_members.sql`).** A project has members, in the table `members`: the accounts that read it and answer its cards (B-r51ts), each an owner or a member (`Role`). `projects.owner` stays the account that made the project and holds it: always an owner, never removed, and the one whose deletion deletes the project (B-b46z3). Migration 6 made every project's owner its first member.
- **`Accounts.role`** is an account's role in a project, or nothing; **`Accounts.member`**, whether it has one. Nobody has a role in a project whose holder's account is closed: the project closes with it, for every member, until it's restored or deleted. **`Accounts.projectsOf`** is the projects an account is a member of, each with its role (what `GET /v1/account` lists); **`Accounts.projectsHeldBy`**, the ones it made, which is what deleting an account erases (`deleteClosed()`), never a project it was only a member of. **`Accounts.members`** lists a project's members, the holder first.
- **A link adds one person** (B-jsady): `Accounts.invite` makes a code, good once for seven days (`LIMITS.inviteMs`), and keeps only its hash, with who made it, in `invites`; no address is kept. `Accounts.lookInvite` says what a code is for while it still works; **`Accounts.acceptInvite`** uses it up and adds the member in one batch, so two people opening one link can't both join; `Accounts.cancelInvites` drops the unused ones.
- **`Accounts.removeMember`** takes a member out, or lets them leave: the membership goes and that account's machines are signed out of the project, in one batch. **`Accounts.setRole`** makes a member an owner, or back. Neither touches the holder.
- **`Accounts.approveDevice`** lets any member sign a machine in to the project; someone who isn't one is told to ask an owner for a link. **`Accounts.close`** also signs every member's machines out of the projects the account holds.

A flow (`Flow`) is a sign-up, recovery, sign-in, fresh check, enrolment or Globus round trip in progress, found by the hash of the secret its browser holds. **`Accounts.refresh`** rotates a grant's tokens in one conditional batch; a refresh token used again, or twice at once, revokes its grant (RFC 9700).

## Web push (service/src/push.ts)

Baesian's own code on Web Crypto (B-nk97q), with no dependency. **`encrypt()`** is RFC 8291's `aes128gcm`: an ephemeral P-256 key (`ephemeralKeys()`), ECDH with the browser's `p256dh` (`ecdh()`), HKDF with its `auth` secret, AES-128-GCM over one record of up to 4,096 octets (`RECORD_SIZE`), its header carrying the salt and the server's key; the plaintext is padded to 512 octets (`PADDED`), so a message's length doesn't say how long a project's name is. **`Vapid`** makes RFC 8292's tokens: ES256 JWTs whose audience is the push service's origin, expiring 12 hours ahead (`TOKEN_LIFE_S`, under Apple's day), each reused for an hour per push service (`TOKEN_REUSE_MS`, as Apple asks), with the website's origin or a `mailto:` as subject; the key is the secret `VAPID_KEY`, a P-256 private key as a JWK (`vapidKey()`, and `vapidPublicKey()` for `/v1/config`). **`sendPush()`** posts one with `TTL` (a day, `PUSH_TTL_S`), `Urgency` and `Topic`, 32 characters of base64url from the project's ID (`topicOf()`), so a newer push replaces an undelivered one and the push service doesn't see the ID; 404 or 410 is `gone`.

## Notifications (service/src/notify.ts)

When they go is card B-advkh, "Stopping cards at once, the rest in a digest"; to whom, B-tzdjn, "Sent to one, open to all" (P20); what they say, B-mjf3g. A card revision a machine uploads is noted in the project's object (`PushLedger.arrive`), with its machine; the object's alarm is set for 10 seconds on, and at it (`ProjectRelay.notify`, private) **`decide()`**, one pure function of what's known, says what to do for each member of the project (`Accounts.toNotify`: those whose account is open, in a project whose holder's is), with the numbers in **`WHEN`**:
- **a card sent to them** (`sentTo()`, above): a blocking or hard one is due 10 seconds after it arrived (`soonMs`), so a burst of filings is one notification, at high urgency; a provisional one, 3 hours after (`digestMs`), at normal urgency; a notification sooner counts it in, and settles it;
- **a card sent to someone else:** a blocking or hard one is due once it has waited half an hour (`othersMs`, B-aaj69, "After half an hour"), and a provisional one never is on its own;
- **a card passed on by whoever it was sent to** ("it's outside my expertise" from its member, or from an owner when it was sent to nobody in particular; `ProjectRelay.passedOn`, private, as the answer is written, with or without the passkey): an arrival again for everyone but them (`PushLedger.handOn`, `Arrival.handed`), due 10 seconds after, whatever its level and whatever its machine's pause. A member passing on a card sent to someone else puts it aside for themselves, and tells nobody;
- nothing is sent to a member who is present in a client (`MemberPresence.present`, a heartbeat of theirs in the last 90 seconds, D41), and what arrived then is settled for them as seen; another member's being there silences nobody else;
- at most 4 an hour to each member from a project (`capPerHour`, `PushLedger.sent` by account); the next waits for the hour to free, and counts everything waiting then;
- more than 20 new cards from one machine within 10 minutes (`burst()`) pause its cards' notifications for an hour after its latest (`pauseMs`); they're on the desk, and other notifications count them; the project's page says so, from `GET pushes`;
- a card answered, withdrawn or revised before its time is settled without one.

What a member was told of, saw while present, or is never to be told of is settled for them alone (`PushLedger.told`, the table `push_told`); an arrival waiting for nobody any more, for the project (`PushLedger.settle`), and what each member was told of it goes with it. A project of one member is told exactly as it was before there were members: every card is theirs. With no members known (no accounts database, or a project it doesn't have), `decide()` runs once, for nobody named, as it did then.

What's waiting is what the desk's queue holds (`Relay.waiting`, kept with the state as built, B-evrec): open cards and audits, at their level in force, counted by **`countWaiting()`**, as `GET waiting` gives them to the projects page (B-wgbdh). The notification (**`pushText()`**) counts all that wait for the member it goes to, with the hard and blocking ones, and the project's name (B-zqkwk): "2 cards waiting in Shop (1 hard)", "Tap to open them."; its page is `/projects/{project}` and its tag `baesian:{project}`. It goes to every browser of that member that gets them (`ProjectRelay.send`); one its push service says is gone is deleted (`Accounts.dropSubscription`), and each delivered one's `last_sent` is set. Without `VAPID_KEY`, nothing is sent.

## Usage counts (service/src/usage.ts)

D141, "everyone, with an opt-out", and B-7nq85, "Ten kinds of event, fixed values only". The kinds and their fields are one list, `USAGE_KINDS` in `src/usage-fields.ts`, which the website's public page, `/counts`, shows: **`Usage.record`** keeps an event only if `usageProblem()` passes it, every value from a fixed list, a whole number or yes/no, so none can carry text. Each event names the account's `usage_id` (random, made at its first event) and the project's `usage_key`, and the hour, UTC; a server error names neither. **`Usage.setCounted`** opts out, deleting the account's raw events and its usage ID, or back in; **`Usage.recordDaily`** keeps the first of a day (a visit); **`Usage.rollup`** turns events older than 90 days (`USAGE_RAW_DAYS`) into daily counts, `usage_daily`, with no ID, key or hour, at most once an hour as events are recorded. A failure to count is logged, and never fails what was counted. `harnessOf()` keeps an agent's name only as `claude-code`, `codex` or `other`. The written balancing test is a draft, [[Usage Counts Balancing Test]].

## Deleting an account (service/src/deletion.ts)

M9f, as card B-b46z3 decided, "Closed for 14 days, then deleted"; the [[Privacy Policy]] says the same.
- **Closing** (`POST /v1/account/delete`, `closeAccount()`): the handle typed out, regardless of case, and a passkey check in the last five minutes, as adding a passkey asks. `Accounts.close` sets `accounts.closed`, deletes every sign-in, subscription and flow of the account, and revokes every machine's grant, in one batch; each of its addresses is emailed when it will be deleted and how to keep it (`mails.accountClosed`). The reply clears the cookie. A closed account has no sign-in (`Accounts.session` takes none), no machine, no notification, and nothing is counted for it (`Usage.record`); its projects' objects keep their data, which nobody can reach.
- **Restoring:** a passkey sign-in to a closed account (`/v1/signin/finish`) signs nobody in: it answers 409 with when the account will be deleted and a `restore` flow for five minutes, and `POST /v1/signin/restore` reopens it (`restoreAccount()`, `Accounts.reopen`), emails a notice (`mails.accountRestored`) and signs in. Its projects are as they were; its machines sign in again with `baesian login`, and notifications are turned on again. Getting back in by email treats a closed account as none, and Globus sends the browser back to `/sign-in` saying to use the passkey, so only the passkey restores it.
- **Deleting, 14 days on** (`DELETION`, `deletesAt()`): the Worker's daily job, `housekeeping()`, on its cron trigger (`service/wrangler.jsonc#triggers`, 04:17 UTC), runs `deleteClosed()`: for each account closed 14 days ago or more, each project it owns is erased (`ProjectRelay.erase`: its sockets closed, its alarm deleted, its whole database deleted with `storage.deleteAll`, atomic on SQLite; its tables made again only if anything asks for it after), then `Accounts.erase` deletes its rows table by table, each named, not left to the foreign keys' cascades: raw usage events (by its usage ID), flows (by account and by its addresses), spent tokens, grants (its own and its projects'), device codes, subscriptions, sign-ins, its Globus identity, recovery code, passkeys, addresses, projects, and the account. `usage_daily` names no one and stays. An account whose projects can't all be erased waits for the next day. The same job clears what has ended (`Accounts.clearEnded`): sign-ins, machines signed out or lapsed, flows, device codes, and a link to a project a day after it's used or it expires (P20).
- **The CLI after:** a machine of a deleted account gets 401 and says to sign in again; `baesian login` makes the project again, owned by whoever approves it, and the CLI, finding the log shorter than what it had pulled, starts afresh and sends everything its agents wrote ([[src-sync]]).

## Machines (service/src/machines.ts)

OAuth's standard endpoints (B-t5wxr), form-encoded, for `baesian login` (M9d): `machinesRoute()`. The client is `CLIENT_ID`, `baesian-cli`, a public client.
- `POST /v1/machines/device`: RFC 8628's device authorization, with `project` and `machine` besides: `{ device_code, user_code, verification_uri, verification_uri_complete, expires_in, interval }`. The page is the website's `/device` (M9e).
- `POST /v1/machines/token`: the device code grant (`authorization_pending`, `slow_down`, `access_denied`, `expired_token`), and `refresh_token`, each refresh token once; `{ access_token, token_type, expires_in, refresh_token, project, machine, grant }`.
- `POST /v1/machines/revoke`: RFC 7009, by either token; always 200.

## Passkeys (service/src/webauthn.ts)

SimpleWebAuthn (B-jp22m), with user verification required everywhere and attestation `none`: `registrationOptions()` (discoverable, ES256, EdDSA or RS256, `PASSKEY_ALGS`), `verifyRegistration()` (and `spkiOf()`, the COSE key as SubjectPublicKeyInfo for the key file), `authenticationOptions()` (a challenge given, as a proof's digest, or a random one), `verifyAssertion()`, and `keyFile()` and `pinLine()`, the key file and its line for `BAESIAN_TRUST` (D159).
