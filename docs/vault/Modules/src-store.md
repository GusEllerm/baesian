# src/store.ts

`Store` is the only code that touches Baesian's files. `Store.overRecord` opens a read-only view of a committed record, which is how CI reads it ([[src-verify]]). `Store.open` finds the repo with `openRepo`. The live layer is `LIVE_DIR` inside git's common directory, and the record is `RECORD_DIR` in the worktree ([[File Formats]]).

## One store, two kinds of storage (B-0ag7h)

The store reaches the live layer only through `Storage` (`src/storage.ts`), so the same code files, answers and checks on your machine and on the relay (M9b), as card B-0ag7h decided. The record, `.baesian/`, and everything git does stay on your machine, in Node.

**The interface has five methods,** all synchronous, as a Durable Object's SQLite storage is. Paths are relative to the layer and `/`-separated (`cards/B-7f3kq/r1.md`):
- **`Storage.read`** gives a file's bytes, or undefined when there's none;
- **`Storage.list`** gives a folder's names, files and folders alike, one level down. A folder exists while it holds a file, and a write in progress is never listed;
- **`Storage.create`** writes a file that never changes, whole and once: a second create throws an error whose `code` is `EEXIST` (`FileExists`; `alreadyExists()` tells), and no reader sees it half-written;
- **`Storage.replace`** writes a mutable file, replacing what's there, so a reader sees the old bytes or the new: presence, waiting markers and inbox cursors;
- **`Storage.remove`** removes one, for a waiting marker that stops.

**No file carries a time from the storage.** What goes stale, presence and waiting markers, says when it was written in its own `at` (D41, D90), and the store judges staleness from that, as it always has. Nothing here reads a file's modification time; workerd's `node:fs` gives the Unix epoch for every one anyway. Only the local server's watcher reads them, for its fingerprint (`watchLive`, [[src-server]]).

**The two implementations:**
- **`FolderStorage`** (`src/folder-storage.ts`) is a folder, with exactly the old behaviour: `FolderStorage.create` writes a temporary file and links it into place, falling back to an exclusive create where hard links aren't supported; `FolderStorage.replace` writes a temporary file and renames it over the old; `FolderStorage.list` hides the temporary files (`.tmp`). Inbox cursors were rewritten in place before; they're replaced whole now, as presence is.
- **`MemoryStorage`** keeps one entry per path, as the relay's table will. It hands out copies, so nothing changes a file once written, and refuses a path that isn't the layer's (`checkPath()`). It stands in for the Durable Object in tests; `MemoryStorage.paths` lists what it holds.

**`Store.storage`** is a store's live layer. A store on your machine has a repo and a record besides (`Store.hasRepo`), and `Store.repo`, `Store.live` (the folder) and `Store.record` give them.

## Personal mode (B-4rwyz)

**`Store.personal`** says a clone uses Baesian in personal mode: for one person, in a repo whose collaborators don't, committing nothing. What makes it so is the clone's own config in the live layer, `PERSONAL_CONFIG` (`.git/baesian/config.json`), which `Store.init` writes in place of the record's when asked for personal mode, or when the clone is personal already. A read-only view of a committed record, and a store with no repo, never are. In a personal clone:
- **`Store.config`** reads the clone's config, and `Store.setVault` and `Store.setLink` write it (the same `Config`, in the same format);
- **no record is written**: the private step that copies each new file into the record does nothing, and `Store.syncRecord` copies nothing, so the live layer plays the record's part, and a stray `.baesian/` is never made;
- **answers from before linking** (B-45xz8) are what the clone held when it was linked, since there's no record at a linking commit: `Store.setLink` keeps the blob ID of each unsigned verdict, rule, retirement, topic merge and preference file in `BEFORE_LINKING` (`before-linking.json`, a `BeforeLinkingSnapshot`), once per project, so linking again keeps the first, and the private linking step reads it in the record's place. A clone that switched to shared mode keeps it in that place until the link is committed, where before the record at HEAD stood in.

**`Store.sessionKnown`** says whether a harness's session has read the branch's inbox before; the CLI's quiet inbox hands a personal clone's agent its instructions at a session's first read ([[src-cli]]).

## A store with no repo (B-0ag7h)

`Store.over` makes a store over any `Storage` alone, with no repo and no record, as the relay will run one. `StorageOptions` gives it what the repo would: the branch it files on (`source_branch`, the branch's deck, its inbox cursor), the record's config (`project`, in a hosted repo), the keys it pins, the answers a machine uploaded as from before linking (`beforeLinking`, B-3zjjx), and the held cards whose gate records the relay's retention removed (`heldEarlier`, M9f), which the gate's burn-in still counts. It never reads CI's settings (`BAESIAN_TRUST`): unless it's given keys, it pins none, and a layer with the service's key in `trust/` makes it hosted, as on your machine.

**It does everything over the live layer as any store does:** filing and revising, with the gate and its record; withdrawals and fallbacks; `Store.addVerdict` with all it does (stale revisions refused, rules saved and retired, the preference file a slider proposal writes, convention cards through `afterVerdict()`); topic aliases; preference changes; the gate records; `Store.view`, with the same caching per view; status and levels; inbox, presence and waiting markers; and in a hosted repo `Store.judge` and `Store.hosted`. `Store.isInitialised` is true.

**What it can't do, it refuses with `NeedsRepo`, before writing anything:** `Store.init`, `Store.setVault`, `Store.syncRecord`, a deck's `from` path in `Store.createDeck`, and `Store.repo`, `Store.live` and `Store.record`. Two things go quietly instead, since filing and answering need them on the relay: the copy of each new file into the record is skipped (it's your machine's, and it pulls what the relay holds, P15); and a brief's commits (`BriefCommit`) are only the ledger's, with none found in git's history and none marked rewritten, since there's no history to look in (B-17wn9 left these out on the website).

**It calls nothing in `node:fs` or `node:child_process`.** `test/storage.test.ts` notes every call to either while a store over `MemoryStorage` files, answers, checks a hosted repo's signatures and builds the state, and expects none. The same file checks that the state built over memory equals the one a store over the repo's folder builds from the same files (`snapshot`, [[src-server]]), and that the state's reads grow linearly with the cards. The store's own tests run over each kind of storage (`LAYERS` in `test/helpers.ts`, each layer with the `it` its tests run with), and in workerd over the relay's SQLite too ([[service#Tests]]).

## What the store does for the relay (M9b)

The relay runs this store over a Durable Object's SQLite (`SqlFileStorage`, [[service]]); its storage signs what a person writes as it's written, so the store itself never signs. Three things are the relay's:
- **`Store.relayGate`** writes the relay's gate record for a card revision it accepts (D158), `cards/<id>/gate-r<n>-relay.json`, as `TestService.gate()` writes it, byte for byte but for its time: the rules over the revision's facts under the preferences in force, the draw it's given from the service's signature over the card, kept as `draw_proof` on a held card, and the project. The burn-in counts the relay's own enforcing held records. What the revision is to the gate is worked out from the files, as filing it decided: Baesian's own card, a revision after the reviewer's own answer or the agent's reply, or the agent's.
- **Who wrote it.** `Store.mergeTopics` and `Store.writePreferences` take the account and the project the relay names, and an answer's `project` goes into everything it writes besides: a rule saved from a draft, a retirement, a slider proposal's preference file (B-tf9fc).
- **`signedFile()`** says which files the service signs: those `Store.judge` judges, the relay's gate records and passkey keys.

## Format numbers (D156, D157)

Every file the store writes carries `format`, right after `type`, and is written in the newest format of its kind (`newestFormat()`): revisions, verdicts, withdrawals, fallbacks, ledger entries, decks, rules, retirements, aliases, attachments, presence, waiting markers and the inbox cursors (`Cursor`). `Store.init` and `Store.setVault` write it first in `config.json`. A revision's `format` is always Baesian's, whatever a draft says: a draft's own optional `format` is the card draft format.

Every file the store reads goes through `upgradeFile()` before its schema: a file with no `format` was written before v1 and reads as format 1, an older one is upgraded in memory, and nothing is ever rewritten for it. A file in a newer format throws `NewerFormat`, naming the file, its kind and format, and what this Baesian reads. That's how bad files are treated already: `Store.view` with a `report` reports it and skips it, and without one it throws. `Store.presence` treats one as "unknown", as it does any unreadable file, and so does `Store.startWaiting` when it looks for its own marker. The table of kinds and their upgrades is `FILE_KINDS` in `src/schema.ts` ([[File Formats#Rules that apply to every file]]).

## The hosted service's proof (M9a)

In a hosted repo only what the service signs counts (D138), and the store is where that's applied, so every reader agrees: the CLI, `baesian wait`, the hooks, the server, the MCP server and `baesian verify`. Outside one, nothing here changes anything. The formats are in [[File Formats#The hosted service's proof (M9a)]], and the checks themselves in [[src-trust]].

- **`Store.hosted`** says whether the repo is hosted, and with which keys (`Hosted`): CI's pinned keys whenever it pins any (D142, D159), read from its settings the first time they're needed, or given by the caller as `StoreTrust` (`Store.open`, `Store.overRecord`; `null` pins none); or else the service's keys in the layer's `trust/` (`Store.trustFiles`), with its passkey keys only once the service signed them. Revocations count wherever they are. It carries the repo's project, which every signed file must name too (B-tf9fc): the one CI pins beside the keys (`TrustRoot.project`, B-mar8x), whatever the config says, or else the config's.
- **`Store.judge`** says whether a file a person writes counts, and why not (`Judgement`): its `.sig`, by a trusted key valid at the file's own time; its name and folder matching what its bytes say, since a signature doesn't cover them; its `project` matching the repo's, since one key signs every project's files (B-tf9fc); for an answer, its `card_digest` matching the card revision's file, so a card rewritten after its answer is unanswered (B-f571v); and a passkey proof for an answer on a hard card (D139) or a preference change that lets more past you (D163), alone or in the batch form one tap over several answers writes (B-a6xpc), by a passkey key trusted for the file's own account. Preference files are judged oldest first, each against the newest counting one before it. A judgement holds for a view, since files are written once. A signature or proof in a newer format still throws (`NewerFormat`).
- **Answers from before linking (B-45xz8, M9d).** An unsigned file a person wrote (a verdict, rule, retirement, topic merge or preference file) counts as it is when it was in the record, with the same bytes, at the commit that linked the repo: answers given before linking were trusted then (D62), and anything added later needs the service's signature. `recordAtLinking()` finds that commit, by ancestry, never by commit dates, which anyone can set (B-mar8x): in the history of a commit, the one whose config names the project and none of whose ancestors' configs do; and lists its record's blobs; each file is compared by its blob ID (`fromBeforeLinking()`, private). Two or more such commits, none descending from another (a commit made on a branch from before the link, or the link committed twice), fail closed: `unclearLink()` says why, and nothing unsigned counts. A store finds it once, in its own commit's history (HEAD's on your machine; for `Store.overRecord`, the commit whose record it reads), for the project CI pins or else the config's; or it's given one, as `StoreTrust.linking`, which is how `baesian verify` with a pin finds it once from the tip and uses it for every commit, those from before the link included ([[src-verify#In a hosted repo (M9a)]]). Unpinned, before the link is committed, the record at HEAD stands in for it, or what a personal clone held when it was linked (B-4rwyz, above); with keys pinned, nothing does, so a commit can't make up a linking commit of its own. **`Store.linkingCommit`** says which commit it is, or why it can't be told. In a shallow clone, when the commit found is the clone's boundary, the real one may be further back, so an unsigned answer can't be told apart: it doesn't count, with `SHALLOW_HISTORY` as its reason, and `baesian verify` fails, saying to fetch the full history ([[src-verify]]). A store with no repo, as the relay's, has no history: it counts only the files it's given as from before linking (`StorageOptions.beforeLinking`), which the relay took from a machine before the project's first answer on the website (B-3zjjx, M9e). **`Store.answersFromBeforeLinking`** lists what counts here this way, for the CLI to upload at first link; **`Store.decidedBeforeLinking`** says whether a resolved card's answer is one of them, which the state gives as `ApiCard.before_linking`, for the website to say so.
- **The readers skip what doesn't count:** `Store.verdicts`, `Store.rules` (and a retirement), `Store.aliases`, `Store.preferenceNames` and `Store.preferenceFile` (so `Store.inForce`), and the relay's records in `Store.gateRecords`. So a card answered only on the machine stays open, an unsigned rule covers nothing, and an unsigned preference file is never in force.
- **The gate record that counts** (`Store.gateRecord`) is the relay's signed one in a hosted repo (D158), so a card the relay hasn't gated isn't held. `Store.gateRecordBy` gives one writer's.
- **`Store.levelOf`** is the level in force on a revision: the card's own, raised in a hosted repo by the relay's signed record when it shows the card higher (P16 section 3). The commit gate's hard check (`evaluate()`) and `baesian wait` read it.
- **`Store.uncounted`** lists what doesn't count, with why, for `baesian verify`'s notes. **`Store.bytes`** gives a file's bytes as written, which a signature covers.
- **`Store.syncRecord`** copies a signed file with its `.sig` and passkey proof, and in a hosted repo only once it counts, so an answer written on the machine never reaches the record (P15). It copies `trust/` into every branch's record, as it does rules.

## Errors

The store's errors are classes, so the MCP server can give each a code ([[src-mcp]]); the CLI prints their messages and exits 1, or 3 for a duplicate. Most are `Told` errors (src/cite.ts): a message that may cite Baesian's decisions, which only `--verbose` prints, and the next steps it knows, which its `message` gives as `next:` lines ([[src-cli#What it prints: src/style.ts (B-eyrt5)]]):
- `NotARepo` (from `openRepo`): the directory isn't in a git repository;
- `NotSetUp` (`Store.requireInit`): there's no live layer, so `baesian init` hasn't run, which is its next step;
- `ValidationError`: the card fails its schema or a filing rule. A draft that isn't a card says how many fields need filling in or fixing, then which are missing, empty or wrong, in a few lines (`describeDraftError()`), with `baesian template` as the next step; a filing rule says `not filed:` and the rule (`filingProblems`);
- `PossibleDuplicate`: an open card or a resolved decision may cover it, with the matches;
- `NoCard`: no card with that ID;
- `NotAllowed`: the card's state, or who asks, doesn't allow it: revising a card that isn't returned, a second reply, a rule nobody asked for, withdrawing another agent's card or one already withdrawn;
- `NoDeck`: the card names a deck that doesn't exist;
- `StalePreferences`: a preference change made from an older view (the server says 409);
- `NeedsRepo`: a store with no repo was asked for something that needs git or the record (above);
- `LooksLikeSecret`, a `ValidationError`: in a hosted repo, a draft that looks like it holds a secret, with no `secret_reason` (B-jfkv9). Its message names each field and the kind of secret, never the text.

## Writing

- **`Store.fileCard`** validates a draft, checks for possible duplicates, assigns an ID and writes revision 1. It writes into the live layer and copies the card and its deck into the worktree's record.
  - **The filing rules:** `filingProblems()` rejects a draft whose two options are really one, whose crux doesn't decide between them (D74), that lacks `wrong_if` and `check` when a facet asks for them (D77), or that has half a facet (D75). The store also rejects IDs in `depends_on`, `rules` or the `_breaks` lists that don't exist. The body is optional context, and none of these rules apply to it (D92).
  - **Warnings:** `filingWarnings()` notes long fields in the result's `warnings`, and any field, or the body, that looks like it holds a secret (B-vqn69), naming the field and what the text looks like, never the text. The card is filed anyway. `Store.reviseCard` warns the same way.
  - **In a hosted repo** (its config names a project), a card goes to the service as it's filed, and its first version can't be taken back, so a draft that `secretsIn()` flags is refused before anything is written (`LooksLikeSecret`, B-jfkv9), unless it gives `secret_reason`, why it's filed anyway, which is kept on the card. `Store.reviseCard` refuses the same way. Elsewhere it only warns, as above (D136).
  - **The filing check:** `Store.matches` returns open cards and resolved decisions with the same canonical topic, or a title similar enough (`SIMILAR_TITLE`). Any match raises `PossibleDuplicate` unless the caller forces it.
  - **The gate** (M8, D144, D145; [[src-routing]]): every revision is written through one private step that runs the rules (`route()`) over the draft's facts, `reverse` and the level it asks for, under the preferences in force (`Store.inForce`), and writes the card at the level that gives (`levelInForce()`), with its record beside it, `cards/<id>/gate-r<n>-cli.json`, in both layers. The result carries it as `gate`. The draw is `drawOf()`; the burn-in counts every enforcing held record on the card's row in the live layer, so across branches, and the record keeps the count (`held_before`). A card filed under the name `baesian` (conflict cards) is Baesian's own and always shown. The gate fails toward the reviewer: if it throws, the card is shown at the level asked for, or provisional, and never below hard with a hard-by-default fact (D144, D146); an unreadable newest preference file runs "Today" in shadow, with a warning. With no preference file, a draft whose facts include one of `HARD_BY_DEFAULT` is hard, whatever level it asks for, and `hardBecause` names the facts; a repo may lower security and privacy to provisional (D146).
- **`Store.reviseCard`** writes the next revision, and only for a card whose status is `returned`. The gate shows a revision that follows the reviewer's own answer; one returned because a parent went the other way (D80) is gated as a new decision.
- **`Store.fileOwn`** files a card Baesian writes itself, with the fields only it sets (`convention`, `pref_row`, `pref_from`, `pref_to`), creating its deck on first use: convention cards and slider proposals ([[src-routing]]).
- **`Store.mergeTopics`** writes a topic alias (D44, D111) from one topic's canonical key to another's, so aliases never form a cycle. It refuses two topics that are already one, and a target no card uses. Aliases are immutable: a merge can't be undone.
- **Rules from answers (D16, D109, D110):** `Store.ruleAsked` says whether the latest verdict on a decision carries `make_rule`, or accepts a convention card (D161), and no draft exists yet. `Store.draftRule` files the draft: a card built from the decision, in its topic and deck, that `depends_on` it and carries `rule` and `rule_covers`. When the reviewer accepts the draft, or answers it with their own wording, `Store.addVerdict` saves the rule (`saveRule`), once per decision.
- **Retiring a rule (D119):** a verdict's `retire_rules` names rules the chosen option breaks. `Store.addVerdict` refuses it, writing nothing, unless the verdict chooses an option (`accept` or `alternative`), that option's `_breaks` lists each rule, and none is retired yet. It then writes a `RuleRetirement` beside each rule and copies it into the record.
- **`Store.replyToCard`** writes the agent's one reply (D89, D104): the next revision, a copy of the last plus `reply`. It's allowed only when `Store.canReply` says so: the latest answer went against the pick (`alternative` or `correction`), and no revision has had a reply. The reply reopens the card. The D81 brief counts the answer the reply was to as the earlier one. The gate always shows a reply, and a rule draft (`Store.draftRule`), which is Baesian's own card.
- **`Store.attach`** records an `Attachment` (with no folder path, D121), and copies the card's revisions into this worktree's record. **`Store.waiting`** counts the filer plus the attachments.
- **`Store.withdraw`** writes the card's single `Withdrawal`, and only for the agent that filed the card or one attached to it; a second withdrawal is refused too (`NotAllowed`). Agents name themselves, so this guards against mistakes, not against an agent set on it. **`Store.withdrawal`** reads it back, for the vault adapter's notes ([[src-vault]]).
- **`Store.setVault`** records the vault in the worktree's `config.json`, keeping its other keys (M6). `Store.init` writes the config only when there's none, so `baesian init --vault` in a repo already set up goes through it. **`Store.setLink`** records the repo's link to the hosted service the same way (M9d, B-5gnea): the service, the project and the repo's first commit, set together; `baesian login` calls it once the machine is approved ([[src-sync]]). In personal mode both write the clone's own config, and `Store.setLink` keeps what the clone held first (above).
- **`Store.addVerdict`** is for the client only. It rejects stale revisions, and keeps `at` strictly increasing per card. It refuses `should_have_asked` on a card whose gate record doesn't say held (D151). Accepting a slider proposal writes the preference file it proposes, with `from_card` naming it, unless the row has moved since (B-y6jn6).
- **Preferences (D147):** `Store.preferenceNames` lists the files, oldest first; `Store.preferenceFile` reads one; `Store.inForce` gives the settings the gate applies (`InForce`): the newest file, or "Today" in shadow with none, or with one it can't read, saying why. `Store.writePreferences` is for the client only, through the local server, and the slider acceptance above: it applies a change over the file in force, from a preset if one is named or the one the setup survey's answers suggest (`suggestPreset()`), and refuses one whose `replaces` isn't the newest file (`StalePreferences`). The schema refuses security or privacy below "tell me but carry on". `settingsOf()` reads a file as the gate does, the commit gate's paths among it (`Settings.paths`, B-qkek1). A change keeps the file in force's paths unless it sends a list, and a list it sends is kept as `pathSetting()` says: left out when it's the built-in one, so it means the built-in one; a list that isn't one of globs is refused (`ValidationError`). The commit gate reads its paths from `Store.inForce` ([[src-gate]]), so in a hosted repo an unsigned file, or a signed one that makes the gate see less without the passkey's proof, never sets them.
- **`Store.recordFallback`** notes that an agent proceeded on a blocking card without a verdict (D46). **`Store.fallbacks`** lists them.
- **`Store.writeLedger`** records that a commit builds on a card (D15). The post-commit hook calls it, and **`Store.ledger`** lists a card's entries, oldest first; **`Store.ledgerEntries`** lists every card's (D181). A changed answer's brief merges them with the history's trailers (D81, B-9v5xj; below).
- **`Store.writeMerge`** records a merge the hooks found (D181), live only, at `mergeFile()`'s path, named by its commit and branch: the same merge found again, here or pulled from another machine, writes nothing (it returns undefined). Since B-w41p7 it takes the tip that landed and the commits citing cards it brought, which the hooks have checked against git's ancestry; a later fast-forward of the same branch lands at another commit, so it's a file of its own, and nothing is ever rewritten. **`Store.merges`** lists them, oldest first. `snapshot()` gives both to the client as the state's `merges` and `commits` (the ledger's entries, each commit and card once, with no body), for the branches panel ([[Client Build]] item 26).
- **`Store.defaultBranch`** (B-jr8mk) is the repo's default branch, the trunk the panel draws on top: on your machine read from git each time (`defaultBranch()`, [[src-sync]]), on the relay what a machine last sent (`DEFAULT_BRANCH`, `default-branch.json`); undefined when neither says. `snapshot()` gives it as the state's `defaultBranch`. Over storage alone it reads the file and calls no git, as the rest of the store doesn't.
- **`Store.touchPresence`** writes the client's heartbeat atomically, and **`Store.presence`** reads it. A missing or unreadable file means "unknown", never an error.
- **`Store.startWaiting`** writes an agent's waiting marker (D90), replaced whole (`Storage.replace`), and returns its `since`, its `path` in the layer (which `baesian wait` sends to the relay in a linked repo, M9d), and a handle to refresh it and to stop, which removes it. If the same agent already has a fresh marker on the card, from an earlier run of a sliced wait (D101), it picks that one up again, keeping its `since`. **`Store.waitingOn`** lists a card's markers, each stale once it's older than `WAITING_STALE_MS` (90 seconds, as presence). The markers are mutable, like presence; everything else is written once.
- **`Store.syncRecord`** copies verdicts and ledger entries for the cards the record already holds, plus everything in their card directories: revisions, gate records, withdrawals and fallbacks (D37). It also copies every rule, retirement, topic alias and preference file, which apply to the whole repo (CI rechecks a gate record against the preference file it names): the client saves them into the record of the worktree it runs in, the local gate reads them from the live layer, and CI reads each commit's own record, so without this a rule passed locally and failed in CI on any other branch. The service's keys in `trust/` go to every branch's record the same way, and a signed file goes with its signature and proof, in a hosted repo only once it counts (above). Given cards the record doesn't hold yet, it copies them in too, with their decks: so a personal clone switching to shared mode writes its branch's record (B-4rwyz, [[src-cli]]). In personal mode it copies nothing.

All of these go through a private write-once helper, which writes through `Storage.create`: so a second write fails, and another process never reads a file half-written. In a folder, the file is written whole to a temporary file beside it, then linked into place, which fails if the name is taken, and a temporary file (`.tmp`) is never listed (`FolderStorage.create`). An exclusive create alone left the file empty for a moment, which the server's four-writer test caught once the gate made filing read more of the layer. Nothing is ever edited in place.

**`Store.ensureBranchDeck`** creates the branch's deck on first use. If another agent on the branch creates it at the same moment, the exclusive create fails, and that's taken as success, since the deck now exists. The server's four-writer test found this race.

## Reading

- **`Store.status`** is computed, in this order:
  1. withdrawn (by the agent, or because a `depends_on` parent was rejected);
  2. superseded: a resolved card `supersedes` it, or a resolved conflict card names it in `conflict_of` and chose the other decision (D35);
  3. returned, when a `depends_on` parent's latest verdict chose something other than its proposal (`alternative` or `correction`) after this card's latest revision and its own latest verdict (D80);
  4. otherwise, the latest verdict on the latest revision: resolved, returned (including `see_it_run`), rerouted or deferred; or, with none, `held` if the revision's gate record (`Store.gateRecord`, the CLI's; the relay's signed one in a hosted repo, D158) says held while enforcing (D150), and open if not. In a hosted repo, only verdicts that count are read (above).
- **`PENDING`** is the set of statuses that still need the reviewer; a held card isn't in it. **`Store.decision`** gives what was decided for a resolved card. **`Store.gateRecords`** lists a card's gate records.
- **`Store.canonicalTopic`** follows `TopicAlias` files. **`Store.topics`** lists the canonical topics in use.
- **`Store.briefs`** says what an agent should be told beyond the verdict, computed from the records and never stored (`Brief`). Each names who wrote its texts, the reviewer of each answer and the parent's agent and branch, so an agent reads them quoted with their authors (D169):
  - `parent-decided-otherwise`: a parent went the other way, so this card is returned (D80);
  - `answer-changed`: the answer changed after an earlier one had resolved the card (D81). It lists the commits built on it before the change (`BriefCommit`); only commits that cite the card, so a lower bound. Since a rebase or a squash merge rewrites commits, and the ledger's hashes go stale, they're found by their trailers (B-9v5xj): `readHistory` ([[src-gate]]) gives the commits on any branch, local or remote-tracking, whose `Baesian-Card` trailers cite the card, authored before the change (a rebase keeps the author's date, and a rework made after the change isn't listed). Each is named by the branch the ledger says it was made on, or else the branch the search found it on; a ledger entry made on a detached HEAD doesn't count (since D181 one made during a rebase names the branch being rebased). Then come the ledger's entries whose commit is on no branch now, marked `rewritten`; one whose commit this clone doesn't have, another machine's pulled from the relay (D181), isn't marked so, since nothing here says it was rewritten. The history is read once per view, and cached per process while the branches stay put. The ledger itself is unchanged.
  - `held-answered`: the gate held the card back, so its agent went ahead with its pick, and the reviewer has since overturned or rejected it, on an audit or from the held-back list (D151). Its commits are found as for `answer-changed`.
- **`Store.view`** runs a function over one consistent read of the live layer: each file is read once, and the list of cards, each card's verdict files and each card's claimants (`Store.claimants`: the cards that supersede it or name it in a conflict) are built once. With a `report`, a file that can't be read is reported and skipped instead of thrown; the server reads that way ([[src-server]]). Without one, a bad file still throws, so the CLI stays loud. The CLI's `list`, `show`, `inbox`, `topics`, each poll of `wait`, and filing's checks read through a view: a card's status reads the others, and reading afresh made them quadratic ([[2026-11-03 Scale Test]]). A view must not span a write it then reads back: filing ends its view before writing.
- **`Store.inbox`** returns `InboxItem`s newer than a per-branch cursor (`Cursor`, a mutable file in the live layer, replaced whole in the newest format whenever it moves), and advances the cursor unless peeking. They cover verdicts on the branch's cards (filed or attached), and dependents returned by a parent's verdict, listed under the dependent's ID. Each carries its brief. Items that `baesian wait` has already delivered are skipped. Baesian's own proposals are the reviewer's business: a slider proposal never reaches an inbox, and a convention card reaches every branch's only with a yes, which asks any agent for a rule (D161). `Store.canReply` is false for any card Baesian filed. With a `session` (the harness's session id, which the plugin's hooks pass), the session keeps a cursor of its own, so each session on the branch hears each verdict once (B-ghhym, provisional). A session's first read saves its place, starting from the branch's cursor, which keeps up with the newest any session has read; so a new session isn't handed old verdicts, and one session reading first can't take another's. What `wait` delivered stays delivered for every session.
- **`Store.markDelivered`** is how `wait` says what it delivered: the verdict it printed, and those behind its briefs. They're listed in the cursor file's `delivered`, beside its time, which doesn't move, so older verdicts on other cards stay in the inbox. Once `inbox` has shown everything newer than the cursor, the cursor moves past it all and the list empties.
- **`Store.branchDeckId`** and **`Store.ensureBranchDeck`** give each branch its default deck.
- **`Store.rules`** reads every rule, each with its retirement if it has one. The gate uses the `covers` globs of rules that aren't retired to acknowledge facts automatically.
