# src/login.ts and src/sync.ts: the CLI's side of the hosted service (M9d)

The design is [[Hosted Service]] sections 1, 2 and 5 and [[Formats for v1]] section 8, as the cards in deck `hosted` decided them. The service's side is [[service]]; the formats are in [[File Formats#The CLI's side of the relay (M9d)]]. The commands that use these are in [[src-cli]], the MCP server's tools in [[src-mcp]].

## src/login.ts: signing a machine in

**The grant file (B-gq8j1).** `grants/<project>.json` beside the personal config (`grantsDir()`, `grantPath()`, from `userConfigPath()`), a `MachineGrant`. **`writeGrant()`** writes it whole: a temporary file created with mode 0600 in a folder made 0700, renamed over the old, so nobody else can read it and a reader sees the old tokens or the new. **`readGrant()`** reads it; one it can't read throws `SignedOut` without quoting it, since it holds tokens. **`removeGrant()`** deletes it. No token is ever printed, logged or put in an error.

**The device flow (RFC 8628, B-t5wxr).** **`signInMachine()`** posts `client_id` (`CLIENT_ID`, `baesian-cli`), the project and the machine's name to `/v1/machines/device`, shows the code (`onCode`), and polls `/v1/machines/token` at the interval the service gives, five seconds more after each `slow_down`. A refusal or an expired code throws `SignInFailed`. It returns the grant; the caller writes it. **`machineName()`** makes the hostname into a name the service takes.

**Refreshing (RFC 6749, RFC 9700).** **`refreshGrant()`** runs holding the project's lock file, `grants/<project>.json.lock` (`withGrantLock()`, private; a lock older than 30 seconds is taken over), because a refresh token is used once and the service revokes a grant whose refresh token comes back: two commands refreshing at once would end the grant. Under the lock it reads the grant file again; if another command refreshed meanwhile, it takes those tokens and sends nothing. Otherwise it refreshes, writes the new pair, and only then returns it. A grant the service refuses (`invalid_grant`: revoked, lapsed, or its refresh token seen twice) is removed here, and `SignedOut` says to run `baesian login`.

**Revoking (RFC 7009).** **`revokeGrant()`** posts the refresh token to `/v1/machines/revoke`, which ends the grant and its access token.

**Errors.** `Offline`: the service couldn't be reached, or didn't answer within `REQUEST_MS` (10 seconds a request), or the command's signal stopped it; `reason()` says why in a few words. `SignedOut`: this machine has no grant that works for the project. `SignInFailed`: signing in didn't finish.

**Linking (B-62qnz, B-5gnea, B-w4g6c).** **`newProjectId()`** makes a project's ID, `p-` and 20 characters of Crockford's base32 (100 bits): the CLI picks it, and approving it makes it the approver's (M9c). **`firstCommitToLink()`** is the commit the repo's history starts from, the oldest of `rootCommits()`; it refuses a shallow clone, which can't see it (`isShallow()`), and a repo with no commits. **`linkRepo()`** writes the service, the project and the first commit into the config (`Store.setLink`): the record's, or in a personal clone (B-4rwyz) the clone's own, with nothing to commit, which keeps what the clone held then, in place of the record at a linking commit ([[src-store#Personal mode (B-4rwyz)]]). Sync is the same in either mode. The service is the one `--service` or `$BAESIAN_SERVICE` names, or else **`DEFAULT_SERVICE`**, https://baesian.dev (B-f2mfb), whose approval page names it and takes a passkey before any card leaves the machine; `baesian login` says which it's linking to when nobody named one. **`linkAck()`** is the trailer that covers the gate fact the link is (B-w4g6c), which `baesian login` prints inside a commit command ready to run. **`projectPage()`** is the project's page on the website, `/projects/{project}` (M9e), which `baesian login` prints once the machine is in, and `baesian serve` opens in a linked repo (D143). The CLI sends the service only the project's random ID and the machine's name, never the repo's: a new project is named by the person on the approval page (B-zqkwk), and `baesian login` says so.

## src/sync.ts: syncing through the relay

**Is this repo linked, and is this machine in?** **`relayFor()`** gives a `Link`: `off` when the config names no project (nothing changes, as before M9d); `stopped` when **`linkProblem()`** finds this checkout isn't the project's repo (B-5gnea: its history doesn't start at the config's `first_commit`, or the config has none, or there are no commits yet; a shallow clone skips the check); `signed-out` when there's no grant for the config's service and project; else `on`, with a **`RelayClient`**.

**`RelayClient`** calls the project's addresses, `/v1/projects/{project}/…` (B-7z97x), with the access token as `Authorization: Bearer`. **`RelayClient.token`** refreshes when the token has less than a minute left; on a 401 it reads the grant file again (another command may have refreshed), else refreshes, and tries once more. **`RelayClient.liveUrl`** is the live socket's address.

**Pulling.** The log after `pulled` (`GET log`), page by page; a log whose `head` is below `pulled` is a project deleted with its owner's account and made again (B-b46z3, M9f), so the machine starts afresh, with `pulled` at 0 and nothing marked as the relay's, and the agent is told; each entry is read with `readRelayEntry()` (an encrypted one is refused, D137) and written into the live layer as if it had been written here, with an exclusive create, its `.sig` first, so no reader sees a signed file without its signature. Only the folders the relay holds are written (`cards`, `decks`, `verdicts`, `rules`, `topics`, `preferences`, `trust`, `attachments`, and since D181 `ledger` and `merges`; never presence, cursors, markers or `relay.json`); an entry whose bytes don't match its size and digest is skipped, and one whose body was removed by the relay's retention (D137, B-9jqt4, B-ec3kj, M9f) has nothing to write; when this machine has that file nowhere, in the live layer or the worktree's record, the agent is told once per pull, naming the cards. A path this machine wrote first with other bytes takes the relay's copy, in the worktree's record too, and the agent is told (`put()`):
- a merge (D181): two machines found the same merge and said it differently (the cards each knew of, when); the relay's stands, quietly;
- a revision: it was **revised on another machine first**, so this machine's wasn't sent, as the local API's 409 says of a stale verdict;
- a card's first revision this machine never sent: **another machine's new card took its ID**, so this machine's card is taken out (`takeOut()`) and, once the pull is done, **filed again under a new ID** (`Store.fileCard`, with the level its agent asked for, from its gate record), and the agent is told the new ID.

**Pushing.** **`agentWritten()`** says which files a machine pushes, the kinds the relay takes from one (`agentKind()` in `service/src/uploads.ts`; a test keeps the two in step): card revisions, the CLI's gate records, withdrawals, fallbacks, attachments and decks, and since D181 the ledger's entries and merges. **`unsent()`** lists those the relay doesn't have yet, in its order: decks, then revisions, each card's in order, then the rest, then the ledger's entries and the merges. A ledger entry goes only when its body is the one line naming its commit's short ID and its card, and it names its commit (`plainLedger()`): a commit's subject and message never leave the machine, and an entry written before D120, which listed the commit's files, stays. A 410 for a ledger entry says its card's text went, as for the card's own files. When a repo is first linked that's everything in the live layer (B-6k0rk). Each goes up with `PUT files/{path}`; a 409 (written first elsewhere) is followed by a pull that brings the relay's copy, and the push runs again, at most three rounds; a 410 says the relay removed that card's text (M9f), so the card's files are marked as the relay's and not offered again, with a note; anything else refused stays here, with a note, and is offered again next time.

**The default branch (B-jr8mk).** After the files, a push sends the repo's default branch, `default-branch.json` (`DefaultBranch`, only its name), when what git says here (`Store.defaultBranch`) isn't what this machine last sent (`RelayState.default_branch`); the relay keeps it as mutable state, in place of the one before, and the state it serves the website carries it as `defaultBranch`. It's sent apart from the files (`agentWritten()` doesn't name it, though `agentKind()` takes it), counted among none of them, and quietly: a relay that refuses it (an older one) is offered it again at the next sync. Only a machine whose reading changed sends it, so two machines that read it differently don't take turns. **`defaultBranch()`** in `src/git.ts` reads it, a few local git calls: the remote's HEAD (`refs/remotes/origin/HEAD`, which `git clone` sets, or with no `origin` the one remote's); else `init.defaultBranch`, where a local branch of that name exists; else the branch `git init` ran on, the one whose reflog starts with `commit (initial)` (the oldest, where an orphan branch has one too). Reflogs expire, so an old repo with no remote may say none; the panel then guesses as before.

**The answers from before linking (B-3zjjx).** After what agents wrote, **`unsentBeforeLinking()`** lists the answers, rules, rule retirements, topic merges and preference files that count here as from before linking (`Store.answersFromBeforeLinking`: unsigned, and in the record at the linking commit, B-45xz8), in that order, which the relay doesn't have yet; they go up the same way. It lists none once someone has answered on the website, as far as this machine has pulled (anything in those folders with the service's signature): the relay takes them only before the project's first answer there. If the relay says that window has closed (403, `before_linking: "closed"`), the rest stay in git, where they still count, and the agent is told. One pulled with `before_linking` is noted in `uploaded`: another machine has sent it, and this machine counts it only where its own record at the linking commit holds it.

**`relay.json`** (`RELAY_STATE`, `RelayState`): `pulled`, the last sequence number pulled, `uploaded`, the files the relay has (acknowledged, or pulled from it), and `default_branch`, the default branch last sent (B-jr8mk), for one service and project; a project deleted and made again clears it with the rest. **`readRelayState()`** starts afresh when there's none, when it's another relay's, or when it can't be read: pulling again is harmless, since every file is written once. It's replaced whole after every sync, whatever got done (`Storage.replace`).

**When it syncs** (Hosted Service section 1; there's no daemon):
- **`syncRelay()`**: pull, then push. It never throws for the network, the grant or the relay: its `SyncReport` says `synced`, `offline`, `signed-out` or `stopped`, with the notes for the agent. `SyncOptions.sending` is told how many files a push is about to send, before it sends them, which `baesian login` prints;
- **`aroundFiling()`**, for the filing commands and the MCP filing tools: pull, run the command, push. When the pull couldn't reach the relay, the push isn't tried, so a command never waits twice;
- **`waitWithRelay()`**, for `baesian wait` and `wait_for_verdict` (B-bv49e): pull and push first, so the cards are on the relay and an answer already given is here; then the wait it's given (`waitOp`, or `waitAllOp` on several cards, B-xnae9, [[src-cli#src/wait.ts]]), with a `Listener` (private) beside it: the relay's live socket, opened with the bearer token in Node's WebSocket headers, whose `changed` messages each start a pull, so the wait's own poll finds an answer within a moment; each waiting marker sent up at each beat (`WaitOptions.onMarker`) and removed when its card is answered or the wait ends; and the reviewer's presence, read from the relay's state at a beat (once, however many markers it refreshes) and written into the live layer when it's newer, so the wait knows when they're away (D41). A socket that closes is opened again, after 1, 2, 5 and then 10 seconds, and pulls as it opens, for what changed while it was closed; and the listener pulls every `RESYNC_MS` (5 minutes) besides, since a wait in the background may run for hours, over a laptop's sleep or a socket that died without closing (B-xnae9).
  - **A wait with no time limit that starts offline** (`WaitOptions.untilAnswered`, `baesian wait --until-answered`) listens all the same: its first sync both ways happens when the socket opens, and until one has gone through, each pull pushes too, so its cards reach the reviewer. Any other wait that starts offline, or signed out, waits on the live layer alone, as before.

**Offline, or signed out,** everything local works as before: the command's own output is unchanged, a note goes to standard error (or after an MCP tool's text), and what's new goes up at the next command that reaches the relay. A quiet hook prints nothing.

## src/ci.ts: setting up CI (B-pt52b)

`baesian ci`, in a linked repo, pulls from the relay (`syncRelay()`, with no push), then prints what CI needs to run `baesian verify` with its keys pinned ([[src-verify#In GitHub Actions]]). Not linked, signed out, a copy of another repo, or offline, it stops and says what to run first: the keys must come from the service, through that pull.

- **`ciPin()`** reads the pin from the live layer the relay wrote (`.git/baesian/trust/`, `Store.trustFiles`), never the committed record (`.baesian/trust/`), which a commit can change: the project's line (`projectLine()`, B-mar8x), each service key and revocation, and each passkey key file whose `.sig` checks against those keys at the time it was enrolled (`checkSigned()`); one that doesn't is left out, with why (`CiPin.skipped`). Each line is the file's JSON compacted, its fields in the file's order, as the website shows a passkey's line when it's added. With no service key yet, it says so: the relay sends its key with the project's first file. `CiPin.site` is the website's origin, from the service's key, for the account page.
- **What it prints:** the service it read the keys from (the config's, which a commit can change: if it isn't the one you meant, stop), the lines, each passkey's handle and date with a request to compare its line with the one the website showed and the account page, and **`workflowSteps()`**: checkout with the full history, Node, and `npx --yes baesian@<version> verify` on a push and `verify --merge` on a pull request, each passing `BAESIAN_TRUST: ${{ vars.BAESIAN_TRUST }}`. The version is the release printing them (`VERSION`), pinned (B-c0e0d), with a comment saying so: a repo moves its CI to another release by running `baesian ci` with it and committing the steps. `--json` gives the same as data.
- **`--github`** then runs `gh variable set BAESIAN_TRUST` in the repo, with the lines on its input (**`runProgram()`**, replaceable as `Io.run`, so tests never run gh). Without gh on PATH, it says the variable wasn't set, and exits 1.

## Tests

`test/relay.test.ts` runs the CLI against the real relay: the service's own Worker, from `service/wrangler.jsonc`, started in workerd by Wrangler's `unstable_startWorker` from the service's packages (`test/relay-harness.ts`), its accounts database migrated, a signing key and the stand-in's sessions made for the run, nothing reached but 127.0.0.1. A machine's code is approved in the accounts database, as a person on the website (M9e) would. It covers signing in and linking, a refusal, refreshing (and a refresh token used twice ending the grant), signing out, pushing and pulling between two clones, a signed answer counting, everything going up at first link, a revision revised elsewhere, a new card's ID taken elsewhere, offline, `inbox --quiet` staying quiet, `pre-commit`'s timeout against a relay that never answers, `baesian wait` hearing an answer over the socket with its marker on the relay, `baesian wait --until-answered` on two cards hearing both answers over the socket, each card's marker leaving the relay as it's answered, and the same starting offline and sending its card once the relay answers (B-xnae9), the MCP server syncing with the same grant and saying when it's signed out, the answers from before linking going up once at first link, shown as decided on the relay, not counted by a clone whose record at the linking commit lacks one, and offered no more once someone answers on the website (B-3zjjx), the first-commit check on a template-style copy and a shallow clone, and `baesian ci` (B-pt52b): before the relay has sent its key, then the pin's lines from what it sent (a passkey key file signed with the run's signing key, `LocalRelay.signingKey`, in, and one signed by another key out), `--github` with a stand-in for gh and without gh on PATH, `--json`, offline, and the config pointed at another service. Every test signs in from 127.0.0.1, so the harness raises the limit per network address (`LIMIT_ADDRESS`), and applies every migration in `service/migrations/` (`applyMigrations()`). Without the service's packages installed, those tests are skipped. `test/linking.test.ts` covers the gate fact (B-w4g6c), answers from before linking (B-45xz8), the project and linking commit under CI's pin (B-mar8x), and `baesian login`'s default service, offline (B-f2mfb). `test/ci.test.ts` covers `ciPin()` against the stand-in service: which passkeys it keeps, that it never reads the record's keys, and that `verify` takes the lines it prints.
