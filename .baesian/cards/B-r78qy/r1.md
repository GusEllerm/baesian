proposal: All twelve agent commands
proposal_then: "Twelve tools, one per agent command, named for the action: file_card, wait_for_verdict, check_inbox, show_card and the rest. An agent can do everything without a shell, and each tool is tested against its command."
alternative: The design's three tools
alternative_then: file_card, get_verdict (which can wait) and list_resolved (since a time), as the design lists them. Revising, replying, rules, attaching and withdrawing stay in the CLI, so those need a shell.
crux: Will agents use the MCP server where they can't, or don't, run the CLI?
crux_proposal: They will
crux_alternative: They won't
crux_fact: D128 makes the local MCP server 'usually the better way in' to the hosted service, beside the CLI. Claude Code and Codex both have a shell; some harnesses and sandboxed modes offer MCP tools without one (which ones isn't checked). Each tool's schema sits in the model's context unless the harness defers it. Tool names become a public interface once v1 ships.
rationale: An agent that files through MCP but must revise or reply through its shell has two interfaces to keep straight, and a harness without a shell would get half of Baesian. Each tool is a thin wrapper over the store code its command already uses, so the other nine cost little.
wrong_if: Agents with MCP always have a shell as well, and the extra tools crowd the model's context or confuse it.
check: In rehearse, count calls per tool over a few sessions in each harness, and how often agents mix the tools and the CLI.

The twelve are file, revise, reply, rule, attach, withdraw, wait, inbox, show, list, topics and template. People's commands (init, serve, sync, verify) and the gate preview stay CLI-only. The table of tools, their inputs, outputs and errors is in [[MCP Server#3. The tools]].
