D136 (B-vqn69) chose to warn, for a public repo's record, before the hosted service was designed. This card asks only about hosted repos, where the card also leaves the machine for the service. The new field would be on `CardMeta`, set only when the override is used.

**Your question (r1): the overhead, how robust it is, and git's own scanners.**
- *Overhead.* The check already runs every time a card is filed, to give D136's warning. Timed over this repo's 121 card revisions (344 KB), one pass takes about 2.5 ms, about 20 µs a revision. Refusing adds no scanning; it only stops the filing.
- *How easy, how robust.* Seven patterns (`SECRET_PATTERNS` in `src/schema.ts`): private key blocks; AWS access key IDs; GitHub and Slack tokens; JWTs; a key, token or secret parameter in a URL; and a name that contains key, token, secret or password, set to a long value with both letters and digits, so prose and a reference to an environment variable don't count. It flagged none of this repo's 121 revisions, though many are about keys, tokens and sign-in. It misses an unlabelled random string, a password in prose, and other services' formats (Stripe's, Google's, OpenAI's). Dedicated scanners go much further: gitleaks has roughly 150 to 220 rules, and TruffleHog about 800 detectors, many of which test a found key against its service (third-party counts, *unverified*). Either could add patterns, or run when installed; neither is proposed here.
- *Git's own scanners.* GitHub's push protection blocks a push that contains a known secret format. It's free on public repos; private and internal repos need GitHub Secret Protection, billed per active committer. gitleaks or TruffleHog can run as a pre-commit or CI check. All of them see the record when it's committed or pushed. In a hosted repo, a card goes to the service when it's filed (M9d), before any commit, so they never see that copy. And when one blocks a push of the record, the card's file is written once, so taking it out means rewriting the branch's history or bypassing the block.

Sources, read 2026-11-04: GitHub Docs, "Estimating the price of GitHub Secret Protection" <https://docs.github.com/en/code-security/how-tos/secure-at-scale/configure-organization-security/configure-specific-tools/estimating-the-price-of-secret-protection>; AppSec Santa, "Gitleaks vs TruffleHog" <https://appsecsanta.com/sast-tools/gitleaks-vs-trufflehog>.
