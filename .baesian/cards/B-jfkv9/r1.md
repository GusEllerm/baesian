title: A card that looks like it holds a secret, when hosted
question: In a hosted repo, should filing refuse a card that looks like it holds a secret unless the agent gives a reason, or file it with a warning as now?
doing: planning M9d, the CLI syncing through the relay
topic: hosted/secret-cards
deck: hosted
level: hard
touches:
  - security
  - privacy
  - schema
reverse: cheap
proposal: Refuse it, unless given a reason
proposal_then: baesian file and the MCP filing tool write nothing and say which field looks like a secret. The agent rewrites it, or files anyway with a reason, kept on the card. Nothing that looks like a key reaches the record or the service unnoticed.
alternative: File it with a warning
alternative_then: The card is filed, committed and uploaded like any other, and the agent sees the warning baesian file gives now (D136). Fixing it means a revision; the first version stays in the record and on the relay until retention drops it.
also_considered:
  - Refuse in every repo, not only hosted ones
  - Upload nothing that looks secret, but file it locally
crux: Will an agent put a real secret in a card often enough to be worth refusing, given false alarms?
crux_proposal: Yes
crux_alternative: No
crux_fact: "Filing warns now when a field looks like a secret (D136, `looksLikeSecret`): a private key block, a token in a URL, a `password = …` or `api_key = …` with a long value of letters and digits. A card's files are written once, so a revision doesn't remove the first version. The record is committed with the code, and in a hosted repo the card also goes to the service, which drops its text 30 days after delivery (B-9jqt4). D137 calls for a scan before anything leaves the machine. Hosted Service section 5 proposed refusing, with an override whose reason is recorded on the card: one new card field."
rationale: Once a card is written, its first version can't be taken back, from the record or the relay; refusing before anything is written is the only point where a mistake costs nothing. The override keeps false alarms cheap, and its reason shows in review.
wrong_if: The check fires mostly on example values in cards about authentication, so agents add reasons by habit and the refusal stops nothing.
check: While dogfooding, count refusals and how many were real secrets.
