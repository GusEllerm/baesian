proposal: The plugin registers it
proposal_then: The plugin gets a .mcp.json that runs baesian mcp. Installing the plugin starts the server in every session, in both harnesses, and a plugin update can change what it runs.
alternative: Each person adds it
alternative_then: The plugin carries no server. The README gives one command per harness (claude mcp add, codex mcp add) to run baesian mcp; those who want the tools add them, and the hooks work either way.
crux: Should installing the plugin also turn on the MCP tools?
crux_proposal: It should
crux_alternative: It should be a separate step
crux_preference: true
crux_fact: Claude Code starts a plugin's MCP servers automatically when the plugin is enabled; Codex reads a plugin's .mcp.json too (whether it asks first isn't checked). The server runs as you, in every repo you open, and lists its tools in each session; Claude Code defers them when there are many. It can't answer cards. A repo's own .mcp.json, which neither option uses, loads without asking in claude -p runs.
rationale: One install gives the hooks and the tools together. The server adds no capability the CLI lacks, since it can't answer, and the person still chose to install the plugin, unlike a server a repo names for itself.
wrong_if: People install the plugin for its hooks and don't want the tools, the tools cost noticeable context in repos that don't use Baesian, or a harness starts plugin servers without the person's consent.
check: In rehearse, start a session in a repo without Baesian and measure the tools' context in each harness; check whether Codex asks before starting a plugin's server.

The command, baesian mcp, is the same either way, and either way `baesian init` never writes a .mcp.json into a repo. The security reasoning (stdio only, no port, fixed descriptions, no answering tool) is in [[MCP Server#1. Transport, starting and registering]] and [[MCP Server#5. What the server must never do]].
