D140 (B-rca1z) puts each repo's relay in its own Durable Object. Account-level data isn't per repo, and no decision says where it lives. B-grrr9's background (open) names it a storage-layout choice for its own card. This is that card. It is a card under AGENTS.md as a storage-layout and infrastructure choice, and it touches privacy because the store holds every account's email address.

**What the store holds** (from decisions already made):
- *Accounts:* Baesian's stable account ID, the handle and the email address (D153, [[Formats for v1]] section 7), and settings such as the usage-count opt-out (D141).
- *Passkeys:* each credential's ID and public key (D139, D153). CI pins copies of the keys that answer hard cards (D159), but sign-in reads them here.
- *Sign-in and recovery:* the Globus link (D153), the saved recovery code's hash (B-jzgy4), short-lived email codes, device-sign-in codes and WebAuthn challenges, and browser sessions.
- *Machine grants:* one per machine and project (B-84e0d), with the machine's name and the hash of its current refresh token. Refresh tokens are single-use, and a reused one revokes the grant (RFC 9700, P15 section 2), so a refresh has to compare and replace the hash as one step.
- *Push subscriptions:* each device's endpoint and keys (D130, B-mjf3g).
- *The directory:* each project's ID, owner and members (P15 section 2), and invitations if B-mz6qc (open) chooses them.

**Cloudflare's own framing** ("SQL in Durable Objects vs D1"): "D1 is a managed database product", aiming for "a 'batteries included' feature set", including an HTTP API, schema management, import and export, and query insights; "SQLite in Durable Objects is a lower-level compute with storage building block for distributed systems." With D1, "your application code and SQL database queries are not colocated", so each query is a network hop from the Worker.

**How the options compare** (Cloudflare's docs, read 2026-11-03):

| | One D1 database | One Durable Object | Workers KV | An object per account |
|---|---|---|---|---|
| Consistency | strong on the primary; a batch is one transaction; read replicas (beta) lag unless the Sessions API is used | strong; requests run one at a time, so read-check-write is safe | eventual: changes "can take up to 60 seconds" to show elsewhere; last write wins; 1 write a second per key | strong per account; nothing spans two accounts |
| Size and throughput | 10 GB (500 MB on Free); single-threaded, "If your average query takes 1 ms, you can run at most 1,000 queries per second" | 10 GB (1 GB on Free); "a soft limit of 1,000 requests per second" | effectively unlimited | per object, as the second column |
| Restore | Time Travel, 30 days on Paid (7 on Free); a deleted database can be undeleted within 7 days | point-in-time recovery, 30 days | none | per object, 30 days |
| Export and inspection | a SQL console, `wrangler d1 execute`, exports through the REST API (Cloudflare documents a daily backup to R2), `wrangler d1 migrations` | Data Studio in the dashboard (queries are audit-logged); no export the agent found, so Baesian writes one | per key | per object |
| EU jurisdiction | `eu`, `us` or `fedramp`, set at creation only | set through the namespace when the object is made | at creation; data "can be cached outside the jurisdiction" | per object |
| Billing on Paid | rows read and written (25 billion and 50 million a month included); storage $0.75 a GB-month past 5 GB; no compute charge | the same row prices; storage $0.20 a GB-month past 5 GB; plus requests and active duration | keys read and written | as the second column |

- *KV* (also considered) can't make a refresh compare-and-replace atomic, which RFC 9700's reuse detection needs (the agent's reading). Cloudflare's workers-oauth-provider keeps token hashes in KV ([[Sign-in for the Hosted Service]], F14), but it doesn't detect reuse that way.
- *An object per account* (also considered) keeps accounts apart by construction, as D140 does repos. Sign-up and recovery still look accounts up by email, and the Machines page and project lists span accounts, so it needs a directory beside it, and changes across two objects aren't atomic.
- *Cost* is near zero either way at Baesian's scale: a few kilobytes per account (the agent's estimate). A Durable Object is billed for duration only while it's handling requests or can't hibernate.

**The EU question (B-grrr9, open).** Under either answer to B-grrr9, account data is one store in one place. Both options take a jurisdiction only when created, so moving account data later means a new store and a copy. D1 has export and import for that; a Durable Object needs Baesian's own copy code.

**If the store is lost or corrupted,** nobody can sign in: the passkey keys and recovery-code hashes are gone, and every machine's grant with them. The repos keep every card and answer (D127) and CI keeps the pinned passkey keys (D159), so people would start new accounts and link their repos again (B-jzgy4's background). Thirty days of restore points cover mistakes; only an export covers losing the Cloudflare account.

**Under either option:**
- *A grant could be checked where it's used.* A grant covers one project (B-84e0d), so the relay could check it inside that project's own object at each request, revoking at once, with the account store listing grants for the Machines page (the agent's suggestion, not decided here).
- *Strict rate limits* need Durable Object counters anyway, since Workers' rate-limiting binding counts per location (B-mz6qc's background), so the service has Durable Objects beside D1 under the first option.
