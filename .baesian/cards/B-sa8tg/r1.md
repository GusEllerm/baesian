proposal: Only the relay's signed record
proposal_then: The relay gates each card on arrival, with its own clock and draw, and signs its record. The CLI's record guides the agent at once. A card the relay hasn't gated isn't held in CI, so it needs an answer before merge.
alternative: The CLI's record, rechecked by verify
alternative_then: The CLI's record counts. baesian verify recomputes it from the card, the signed preference file it names, and a draw from the card's ID, so holding a card back needs no relay and works fully offline.
crux: In a hosted repo, should the agent's own machine be able to make a card count as settled at merge?
crux_proposal: If it shouldn't
crux_alternative: If that's fine
crux_fact: A held card counts as settled at merge, with no answer (D150). The gate reads the card's facts, level and reverse, the preference file in force, and a random draw. The card's time and ID are written on the agent's machine.
rationale: Holding a card back stands in for an answer at merge, and in a hosted repo only signed answers count (D138). The facts are the agent's either way, but the relay fixes which settings applied, and draws where the agent can't choose.
wrong_if: Cards filed offline routinely reach merge before the relay has gated them, so held cards in hosted repos keep needing answers.

The gate runs in the CLI at filing and again on the relay when the card arrives (P14). Locally the CLI's record is all there is. In a hosted repo the two can differ, and the relay's can be signed. The gate record's fields, the draw and how verify rechecks it are in [[Formats for v1]], sections 3 and 4.
