title: What an older Baesian does with a newer file
question: When Baesian meets a file in a newer format than it knows, should it refuse it, or read the fields it knows and skip the rest?
doing: "drafting v1's format changes (P16): how readers treat format versions they don't know"
topic: formats/newer-format
deck: formats-v1
level: blocking
touches:
  - schema
reverse: moderate
proposal: Refuse it, naming the version needed
proposal_then: "Schemas stay strict. A newer file fails with \"this record has card format 2; this Baesian reads up to 1: upgrade it\". CI must run a Baesian at least as new as the agents' and the service's."
alternative: Read what it knows, skip the rest
alternative_then: Unknown fields are skipped, and a new format may only add fields. An older CI or CLI keeps working on a newer record, but may miss what a new field says.
crux: Could a field added later change what a file means to a reader that skips it?
crux_proposal: If it could
crux_alternative: If additions never change meaning
crux_fact: Every schema is strict today, so an unknown field fails to parse. CI runs whichever Baesian its workflow installs, which can lag the agents' and the service's. The hosted service runs one version for everyone (D129).
rationale: Status and both gates are computed from these files, so a skipped field could make an answer that doesn't count look as if it does, or a card look settled when it isn't. A clear failure costs an upgrade; a silent misreading costs trust in the record.

D108 ruled out tolerant parsing before v1. After v1, readers and writers of different versions will meet: CI, agents' machines and the service upgrade at different times. This card decides what the older one does. The proposal is in [[Formats for v1]], section 1.
