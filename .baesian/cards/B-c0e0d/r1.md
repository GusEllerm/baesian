title: Which Baesian a repo's CI runs
question: Do the CI steps `baesian ci` prints run the latest Baesian release each time, or the release that printed them, pinned in the repo?
doing: "planning M10: what `baesian ci` prints once the command line is on npm"
topic: release/ci/version
deck: release-v1
level: hard
touches:
  - infra
  - user-facing
  - security
reverse: cheap
proposal: Pinned, moved by a commit
proposal_then: the steps run `npx --yes baesian@<version>`, the release that printed them; a repo moves its CI to a new release in a commit, by running `baesian ci` again.
alternative: The latest release
alternative_then: the steps run `npx --yes baesian@latest`, as today's unpinned `npx baesian` does, so every repo's CI takes each release the day it's out, its new checks and formats included, without a commit.
crux: Should a new Baesian release be able to change a repo's CI result without a commit in that repo?
crux_proposal: No
crux_alternative: Yes
crux_preference: true
crux_fact: "`baesian ci` prints steps that run `npx baesian verify`, unpinned, so each run fetches the latest release. `baesian verify` runs with the repo's pinned keys (BAESIAN_TRUST) and decides whether a commit's answers count. D157: CI must read every format the service and the agents write. This repo's own CI runs its own build (`node dist/bin.js`)."
rationale: A pin makes CI's result depend on the commit alone, and keeps a bad or compromised release from reaching every repo's merge gate at once; with a release of format overlap, a pin one release behind still passes.
wrong_if: A pinned CI meets a file from the service in a newer format, and fails until the repo moves its pin.
check: CI runs in hosted repos after the first release that changes a format, under the answer to the format-rollout card.
