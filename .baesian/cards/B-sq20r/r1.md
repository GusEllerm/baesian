title: The filing tool's input
question: In what form should the MCP server's filing tool take a card?
doing: drafting the MCP server proposal (P18) for M7
topic: mcp/card-input
deck: mcp-server
level: blocking
touches:
  - public-api
reverse: moderate
proposal: Fields, with a schema
proposal_then: file_card takes the card's fields as JSON arguments, with a schema generated from the store's card schema and the template's notes. The harness shows each field's guidance, and an error names the field.
alternative: One Markdown document
alternative_then: file_card takes one string in the template's format, parsed as baesian file parses it. Agents write one format for the CLI and the tool, and the tool's schema is a single text field.
crux: Do agents fill in a card better field by field than as the template's Markdown?
crux_proposal: Field by field
crux_alternative: As Markdown
crux_fact: "Today agents copy baesian template: YAML frontmatter with a comment on each field, and background below it. An MCP tool describes its arguments with a JSON Schema that the harness shows the model; the store's card schema can produce one, and the template's notes can describe each field. Either form would be checked by the same filing code."
rationale: "A schema is how harnesses expect tools to take structured input: the model sees each field's note, required fields are marked, and an error points at one field. Generating it from the store's schema and the template's notes keeps the two from drifting."
wrong_if: Cards filed through the schema come back for missing context, or fail validation, more often than cards written from the template.
check: In dogfooding, compare invalid_card errors and need-more-context answers for cards filed each way.
