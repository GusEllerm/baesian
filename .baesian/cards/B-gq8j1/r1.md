title: Where the machine's token is kept
question: Where should baesian login keep a machine's tokens, in a file only you can read, or in the operating system's keychain where there is one?
doing: preparing M9, the hosted service (P15)
topic: hosted/token-storage
deck: hosted
level: hard
touches:
  - security
  - dependency
  - schema
reverse: cheap
proposal: A file only you can read
proposal_then: Tokens go in a grant file in Baesian's user config folder, readable only by you (mode 0600), as Claude Code does on Linux. No new dependency, and it works the same over SSH, in containers and on the cluster.
alternative: The OS keychain, with the file as a fallback
alternative_then: Tokens go in the system's credential store on macOS, Windows and Linux desktops, as gh does; machines without one fall back to the file. It needs a native module, a new runtime dependency with a card of its own.
also_considered:
  - The macOS Keychain through its security command, with no module
  - The keychain only, refusing to sign in where there is none
crux: Is keeping tokens out of a plain file worth a native runtime dependency?
crux_proposal: Not worth it
crux_alternative: Worth it
crux_fact: Where a token is kept doesn't stop an agent running as you from using it through baesian; what the token may do is the boundary (B5 F11). What a keychain adds is that the token isn't in a file a backup, a dotfiles repo or a stray cat can pick up. Refresh tokens are single-use, so a stolen one, once used, gets the grant revoked at the real CLI's next refresh (RFC 9700). Claude Code uses the macOS Keychain, else a 0600 file; gh falls back to a plain file. keytar, the usual module, was archived in 2022.
rationale: The keychain doesn't protect against the agent, which is the threat that matters here, and a native module is a build and install risk on every platform. A 0600 file with short-lived, rotating tokens is what comparable tools fall back to.
wrong_if: A token turns up in a backup, a dotfiles repo or a pasted log, or the first outside users expect keychain storage and say so.
check: Before publishing, look at whether common dotfile tools sync ~/.config by default, and ask the first outside users which they'd expect.
premise: Node has no built-in access to the OS keychain, so using it needs a native module.
premise_option: proposal
premise_check: Check Node 22's and 24's documentation for a credential-store API, and whether a maintained module (such as @napi-rs/keyring) exists and builds for every platform Baesian supports.

P15 left this open ([[Hosted Service]], section 2, "Signing in from the CLI"). The grant file's fields are in [[Formats for v1]] (P16, section 8): service, project, machine, access_token, access_expires, refresh_token. With a keychain, the file would hold no token.

P15's lifetimes, the agent's defaults: access tokens last about an hour; refresh tokens are single-use and rotate, and a reused one revokes the grant (RFC 9700, B5 F10).

Checked for this card, through Context7: keyring-rs, a Rust library of the kind a Node module would wrap, uses the macOS Keychain, the Windows credential store, and on Linux the kernel's keyutils store unless the Secret Service is chosen. A Node wrapper for it wasn't found there, so the module named in the premise check is *unverified*. Headless machines, such as cluster nodes, often have no Secret Service, so they would use the fallback file under either option (the agent's understanding, *unverified*).
