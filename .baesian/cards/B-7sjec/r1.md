title: Where the commit gate's hooks live
question: Should the commit gate's hooks stay committed with the repo, or be installed into each clone's own git folder?
doing: reviewing security before release (overnight, step E2)
topic: release/hook-location
deck: release
level: hard
touches:
  - security
  - infra
reverse: moderate
proposal: Keep them committed, and gate changes to them
proposal_then: hooks stay in .githooks/ (D54); a change to a hook counts as an infra decision at the gate and in CI, so a pull request that changes one needs a card or an ack, and shows up in review.
alternative: Install them into each clone's .git/hooks
alternative_then: the hooks hold only `baesian hook <name>`, so a pull request can't change what runs; every clone runs `baesian init` to get them, and livedocs' hook would need the same.
crux: Will people commit on branches from contributors they don't fully trust?
crux_proposal: If rarely
crux_alternative: If often, as open-source maintainers do
crux_fact: Hooks in .githooks/ run on every commit made with that branch checked out, so a pull request that edits one can run code on a reviewer's machine. livedocs' pre-commit hook lives there too. Nothing runs from a fresh clone until `baesian init` sets core.hooksPath.
rationale: Versioned hooks are what every hook manager does, and they keep each clone in step; making hook changes a gated decision puts them in front of a person, which is the risk.
wrong_if: the repos that use Baesian take pull requests from people the maintainers don't know
check: whether the dogfooding repos (this one, then personal-website) accept outside contributions
