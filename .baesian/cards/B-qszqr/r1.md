title: When the command line uses colour
question: How should the command line decide whether to colour its output?
doing: a UX pass over the command line's output, asked for by the user
topic: cli/output/colour
deck: cli-output
level: provisional
touches:
  - user-facing
  - public-api
reverse: cheap
proposal: The command line decides, plainly for agents
proposal_then: Colour only on a terminal, never when an agent's harness runs the command (Claude Code, Codex and others say so in their environment), never under NO_COLOR, even if FORCE_COLOR is also set; FORCE_COLOR turns it on otherwise. Two global flags, --color and --no-color, override all of it. Node's styleText only paints.
alternative: Node's own defaults
alternative_then: "Node's styleText decides: colour on a terminal, off under NO_COLOR, and FORCE_COLOR wins over NO_COLOR, printing a warning when both are set. No flags of Baesian's own. A harness that runs commands in a pseudo-terminal gets colour codes in its text."
crux: Must an agent's harness never receive colour codes, even when it runs commands in a pseudo-terminal?
crux_proposal: Yes
crux_alternative: "No: harnesses can strip them"
crux_fact: "Tested by the audit: Node's styleText colours its output under Claude Code's CLAUDECODE=1 when stdout is a pseudo-terminal. Its stream check exists only from Node 22.8, while Baesian supports Node 22 and later. NO_COLOR's own convention is that it turns colour off whatever else is set."
rationale: Colour codes in an agent's context are noise it pays for in every read, and the agent can't see the colour anyway. Opting out should always win.
