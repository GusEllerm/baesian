proposal: Baesian accounts with passkeys
proposal_then: You sign up with an email and a passkey; no third party is involved. Recovery is by email and a second passkey. The service knows nothing about your GitHub account or repos.
alternative: Sign in with GitHub
alternative_then: One click for most developers, with GitHub's own two-factor and recovery. The service depends on GitHub's OAuth, learns your GitHub identity, and people without a GitHub account can't join.
crux: Will everyone who answers cards have a GitHub account, and is depending on GitHub for sign-in acceptable?
crux_proposal: Not everyone, or not acceptable
crux_alternative: Yes to both
crux_fact: Reviewers can include domain experts who aren't developers; research use comes later (D2). Either way, hard-card answers would ask a passkey to verify you, which with GitHub sign-in means a second credential. GitHub sign-in can be added later beside passkeys; accounts built on GitHub IDs are harder to move off.
rationale: No dependency on another company for who may answer, and the passkey the account is built on is the same one that verifies hard-card answers (H4).
wrong_if: Most early users ask for GitHub sign-in, or setting up a passkey proves a barrier on the devices they use.
check: Sign-up drop-off at the passkey step, once outside users try it.
