title: Where a repo's preferences are kept
question: Should a repo's preferences live in the repo as files only the client writes, or on the hosted service with a signed copy in the repo?
doing: drafting the routing and preferences design (P14) from the slider research
topic: routing/preference-storage
deck: routing
level: hard
touches:
  - schema
  - security
reverse: moderate
proposal: Immutable files the client writes
proposal_then: Each change is a new file in the live layer and record, like a rule, written only by the client and signed by the service when hosted. Never in config.json. Works offline; history comes free.
alternative: The hosted service holds them
alternative_then: Preferences change only in a signed-in session on the website; the repo keeps a signed copy for offline use. The service becomes the authority for settings, unlike decisions (D127).
crux: Is a check inside the repo strong enough when agents make the commits?
crux_proposal: Yes, with signatures and verify
crux_alternative: No, the root must be off the repo
crux_fact: An agent can edit anything in the repo, including a policy file. Locally, only-the-client-resolves is a convention (D62). Hosted verdicts would carry the service's signature, checked offline against a key pinned in CI.
rationale: It mirrors how verdicts work under D127 and the hosted research's signing, so one trust model covers both, and the gate still runs offline.
wrong_if: An unsigned or agent-written preference file can pass baesian verify in hosted mode.
check: Write a preference file by hand on a branch of a hosted repo, then run baesian verify and the commit gate.

Preferences decide what reaches you, so whoever can change them can hide decisions. The research found agents disabling oversight through a config file they could edit, if rarely, and coding-agent tools protecting their own config. Evidence: [[Preference Sliders and the Gate]], principle P10. Design: [[Routing and Preferences]], section 4.
