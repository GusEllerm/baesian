The Implementation Plan left this open for M9b: "short polls or hibernating WebSockets, since a long poll in a Durable Object is billed for its duration".

**What changes in each.** Today the client opens `/api/events` (`client/src/live.ts`), and the local server sends `changed` and a version, after which the client reads `/api/state` again (D96). With WebSockets, a hosted page opens one socket to the relay and gets the same message; the local server keeps its events. With polling, a hosted page asks for the version on a timer. `baesian wait` (M9d) would hold a socket for each run of at most 100 seconds, or ask every few seconds.

**Why not Server-Sent Events, as the local server sends them.** A Durable Object stays active, and billed, while a response stream is open, and can't hibernate. One page left open all day uses most of the free plan's daily duration.

**Hibernation, in Cloudflare's words.** "Durable Objects that are idle and eligible for hibernation are not billed for duration." Calling `accept()` on a WebSocket instead "will incur duration charges for the entire time the WebSocket is connected"; `ctx.acceptWebSocket()` is the hibernating form. A ping can be answered without waking the object (`setWebSocketAutoResponse`).
