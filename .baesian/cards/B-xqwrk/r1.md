question: Should Baesian's MCP server use the official TypeScript SDK, or implement the part of the protocol it needs itself?

proposal: The official SDK, v2
proposal_then: Adds @modelcontextprotocol/server and its core package, which need only the zod Baesian already has. Its serveStdio speaks both protocol eras, and each SDK release follows the spec's changes.
alternative: Baesian's own small implementation
alternative_then: No new dependency. Baesian writes JSON-RPC over stdio for both eras, initialize and server/discover, in a few hundred lines with tests, and follows each spec revision itself.
crux: Is following MCP's revisions by hand cheaper than taking a fast-moving dependency?
crux_proposal: It isn't cheaper
crux_alternative: It is cheaper
crux_fact: MCP's 2026-07-28 revision replaced the initialize handshake with per-request metadata and a server/discover method. Codex still opens with initialize by default; Claude Code asks for the new revision and falls back. So the server must speak both. SDK v2 (2.0.0 in July 2026, 2.4.0 on 2026-10-23) does; it depends only on zod ^4.2 and its own core package, 8.4 MB unpacked. Baesian needs only tools, over stdio.
rationale: Serving two protocol eras while the spec is still moving is what an SDK is for, and v2 costs two packages that share Baesian's zod. By hand, every revision becomes Baesian's work, with the risk of a quiet mismatch with one harness.
wrong_if: SDK upgrades break the server more often than the spec's changes would have, or its size matters to people installing Baesian.
check: Count SDK upgrades that need code changes from M7 to M10, and compare npm pack sizes with and without it.
