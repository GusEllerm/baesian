title: How a merge's file is named
question: Should a merge's file be named by its commit, the branch merged and its target, rather than its commit and the branch merged alone?
doing: "fixing the bug sweep's D3: a second merge of one branch at one commit was lost"
topic: gate/merges/file-names

level: provisional
touches:
  - schema
  - public-api
reverse: moderate
proposal: Name it by the target too
proposal_then: merges/<commit>-<key>.json, the key a hash of the branch and its target. One branch fast-forwarded into two branches at one commit is two files, on every machine and the relay. The relay checks the new name on upload. Files already written keep their old names; the panel counts one record found under both names once.
alternative: Keep commit and branch
alternative_then: "The first merge of a branch at a commit is the only one kept: a second, into another branch at the same commit, is dropped on the machine that found it, and replaced by the first wherever they meet on the relay."
crux: Can one branch, at one commit, merge into two different branches?
crux_proposal: Yes, it happens
crux_alternative: Not in practice
crux_fact: "Yes, by fast-forward or rebase: both land at the merged branch's own commit. Two builder worktrees started from one v1/next tip each record 'v1/next merged into worktree' at that commit; a branch fast-forwarded into main and into a release branch does too. With today's name the second is lost, on its machine and on the relay (reproduced in the sweep, and through the relay's upload)."
rationale: "A merge is a branch into a target at a commit: naming it by all three is what makes the same merge one file, and two merges two. It's a hash, so no name needs escaping."
