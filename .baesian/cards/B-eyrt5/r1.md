question: Should the command line's output follow one small system, the same words for agents and people with styling only in a terminal, or keep today's text with only its worst problems fixed?

  - user-facing
  - public-api
reverse: moderate
proposal: One system, two renderings
proposal_then: "Every command uses six patterns: a headline saying what happened, aligned fields, rows with a header, `next:` lines with the exact command to run (IDs filled in), notes and warnings, and errors that end with a next step. Agents and the MCP tools get plain text, never wrapped and never coloured; a terminal gets the same words with styling. `init` ends with the commit to make. About 60 to 100 tests change their expected text; the plugin's hooks keep working (two error phrases it matches stay)."
alternative: Fix only the worst problems
alternative_then: Today's text stays as it is, except the long lines are shortened, the missing next steps are added and the raw validation errors are summarised. Each command keeps its own shape, and nothing is styled.
crux: Is consistent, styled output worth a few days and 60 to 100 test updates?
crux_proposal: Yes
crux_alternative: No
crux_preference: true
crux_fact: "About 3 to 4 builder-days, in three phases: the next steps, the styling, then `list`, help and errors. What agents read changes too (headlines first, `next:` lines), but stays plain text; `--json` doesn't change."
rationale: The user asked for output that feels like part of the product. The patterns help agents as much as people (a headline first, the next command filled in), and styling costs agents nothing because they never see it.
