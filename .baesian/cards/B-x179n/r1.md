title: How the history scan is run on a repo already linked
question: Should the history scan, for a repo that's already linked, be a flag on `baesian sync` or a command of its own?
doing: "building B-dezkk's history scan: linking runs it once, and a linked repo needs a way to run it too"
topic: cli/history-scan

level: provisional
touches:
  - user-facing
  - public-api
reverse: cheap
proposal: "A flag on sync: baesian sync --history"
proposal_then: "`baesian sync --history` scans, records what it finds, prints each merge, and sends them with that sync, in one step; to see what it would record without recording it, run it on a copy of the repo"
alternative: A command of its own, with a dry run
alternative_then: a command such as `baesian merges --scan` prints what it would record, and records only with `--write`; the merges go up at the next sync, a second step
crux: Do you want to see what the scan would record before it goes to the service?
crux_proposal: "No: record and send in one step"
crux_alternative: "Yes: look first, then record"
crux_preference: true
crux_fact: "The scan is meant to run once per repo: linking a repo runs it before the first sync. Run again, it finds nothing new. What it records goes to the service with the sync, and the service keeps a merge's file once taken: one recorded wrongly can't be taken back there. In this repo it would record one merge (worktree-agent-aaba362 into overnight/2026-11-03); from a repo with no merges recorded, it found 28, none of them artefacts."
rationale: It's run once, and recording without sending leaves it half done; the flag reuses sync's own output and its relay step.
