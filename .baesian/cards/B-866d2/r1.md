question: "After 1.0, how do the tables in each project's relay storage change: by numbered migrations run as a project wakes, or only ever by adding?"

reverse: moderate
proposal: Numbered migrations, on wake
proposal_then: each project's storage records its schema version in its meta table; a release adds numbered migrations, run in one transaction the first time a project wakes after a deploy, which may change or drop columns.
alternative: Only ever add
alternative_then: tables and columns are only added, as now (`CREATE TABLE IF NOT EXISTS`); a change that needs a column changed or dropped is made as a new table beside the old one, which stays.
crux: Will a later release need to change or drop something already stored in a project's tables?
crux_proposal: Likely
crux_alternative: Unlikely
crux_fact: "Each project's Durable Object makes its tables with `CREATE TABLE IF NOT EXISTS`: files, log, meta, pending, before_linking, five retention tables and three notification tables. Nothing records which release made them, and nothing alters them. The accounts database has numbered migrations, five so far, applied by the deploy before the new code, adding only. The service is live, holding real projects, this repo's among them."
rationale: A version in the meta table costs one row and keeps every later choice open; without it, the first change that isn't an addition can't tell which projects still have the old shape.
