title: How long one waiting call lasts
question: How long should one call of the MCP server's waiting tool last?
doing: drafting the MCP server proposal (P18) for M7

deck: mcp-server
level: blocking
touches:
  - public-api
reverse: cheap
proposal: 100 seconds, as the CLI
proposal_then: wait_for_verdict waits at most 100 seconds per call, as baesian wait does (D101). With the reviewer still there it returns 'again', and the agent calls again, up to six times in the 9-minute budget.
alternative: The whole budget in one call
alternative_then: One call waits up to 9 minutes, reporting progress every 30 seconds. The registration raises Codex's tool limit to 10 minutes, and the agent makes one call instead of up to six.
crux: Is a model turn for each 100 seconds of waiting a cost worth configuring harnesses to avoid?
crux_proposal: It isn't
crux_alternative: It is
crux_preference: true
crux_fact: MCP calls aren't bound by the 2-minute shell limit behind D101's slices. Claude Code allows an MCP call about 28 hours by default, but drops a stdio call after 30 minutes without progress; Codex allows 300 seconds unless tool_timeout_sec raises it. Each 'again' costs the agent a model turn. The marker, budget and fallback are the same either way.
rationale: It behaves like baesian wait in every harness, with the same code and the same meanings, and with nothing to configure in a file both harnesses read. The extra turns are few and short.
wrong_if: Agents lose track of the loop and stop after the first 'again', or the turns spent waiting show up as a real cost.
check: In rehearse, count MCP waits that stop before a verdict, a fallback or the end of the budget, and measure the tokens each wait uses.
serves: the same behaviour as baesian wait in every harness

Cancelling a call removes the waiting marker under either option, and progress is reported when the harness asks for it. See [[MCP Server#4. Waiting within a tool call]].
