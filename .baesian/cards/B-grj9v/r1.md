title: How the service's signatures are encoded
question: Should the service's signatures on answers be OpenSSH signature files, or a small JSON signature file of Baesian's own?
doing: drafting the signature files' format (P16) for D138

reverse: moderate
proposal: OpenSSH signatures
proposal_then: Each signed file gets a .sig beside it in OpenSSH's format, with the namespace baesian, which ssh-keygen -Y verify can check by hand. Keys can be listed in git's allowed-signers form.
alternative: A small JSON signature file
alternative_then: "Each signed file gets a .sig.json: the key's ID, the algorithm and a base64 Ed25519 signature, like the passkey proof's file. Only Baesian's code checks it, and it can carry more fields later."
crux: Will anyone check an answer's signature without Baesian's own code?
crux_proposal: If someone will
crux_alternative: If only Baesian will
crux_fact: Both sign the file's exact bytes with Ed25519. Hard-card answers also carry a passkey proof (D139), a WebAuthn assertion with fields of its own, in a separate file either way.
rationale: A standard format lets anyone audit a public record's answers with tools they already have, as git's SSH commit signing does. Baesian's own parser for it is small.
