question: "Where do people read what changed in each release: GitHub Releases made from the tag, or a CHANGELOG.md in the repo?"

proposal: GitHub Releases, from the tag
proposal_then: the deploy workflow makes a GitHub Release for each tag, with notes written in the release commit (format changes, what to run again, Codex's hooks to trust again); npm's page links to it.
alternative: A CHANGELOG.md
alternative_then: each release commit adds a section to CHANGELOG.md at the repo's root, which ships in the npm package too; nothing else is published.
crux: Should the notes on each release ship inside the package people install?
crux_proposal: No
crux_alternative: Yes
crux_preference: true
crux_fact: "Nothing records changes release by release today; the vault's session logs and Decision Log hold the history. An upgrade can ask people to act: run `baesian init` again for new hook blocks, update the plugin, and in Codex trust its hooks again. Making a GitHub Release needs the workflow's `contents: write`; the deploy has `contents: read`."
rationale: A page per tag sits beside the code it describes and costs nothing in the package; the release commit is already where the version is set (B-3femd).
