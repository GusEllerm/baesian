title: What a blocked commit leaves staged
question: When the gate blocks a commit, should the record files Baesian staged for it stay staged?
doing: finishing the harness adapters; rehearse's agent noticed this in its test runs
topic: gate/blocked-commit-index
deck: m5-adapters
level: provisional

  - user-facing
reverse: cheap
proposal: Unstage them
proposal_then: When the gate blocks a commit, Baesian unstages the record files again, so `git status` shows only what you or the agent staged. The next commit stages the record again, as every commit does.
alternative: Leave them staged
alternative_then: "As now: the record files stay staged until a commit takes them, so `git status` lists them after a blocked commit, and a `git stash` in between takes them too."
crux: Between a blocked commit and the next one, does anyone act on what's staged?
crux_proposal: "Yes: stash, reset or look it over"
crux_alternative: "No: the next step is to commit again"
crux_fact: Baesian's pre-commit hook stages the whole record (`.baesian/`) for every commit, and the commit-message hook can then block the commit; git keeps whatever was staged. Every later commit stages the record again either way. A stash taken in between holds the staged record files, and the next commit copies them back from Baesian's own store, so popping the stash then runs into files that already exist.
rationale: Agents often stash or check `git status` after a commit fails, and files they didn't stage are confusing at best; the stash case is a real collision. Unstaging costs nothing, since the next commit stages the record again.
