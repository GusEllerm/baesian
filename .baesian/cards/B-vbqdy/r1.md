proposal: Pinned in CI, outside the repo

alternative_then: The service's keys are listed in a file in .baesian/, and the commit gate treats any change to it as needing a hard card. One place, nothing to set in CI, and it works anywhere offline.
crux: Is a check whose key lives in the repo enough when agents make most of the commits?

crux_fact: Git keeps an allowed-signers file in the repo only where every commit is signed, so only trusted committers can change it. In Baesian repos, agents commit, and the commit gate runs on their machine. CI reads each commit's own files, so one commit could add a key and an answer signed by it, unless verify checks each change to the file against the keys before it.
rationale: A trust root a commit can't change closes the add-a-key-and-sign loop without new logic in verify.
wrong_if: Setting a key in each repo's CI proves a barrier for users, or checking key changes against the previous keys proves sound in testing.

A signature check is only as strong as the place its trusted key comes from. If answers must be signed (H3), `baesian verify` needs the service's public key, and the question is whether an agent's commit could change it. See [[Hosted Service]], section 4, and [[Hosted Service - Strand B5 Prior Art and Security]], F15.
